# Chapter 1 — Solutions

## Knowledge questions

**K1.** ML engineering produces a model: its primary lever is the training process (data, features, architecture, optimization) and its primary artifact is a trained model file whose behavior is defined by a training set the engineer owns. AI engineering produces a system around a model it did not train: its primary lever is the surrounding software (prompt, context, tools, control flow, evaluation) and its primary artifact is the system, measured on an evaluation set built from the engineer's own tasks.

**K2.** One acceptable mapping (others exist):

| Layer | Failure that belongs here | Misplaced fix often attempted |
|---|---|---|
| Model | Model cannot follow a complex output format reliably | Adding more retrieved documents (context layer) |
| Context | Answer is stale because the policy changed last week | Fine-tuning the model (model layer) |
| Action | Wrong arithmetic, or wrong account balance quoted from memory | Longer prompt telling the model to "be careful" (context layer) |
| Control | A fixed five-step process sometimes skips a step because the model "decided" to | Adding a planner prompt to the agent (context layer) instead of making it a workflow |
| Operations | Nobody can say why yesterday's answer was wrong | Upgrading to a newer model (model layer) |

**K3.** Each rung multiplies the state space that must be evaluated and secured. A prompt has one call to test. Retrieval adds a search stage with its own recall and precision. Tools add every argument the model might emit and every result that might return, each an input to the security boundary. An agent loop adds every path through every tool across an unbounded number of iterations, so control flow itself becomes nondeterministic. Capability is not the ordering criterion; the cost of evaluation, security, latency, and money is, and the loop is the most expensive on every axis. It is placed last so that it is chosen only when the measured benefit of a dynamic path exceeds those costs.

**K4.** Mental model 6: every external tool widens the security boundary; the model proposes, code authorizes. Checks that should have run: (1) schema validation of the arguments, which is the only one that was done; (2) identity and permission: may this user send replies, in this tenant, on this ticket; (3) business rules and limits: ticket exists, is open, reply is within size and content policy, rate limit not exceeded; (4) side-effect handling: `send_reply` is irreversible and marked approval-required in Northwind, so it must be held for human confirmation, and it needs an idempotency key so a retry does not send twice. An audit record of the decision is the fifth.

**K5.** Strongest to weakest: (1) the 300-case evaluation set built from your own invoices, because it measures the configuration you will ship on the distribution you serve; (2) the replicated academic result on a public extraction benchmark, because it is independent and reproducible, though the benchmark may differ from your documents; (3) the vendor blog post, which is a claim under conditions that favor the vendor and may hide prompt format, sampling, or tool use; (4) the colleague's impression, which shows a capability may exist and nothing about frequency. The ranking is by independence and reproducibility, with the special status of your own set coming from its match to your workload rather than from its methodology.

**K6.** The registry version records what you intended to send; the content hash records what was actually sent after rendering. They diverge whenever the rendered prompt depends on request data: an interpolated date, a tenant name, a retrieved snippet, a feature flag. For debugging you need the hash (two requests with the same hash and different answers isolate model nondeterminism); for change management you need the version (pass rate before and after prompt version 7). Storing only one loses the other question.

## Engineering questions

**E1.** Twelve categories, routing to a queue: the information needed is in the ticket text itself, so stop at rung one, a prompt with an output schema that constrains the category to the twelve allowed values, plus deterministic routing code keyed on the category. Build a labeled evaluation set (a few hundred historical tickets with human labels) and measure accuracy per category. Evidence to climb: if per-category accuracy is poor on categories whose definitions depend on internal knowledge (for example, "billing" versus "contracts" depends on product names only Northwind uses), retrieval of category definitions or examples (rung two) is justified. If accuracy remains systematically wrong on the same confusable pairs after prompt and few-shot work, and volume is high enough that a small tuned classifier would cut cost, fine-tuning (rung four) is justified. Tools and agents are not: nothing needs to be read from a live system and the path is fixed.

**E2.** Required justification: a named decision the agent would make that cannot be enumerated as a workflow branch; an evaluation set where the current workflow measurably fails because of that decision; a projection of added latency, cost, and attack surface; and a budget and termination design. The baseline to beat: identity, permission-aware hybrid retrieval over all sources at once (so "which source to search" disappears as a decision), rerank, generation with citations, evidence gate, and a deterministic clarifying-question branch triggered when the gate finds evidence from conflicting documents or the query is below a length or specificity threshold. If that baseline passes the evaluation set, the agent is not justified; if it fails only on cases that require sequential dependent lookups, the agent's scope is exactly those cases.

**E3.** Dropped: `evidence` and `index_version` (no retrieval), `tools` (none offered), and the evidence-related gate. Retained: `request_id`, `tenant`, `principal` and groups (an invoice belongs to a tenant), `model`, `prompt`, `usage`, `latency_ms`, `output_hash`, `output_kind` (an extraction that failed validation and went to the review queue is a fallback, not an answer), `gates` (schema validation and any PII scan are gates), `eval_outcome`. New essential field: an input identity, such as a hash or document id of the invoice that was extracted from, together with the schema version of the output. Without the input identity you cannot replay or compare; without the schema version you cannot tell a model regression from a schema change. A repair-attempt count is also useful for cost analysis.

**E4.** Filtering before ranking means the candidate set never contains a document the caller may not see, so no downstream component can be influenced by it. A post-ranking filter admits restricted documents into the candidate set, where they can leak in several ways even if removed before generation: a reranker trained to use cross-document context can shift scores; a query-expansion or multi-query step may generate follow-up queries from restricted content; a "related documents" or "did you mean" feature may surface titles; result counts and latency can differ in ways that reveal the document's existence; and a bug in the filter stage turns into a leak rather than a search miss. One concrete leak: the pipeline returns "I found 3 documents but you may not see 2 of them" or logs their titles into a trace the user can later request.

## Practical exercises

**P1.** Expected implementation: add a `StageLatency` dataclass (`name: str`, `ms: float`) and a `stages: list[StageLatency]` field on `RequestLineage`; add `dominant_stage() -> str | None` returning the stage with the largest `ms`, or `None` if no stages were recorded; optionally extend `unanswered_questions` to report "per-stage latency" when `stages` is empty. Acceptance: a test where retrieval is 1,400 ms, rerank 300 ms, model 500 ms, gates 40 ms asserts `dominant_stage() == "retrieval"`; a test asserts the sum of stages does not exceed `latency_ms` (or flags it as a violation); the round-trip test still passes with the new field serialized.

**P2.** Expected implementation: `completeness_report(records: list[RequestLineage]) -> dict[str, float]` that calls `unanswered_questions()` on each record, counts occurrences per question string, and divides by `len(records)`; questions never missing appear with 0.0; an empty input returns an empty dict or raises, documented either way. Acceptance: with four records of which one lacks gates and two lack usage, the report shows 0.25 for "which policy gates ran" and 0.5 for "how many tokens it consumed" and 0.0 for the others.

**P3.** Expected implementation: in `consistency_violations`, for each `ToolEvent` with `outcome == "pending_approval"`, look for a `PolicyGate` whose name identifies the approval gate for that tool (for example `f"approval:{tool.name}"` or a gate carrying the tool name in its reason) and report a violation if its decision is `allow`. Also report a violation if a `pending_approval` tool has no approval gate recorded at all. Acceptance: the failing test is written first with `ToolEvent("send_reply", offered=True, called=True, outcome="pending_approval")` and `PolicyGate("approval:send_reply", "allow")`, asserts a violation naming `send_reply`, fails on the current code, then passes after the change; existing tests remain green.

**P4.** Expected diagram: a `flowchart TD` with the ticket text entering a context layer that holds only "render classification prompt vN", a model layer with the gateway and model, an action layer marked as absent or degenerate (no tools offered), a control layer marked single pass, and an operations layer with schema validation gate, trace, and eval. The trust boundary sits around the model: ticket text is untrusted input (it may contain injected instructions), and the only thing crossing back is a category constrained to twelve values by schema validation before deterministic routing code uses it. A good answer marks the ticket text as `subgraph Untrusted`.

## Debugging exercises

**D1.** Root cause: the evidence gate's condition is wrong or vacuous. With `evidence = []` it should have decided `deny` or `escalate`; it decided `allow`, most likely because the check is "all cited chunks are in the context" and a model output with zero citations passes vacuously, or because the relevance threshold is compared against a default score when no chunks exist. The layer is operations (gate logic), not model or context; the model did what an ungated model does. The revealing trace fields are the pair `evidence = []` with `evidence_gate: allow`; a consistency check "evidence gate may not allow when evidence is empty" would have flagged it at request time. Fix the gate to require at least one chunk above threshold and at least one citation, and add that check to `consistency_violations`.

**D2.** Most likely cause: a silent provider-side model change behind an unchanged model name (or a change in a provider default such as sampling or a safety filter). Everything you version is constant, and the one thing you do not control is the only remaining variable. The lineage design allowed it to go undetected because `model.version` is null: the record names the model but not the snapshot, so the change is invisible in traces. Two changes: (1) record the provider's returned model identifier or snapshot tag per response where the API exposes one, and where it does not, pin to a dated model alias and record it; (2) run the offline evaluation set on a schedule independent of deploys (daily against production configuration), with an alert on pass-rate drops, so a drift with no deploy is caught within a day rather than a week. Confirming the diagnosis: replay the failing cases through the fallback provider or a pinned snapshot and compare.

**D3.** Hypotheses consistent with the facts: (1) the filter is correct but the index metadata is wrong, so the document carries `groups: ["retail"]` in the source but was indexed with `all` or with no groups, and the filter admitted it; the trace shows the groups from the source document record, not from the index. (2) The filter is correct and applied, but on a different path: a cache hit returned a result computed for a `retail` user with the same normalized query, bypassing retrieval entirely. (3) The filter is applied to the primary retrieval but not to a secondary source, such as query expansion, a "related chunks" step, or a parent-document fetch that pulls siblings of an allowed chunk without re-checking their groups. The single additional trace field that distinguishes them: the retrieval-stage provenance per evidence item, for example `retrieved_via` with values like `primary`, `cache`, `parent_expand`, together with the groups as read from the index at retrieval time. A cache provenance confirms (2), a non-primary provenance confirms (3), and primary provenance with index-time groups differing from source groups confirms (1).
