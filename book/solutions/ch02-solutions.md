# Chapter 2 — Solutions

## Knowledge questions

**K1.** Any three of the following, each tied to its mechanism. (1) Cost and TTFT: every token in the handbook is processed at prefill on every request, and attention cost grows with the square of the prompt length, so the per-request bill and the time to first token both rise, the latter faster than linearly. (2) Serving memory: every token in context occupies KV cache for the whole request (2 × layers × kv_heads × head_dim × tokens × bytes), so a 1M-token context per user bounds concurrency to a handful of sessions per accelerator, and a hosted provider's rate limits reflect the same arithmetic. (3) Attention dilution and lost-in-the-middle: recall of a fact depends on its position and on how many distractors compete; a handbook puts most facts in the middle among thousands of irrelevant passages. (4) Trust: attention cannot distinguish instructions from data, so the entire handbook becomes an instruction channel. (5) Evidence: the advertised size is an input limit, not a measured recall at that length on this workload. A retrieval stage that selects a few relevant sections addresses all five.

**K2.** BPE merges are learned by frequency on the training corpus. Text that was abundant in the corpus (English, common code) accumulates long merges and tokenizes into few pieces; text that was rare (Cyrillic, Azerbaijani diacritics and suffixes) has few merges and falls back toward short pieces or raw bytes. Different vocabularies were trained on different corpora with different sizes, so the penalty differs per vocabulary: the newer one in the experiment charges 42 tokens for the Russian sentence, the older one 80. Before committing to a cost model, the team must (a) identify the exact tokenizer of the model they will ship on, (b) measure token counts on a representative sample of real traffic per language and content type, not on English test strings, (c) express the budget and the price per request per language from those measurements, and (d) re-measure when the model changes.

**K3.** Total time is 3.8 s + 300 × 0.025 s = 11.3 s, so decode is most of the elapsed time, but the user's wait before seeing anything is the 3.8 s TTFT, which is driven by the 40k-token prompt (prefill, roughly quadratic) plus queueing. Change the prompt first: retrieve or compress to a few thousand relevant tokens, which also cuts cost. Streaming hides the 7.5 s of decode behind visible output but does nothing about the 3.8 s before the first token, which already breaks Northwind's p95 TTFT target of 2 s. A `max_tokens` cap is the separate lever for the decode phase.

**K4.** Temperature divides the logits before softmax. It rescales the distribution without changing the ranking: below 1 the mass concentrates on the top candidates, above 1 it spreads toward the tail, and the entropy rises or falls accordingly. Top-p keeps the smallest set of top tokens whose cumulative probability reaches p and renormalizes, so it deletes the tail outright and adapts the surviving set to the model's confidence. At temperature 2 alone, individually absurd tokens each keep around one percent of the mass; over a few hundred steps one of them will almost surely be drawn, so the output derails. Top-p 0.9 removes those tokens entirely while leaving the plausible candidates, now flattened by the temperature, in proportion. The combination gives diversity among reasonable continuations without the tail; temperature alone gives diversity including the tail.

**K5.** Preference tuning. Pretraining gives no particular reason to accept a premise, and instruction tuning teaches format and task-following. Preference tuning optimizes the model toward answers that raters prefer, and raters (human or model) tend to prefer answers that agree with them, take the request at face value, and sound confident. The model therefore learns to treat the user's framing as given, which is sycophancy: it answers the question that was asked, on the user's false premise, instead of correcting it. Changes outside the model, any two of: (1) ground the answer in retrieved policy text and instruct the model to answer from the evidence and to state when the evidence contradicts the question, so the true carry-over rule is in context and competes with the premise; (2) add an output check that compares claims in the answer (or the accepted premise) against the retrieved evidence and routes contradictions to a correction or abstention path (Chapter 13); (3) add leading-question and false-premise cases to the evaluation set so the rate of premise acceptance is measured on every prompt or model change (Chapter 24); (4) phrase the system contract neutrally rather than with "always help the user do what they ask," which reinforces the learned tendency. Rewording the question is not a fix, because the user controls it.

**K6.** `KV bytes = 2 × layers × kv_heads × head_dim × tokens × bytes_per_element`, per sequence; multiply by concurrency for the total. Fixed by the model: layers, kv_heads, head_dim, and (within what the engine supports) bytes_per_element. Fixed by the request: tokens, which is prompt plus output so far, and across requests, concurrency. GQA reduces kv_heads by sharing one key/value head across a group of query heads, so the cache shrinks by the sharing factor and more sequences fit in the same memory. An 8-bit cache format halves bytes_per_element, which halves the cache again, at some quality cost that must be evaluated on long-context tasks.

## Engineering questions

**E1.** Candidate changes: (1) compact the schema: strip indentation and whitespace, shorten descriptions to the minimum that still steers the model, remove redundant `title` and example fields, and collapse repeated sub-objects into `$ref` definitions if the provider's constrained decoder accepts them; (2) when the provider enforces the schema server-side, stop also describing it in the prompt text, and measure whether the native mode bills the schema as input tokens (providers differ), or use provider prompt caching so the fixed schema prefix is billed at the cached rate (Chapter 5); (3) split the schema: a small routing call decides which of several narrow schemas applies, and only that one is sent. Measurement: record `usage.input_tokens` per request before and after from the provider's usage field, not an estimate, and compute the delta on a replay of a week of real tickets. Quality: run the existing extraction evaluation set (field-level precision and recall against labeled tickets) on both configurations with identical sampling settings and at least a few hundred cases, and require no statistically meaningful drop on any field. Ship behind a flag and compare the two arms on production traffic for a day before switching fully.

**E2.** Replace string equality with layered contract assertions. (1) Structural: the output parses and validates against the pydantic schema; catches truncation, malformed JSON, missing fields. (2) Field-level: each extracted field equals the labeled value after normalization (dates to ISO, amounts to Decimal, strings trimmed and case-folded); catches wrong values while ignoring formatting variance. (3) Set-valued or tolerant assertions where several answers are acceptable: category in an allowed set, free-text summary passes a rubric check or a judge with a fixed prompt (Chapter 24); catches semantic drift without demanding one wording. (4) Repeat each case N times at the deployed settings and require that structural and field-level assertions pass every time, which turns nondeterminism into a measured flake rate instead of a surprise. (5) Pin the model identifier and sampling configuration in the test fixture and record them with every result, so a provider-side model change shows up as a labeled regression rather than as random failures. The string-equality assertion is kept only against the response cache, where bit-exact repeats are expected because the model is skipped.

**E3.** Per token: A: 2 × 40 × 32 × 128 × 2 = 655,360 bytes (640 KiB); B: 2 × 48 × 8 × 128 × 2 = 196,608 bytes (192 KiB). At 24,000 tokens: A ≈ 14.65 GiB per sequence, B ≈ 4.39 GiB. Eight concurrent sessions: A ≈ 117 GiB, B ≈ 35 GiB. Only B fits in 60 GiB; A would fit about four sessions at that context length, or needs an 8-bit cache (≈ 59 GiB, borderline) or shorter contexts. Before deciding you also need: weight memory for each model at the serving precision (it comes out of the same device memory before any KV budget exists); measured quality on your own evaluation set at your context lengths, because "similar quality" is a benchmark claim; TPOT and TTFT under load, since B's extra layers cost per-step compute and memory traffic; engine support for the cache format and for GQA kernels; and license and operational constraints.

**E4.** Mechanism: a reasoning model decodes a stretch of thinking tokens before the visible answer; each is a sequential decode step, occupies KV cache, and is usually billed as output. Predictions by workload. Ticket triage: a short prompt and a one-word label; thinking adds hundreds to thousands of decode steps to an answer that needed a handful, so time to the visible answer rises from well under a second to seconds, cost per request rises by an order of magnitude, and accuracy barely moves because classification is not multi-step. Policy questions: the prompt is long, so TTFT was already prefill-dominated; thinking adds decode time on top, cost rises several times, and quality gains are small because the answer is a lookup in retrieved evidence; KV occupancy per request grows with prompt plus thinking tokens and is held longer, so fewer requests fit at once on a self-hosted engine (and provider rate limits on output tokens are hit sooner). Invoice reconciliation: the one workload with genuine multi-step structure, so this is where quality can improve, but arithmetic should still go to a calculator tool. Across all three, cost per request becomes highly variable, because thinking length varies by request, which makes budgets and per-tenant forecasts harder. Under an unchanged `max_tokens` sized for visible answers, thinking consumes the budget and the `length` finish rate rises, most visibly on reconciliation and on structured outputs, where truncation means unparseable JSON. Test first: the `length` rate and output-token distribution on a replay of a few hundred real requests per workload at the proposed effort, because it is cheap, it breaks correctness immediately if wrong, and the same replay yields measured time-to-visible-answer and cost per request; then compare quality per workload against the current model on the evaluation set. The expected conclusion is to enable high effort only for the reconciliation route, which is what Chapter 7's router does.

## Practical exercises

**P1.** Expected implementation: a `--file PATH` argument; a `split_sections(markdown) -> list[tuple[str, str]]` that splits on lines matching `^#{1,6}\s` and keeps the preamble as its own section; per-section `count_tokens` with the same `TokenCount` provenance; a table with section title, tokens, and share of the total; a final row for the whole document. Acceptance: the test builds a synthetic document of three headed sections, asserts the section list has the expected titles in order, asserts the sum of per-section counts equals the count of the whole document under the heuristic (which is additive) and is within a small tolerance under the real tokenizer (BPE is not strictly additive at boundaries, so assert `abs(sum - whole) <= number_of_sections`), and runs offline by passing an invalid encoding name to force the heuristic path. The script must still print the original sample table when `--file` is absent.

**P2.** Expected implementation: `repetition_penalty(logits, generated_ids, penalty)` returns a copy of the logits where, for each index in `generated_ids`, a positive logit is divided by `penalty` and a negative logit is multiplied by `penalty` (penalty > 1 reduces the chance of repeating; penalty == 1 is the identity). `sample` gains an optional `generated_ids` and `repetition_penalty` pair applied before temperature. Tests: identity at penalty 1; probability of every generated token strictly decreases and of non-generated tokens increases after softmax for penalty 1.5; the function does not mutate its input; indices out of range raise. Demo: a toy vocabulary for a code line such as `total = total + item` where `total` legitimately appears twice; show that after the first `total` is generated, a penalty of 1.5 to 2.0 pushes the second occurrence below an alternative identifier, producing wrong code. The written conclusion is that stop sequences and length caps are safer first responses to loops in code generation.

**P3.** Expected implementation: `build_context(paragraphs, fact, position)` that returns a list of `Message` objects (system contract, a long user message of filler paragraphs with the fact inserted at the given fractional position, and the question); a `run_sweep(client, positions) -> list[SweepResult]` recording position, context tokens via `count_tokens`, and whether the answer contained the expected value; and a Markdown table renderer. With `FakeLLM(handler=...)` the handler can be scripted to answer correctly only when the fact lies within the first or last 20 percent of the user message, which lets the tests exercise the whole harness and produce a visibly U-shaped table. Acceptance: tests assert the fact is present exactly once at the requested position, that token counts grow monotonically with the number of filler paragraphs, that the result table has one row per position, and that swapping the fake for any `LLMClient` requires no code change. The README note states that the real curve must be measured per model and context length.

**P4.** Expected implementation: `--sweep-tokens 4000,16000,64000,128000` (comma-separated) prints, for each length, per-sequence cache, bytes per token (constant), and maximum concurrent sequences under `--memory-gb`; without a budget it prints only the per-sequence sizes. Acceptance: test that per-sequence bytes are strictly increasing with tokens, that maximum concurrency is non-increasing, that the 128k row equals eight times the 16k row, and that the CLI exits non-zero with a clear message when the list contains a non-integer or a negative value.

## Debugging exercises

**D1.** Root cause: the new model tokenizes the same JSON output into more tokens than the old one (a different vocabulary, or a tendency to emit more verbose output such as extra whitespace, longer string values, or added fields), so the same `max_tokens = 400` now truncates the tail of the object. The telemetry confirms it: every failure has `finish_reason = "length"`, the inputs did not change, and the output token count on failing requests sits exactly at the cap. Fixes to consider: raise `max_tokens` to the measured p99 output length of the new model plus margin, and treat `length` as a failure that triggers a repair or retry rather than a parse attempt; or reduce output size by compacting the schema (no indentation, shorter keys, fewer optional fields) and by using constrained decoding so no prose surrounds the object. Either way, add a regression test that asserts a natural stop on the longest realistic ticket, and re-run the token-budget test on every model change.

**D2.** Diagnosis path: the client-side check uses `chars / 4`, which is calibrated for English; Georgian script costs several times more tokens per character with most vocabularies, so a conversation that passes the character check can exceed the real token limit by a factor of two or more. Telemetry: compare `usage.input_tokens` from the provider (exact) against the client's estimate per request and group by detected language; the Georgian group shows a tokens-per-character ratio far above 0.25 while the English group sits near it. Requests that failed show the exact count above the limit while the estimate was below it. The counter provenance field, if the server uses the Chapter 2 pattern, will read `heuristic` on the failing path. Fix: count with the model's real tokenizer (or the provider's count endpoint) in the context builder, enforce the budget on the exact count, and add a language-stratified budget test. The deeper lesson is that the heuristic should have been labeled and alerted on, not trusted silently.

**D3.** Saturated resource: KV-cache memory on the accelerator, not compute. Long pasted documents multiply tokens per session; at 128 KiB per token for a mid-sized model (the chapter's illustrative configuration), a 50k-token session holds about 6 GiB of cache, so a few dozen such sessions exhaust the cache that comfortably held 40 short chats. New requests wait for cache blocks to free up, which shows as queueing with modest GPU utilization, because decode is memory-bound and the engine is now admission-limited. Confirmation: the engine's KV-cache utilization metric near 100%, number of waiting versus running sequences rising together, preemption or swap counters incrementing, and the arithmetic `free_memory / (bytes_per_token × p95_context_tokens)` matching the observed concurrency cliff. Mitigations with trade-offs: (1) cap context per request and route long documents through retrieval or summarization before the model, which lowers memory and TTFT at the cost of a pipeline and some recall; (2) switch to an 8-bit KV cache or a model with fewer key/value heads, which doubles or quadruples capacity at a small quality cost that must be evaluated on long-context tasks; (3) add admission control and a separate queue or pool for long-context requests so short chats keep their latency, at the cost of longer waits for the heavy requests; (4) add hardware, which is the most expensive and does not fix the underlying unbounded context policy.
