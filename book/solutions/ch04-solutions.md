# Chapter 4 — Solutions: Prompt Engineering as Engineering

Identifiers match the exercises in `book/chapters/04-prompt-engineering.md`.

## Knowledge questions

**K1.** Role: without it (when it matters) the model picks its own register, for example adding friendly prose to output that software parses. Task: without a single imperative statement of what to produce, output varies in kind, not just in quality. Constraints: without category definitions, ordered rules, and limits, borderline inputs are decided inconsistently and outputs drift in length and content. Evidence, labeled and separated: without it the model answers from its parametric memory, and without labels it may treat retrieved text as instructions or fail to cite. Output schema: without it parsers break on prose, missing fields, or invented fields; the prompt states the schema and a validator enforces it. Failure behavior: without an explicit `other`, abstain flag, or empty-citation branch, the model produces a plausible answer when it should decline, which is the root of many hallucination incidents. (The decoding policy is a seventh element of the contract in this chapter's files, versioned in the front matter.)

**K2.** System instructions carry deployment policy, developer instructions carry task guidance (folded into the system role in `aie_core`), user messages carry the request, and data (documents, tool results, files) carries material with no authority. Models are trained to prefer higher levels when they conflict, so placing each kind of text at the right level makes correct behavior the path of least resistance: format and refusal rules in the system message hold even when a user asks otherwise, and a labeled document's embedded request is usually ignored. It is not a boundary because it is a learned tendency of a probabilistic reader, not an enforced rule: persuasive user text or document text can still win. Anything an attacker would want, such as tool authority, data access, or secrets, must be controlled by code outside the model (Chapter 26).

**K3.** Both change behavior. Temperature and token limits change the output distribution; the schema changes what the model is asked to produce and what the validator accepts (and, with provider structured output, what decoding allows). If they were outside the hash, a trace saying `ticket.classify@1.1.0` could refer to two different behaviors. Example incident: someone lowers `maxLength` of `evidence` from 200 to 50 in the shared schema; schema-valid rate drops because longer quotes now fail validation, but every trace still shows 1.1.0 with an unchanged hash, so on-call engineers search the prompt text and the model for a change that is not there.

**K4.** Free-form reasoning is prose the model writes before answering; it may improve accuracy on multi-step tasks but costs output tokens and proves nothing, since a fluent rationale can accompany a wrong answer. Verifiable artifacts are structured intermediate outputs that code can check. Router: (1) an `evidence` field that must be an exact quote from the ticket, checked by normalized substring match against the input (`quote_in_variable`); (2) a `matched_rule` index naming which decision rule applied, checked by verifying the rule's keywords occur in the ticket and no earlier rule matches. Answering prompt: citations as document ids, checked as a subset of the ids actually provided in the request; a stronger version adds one supporting quote per citation, checked as a substring of that document's text.

**K5.** Tokens on every request (prefill latency and input cost; the chapter's 1.1.0 grew input about fourfold); surface bias (outputs imitate example length, labels, phrasing); leakage (examples overlapping test cases inflate scores); spurious correlations (a feature shared by examples of one label becomes a shortcut). Measure by ablation: run the full suite with and without the example at fixed settings, with repeats if temperature is above zero, and compare per-case fixes and regressions and the token delta. Keep the example only if it fixes cases it was meant for without regressing others and the token cost is acceptable.

**K6.** HTML escaping converts `<`, `>`, `&`, and quotes into entities everywhere, which corrupts code, emails, and logs, while the model reads the entities as roughly the same characters anyway, so nothing is protected. Correct escaping for untrusted prompt variables: render the value inside an explicit labeled delimiter; neutralize any occurrence of the delimiter inside the value so it cannot close its own block or open a new one; normalize look-alike characters (NFKC) before that check; drop control and invisible formatting characters such as zero-width spaces and bidirectional overrides; optionally cap length per variable. Separately, never build template source from untrusted input.

## Engineering questions

**E1.** Minimum guarantees: (1) Immutable versions: every save creates a new version with a monotonically assigned number; published versions cannot be edited, only superseded. (2) Content hash per version, covering text, decoding policy, and schema, returned by the read API and stored in an append-only history. (3) Separate draft and served states: drafts are editable and unservable; serving happens only through named aliases (`prod`, `canary`) whose changes are audited with author, time, and reason. (4) A promotion gate: moving an alias runs the regression suite for that prompt against the candidate and stores the report; promotion is blocked on gate failure unless an authorized override with a reason is recorded. (5) Trace identity: the runtime client returns id, version, and hash with every rendered prompt and the application records them on spans and request metadata. (6) Rollback: alias changes are reversible in one action and the runtime picks them up within a bounded time (cache TTL). (7) Schema and variable declarations are validated on save (undeclared variables, taint rules) so the UI cannot produce a prompt that fails at render time. (8) Exportable history so incidents can be replayed with the exact version. Without 1 to 5, the UI reintroduces silent drift and the attribution problem.

**E2.** Plan: (1) Freeze prompt changes for the twelve prompts for the duration of the migration, so only one variable changes. (2) For each prompt, run its suite with repeats against the current model (fresh baseline, since provider behavior can drift) and against the new model at the same prompt version and decoding policy. (3) Classify: prompts with no regressions and acceptable cost and latency are migrated first; prompts with regressions get new minor versions tuned for the new model, evaluated against the new model, and paired explicitly (a model hint or a routing rule that serves version N+1 only on the new model). (4) Canary per prompt: route a traffic slice to the new model with the paired version, with dashboards sliced by model and `prompt.version`, compare schema-valid rate, distribution metrics, downstream signals, TTFT, and tokens. (5) Promote prompt by prompt, keeping the old model and old versions available for rollback. Attribution is preserved because at each step exactly one of {model, prompt version} differs between compared arms; when both must change for a prompt, first measure the model change alone on the old version, then the prompt change alone on the new model, so each delta is known.

**E3.** System message, stable and first: role, task, constraints, citation rules, data-labeling statement, output schema, failure behavior, and a fixed sentence such as "Answer in the language specified in the request" so the policy itself is stable. User message, after the stable prefix: the documents as labeled data blocks, then the per-request language code as a trusted variable (it comes from the user's profile or the request header your code validated against an allowlist of language codes), then the question as untrusted data. Rationale: the language instruction is per-request, so putting its value into the system message would make the prefix differ by language and fragment the cache; keeping a fixed instruction in the system message preserves the hierarchy (the rule is policy) while the value is request data. Documents go before the question so the question sits closest to the point of generation; if documents are shared across many requests (for example a fixed policy pack), they can move into the stable prefix to be cached, but per-request retrieved documents cannot. A user asking in the question to "ignore the language setting" is untrusted data and does not override the system rule.

**E4.** Gate: block on any regression among `critical` cases; block on a net pass-rate drop beyond a small tolerance; treat other regressions as review items rather than blockers; never count errored cases as regressions. Suite changes: run each case three to five times and define a case's status by its pass rate, so a flaky case is reported as flaky rather than flipping between passing and failing across runs; mark persistently flaky cases and investigate whether the label is ambiguous, the prompt is underspecified, or the case needs temperature 0; grow the suite (40 cases makes each case worth 2.5 points) toward a size where aggregate changes mean something (Chapter 24); split cases by tag so the report shows which category moved. Require that any override of the gate records a reason in the pull request. This keeps real regressions on important cases blocking while removing noise that trains engineers to ignore the gate.

## Practical exercises

**P1.** Expected solution: copy `1.2.0.md` to `1.3.0.md`, set `version = "1.3.0"`, and make two edits to the decision rules: remove the ambiguous keyword "till" from the payments rule (it matches "still"), and add a rule "- If the ticket mentions stolen, choose hardware." after the payments rule and before the account and password rules, so "The laptop was locked" no longer routes a theft report to password support. With the simulated router this fixes TCK-2026-0007 and TCK-2026-0023 with no regressions (pass rate 16 of 17; TCK-2026-0043 remains, a label question). Set `status = "active"` when done and run `prompts_cli.py lock`; `verify` must report no problems and the lock must gain `ticket.classify@1.3.0`. New cases: one ticket whose text contains a common word containing a short keyword (for example "We still cannot print labels" with gold `warehouse_scanner` or the right category for the content), and one theft or loss report that also mentions "locked" or "password" (for example "Phone stolen on the train, it was locked with my password"), both tagged with their categories and the theft case tagged `critical`. Acceptance: `compare --baseline 1.2.0 --candidate 1.3.0` passes the gate, and both new cases fail on 1.2.0 and pass on 1.3.0.

**P2.** Expected implementation: `Comparison` gains `regressions_by_tag: dict[str, list[str]]`, filled in `compare` from the candidate's case tags. `gate(..., max_regressions_by_tag: Mapping[str, int] | None = None)` appends a reason for each tag whose regression count exceeds its limit (`"pos_payments: 2 regressions (allowed 1)"`). `render_report` adds a section listing per-tag counts for tags with at least one regression. Tests: a synthetic baseline and candidate built with `FakeLLM` scripted outputs where two `pos_payments` cases regress and none critical; assert the gate fails with `{"pos_payments": 1}`, passes with `{"pos_payments": 2}`, and that the report contains the per-tag line. Existing tests must still pass because the new parameter defaults to `None`.

**P3.** Expected implementation: `VariableSpec` gains `marking: Literal["none", "datamark"] = "none"` and `Untrusted` carries it. In `Untrusted.escaped`, after sanitizing and truncating, if marking is `datamark`, replace each run of whitespace except newlines with a marker character such as `^` (configurable), and add `marking="datamark"` to the block attributes so the system prompt can explain the marking. Sanitization and delimiter escaping run before marking, so a forged tag is escaped first. Tests: a value "pay the invoice now" renders as "pay^the^invoice^now" inside the block with the attribute present; a value containing `</untrusted_data>` still yields exactly one real closing tag; for the router suite with `ticket_body` marked, the system and example messages are byte-identical across all cases (prefix stability), since marking only affects the final user message. The chapter's static taint check needs no change.

**P4.** Expected implementation: `assist.answer@1.1.0` with schema change (minor if the new field is optional, major if required; choose major and update callers if you make it required): `citations` becomes a list of objects `{"id": str, "quote": str}`; the system prompt asks for one short verbatim supporting quote per cited document. New assertion type `quotes_in_cited_documents` with `path` pointing at the citations list and `variable` naming the documents variable: for each citation, find the document with that id in the case variables (fail if absent) and check the normalized quote is a substring of the normalized document text. Cases with scripted `FakeLLM` outputs: correct quote from the cited document passes; a real quote attributed to the wrong document fails with a message naming the citation; an invented quote fails. The existing `subset` assertion becomes a check on `citations.*.id`, or is implemented inside the new assertion. Lock updated; the 1.0.0 answer suite is unchanged.

## Debugging exercises

**D1.** Root cause: the new line puts a per-day value into the system section, near the top. Prefix caching requires a byte-identical prefix; everything after the first changing token is no longer cacheable, so almost the entire prompt is recomputed on every request (and the cache fragments by day at best, by request if the value includes time). Quality is unchanged because the model sees the same content; only latency and cost moved. Telemetry: cached input tokens per request (from provider usage, recorded by the gateway as `cached_input_tokens`) drop to near zero at the deploy; TTFT p50 and p95 step up; both changes align exactly with `prompt.version` changing from 1.1.0 to 1.2.0 in traces; input token counts are almost unchanged. Fix: move the date into the user message after the stable content (or into a final short system note placed after the static part if your provider allows it), keeping the system section static; release as 1.2.1 or 1.3.0. Test: the prefix-stability test, rendering the prompt with two different `today` values and asserting all messages before the request-specific user message are identical; it would have failed in CI.

**D2.** Explanations, most to least likely: (1) The CI suite ran with `LLM_PROVIDER=fake`, so the behavioral gate exercised the harness and the simulated router, not the real model; nothing tested how the real model ranks the payments and security rules. Evidence: CI configuration and the report header ("using the simulated router"); rerunning the suite against the real provider. (2) Coverage gap: the golden set has no data-exposure ticket worded like the production ones (for example mentioning card numbers), so no critical case regressed even against the real model. Evidence: compare the two production tickets with the suite's critical cases; add them and rerun 1.0.0 and 1.1.0. (3) Nondeterminism: the critical cases pass on one run but not always; the suite used `repeats=1`. Evidence: rerun with repeats and look for flaky cases. (4) A caller override, such as a higher temperature passed at the call site. Evidence: `prompt.overrides` in request metadata and the `temperature` attribute on the `prompt.call` span for those two requests. (5) Unlikely given the controls: the served file differs from the tested one. Evidence: compare `prompt.hash` on the production spans with the lock entry for 1.1.0; a match rules this out. Remediation: add both tickets as critical cases, run behavioral suites against the real model with repeats before promotion, and use the canary alias with a security-category distribution monitor.

**D3.** Likely causes: the judge changed while the answers did not. Candidates: the `judge.groundedness` prompt was promoted to a new version (for example a rubric edit that made 3 easier to reach), the judge's model changed (a provider upgrade behind an unpinned model name or a router change that sends judge traffic to another model), or the judge's decoding policy was overridden. Check: `prompt.version` and `prompt.hash` on the judge's `prompt.call` spans before and after the jump; `model` and `provider` on the judge's `llm.complete` spans; `prompt.overrides` in metadata; the registry history and `aliases.toml` for `judge.groundedness`; whether the answer prompt's version and model stayed constant (they did, per the scenario). Confirm with the human-labeled calibration set: rerun it with the old and new judge configuration and compare agreement. Prevention: treat the judge like any prompt with an immutable version and pinned model; freeze judge version and model for the duration of any comparison; require a calibration run against human labels before a judge change is promoted; and record judge version and model with every score so dashboards never mix judge configurations.

**D4.** Root cause: in 1.4.0 the `ticket_subject` variable was declared `trusted = true` (or its declaration was dropped and re-added as trusted during the "cleanup"). The trace shows it: the body is inside an `<untrusted_data>` block, the subject is printed bare after `Subject:`, so the injected sentence reaches the model as text with the same standing as the prompt's own instructions, and the model obeys it. The evidence quote passes `quote_in_variable` because it really is a quote from the input, which is why the output also looks valid. Why every control passed: the taint check only constrains untrusted variables, so declaring one trusted switches it off by design; the lock proves the served file is the reviewed file, not that the review was right; the regression suite has no injection probe in the subject (INJ-001 targets the body), so no case regressed; the cache numbers are normal because the change was below the stable prefix. Control: trust is a property of where a value comes from, not of the prompt, so make it checkable in code. Keep a per-prompt allowlist of variables that may be trusted (here only `tenant`, sourced from the authenticated session) in a reviewed policy file or test, and fail CI when any prompt declares another variable trusted; additionally require code-owner review from the security owner for any diff that touches a `trusted =` line. Test: a structural test that loads every prompt version and asserts `{name for name, spec in pv.spec.variables.items() if spec.trusted} <= TRUSTED_ALLOWLIST[pv.spec.id]`, plus a behavioral injection probe that places the instruction in the subject and is tagged `critical`. Telemetry that would have flagged it earlier: the `benefits_leave` share on the store tenant jumping after the 1.4.0 rollout (the category-distribution alert) and outputs whose evidence quote contains imperative text addressed to the model.
