# Chapter 5 — Solutions: Context Engineering

Identifiers match the exercises in `book/chapters/05-context-engineering.md`.

## Knowledge questions

**K1.** Money: input tokens per request, split by section from the manifest's `used_by_section`, multiplied by the pricing table into cost per request (Chapter 30). Prefill latency: time to first token at p95, correlated with prompt tokens. KV memory: on self-hosted serving, KV-cache utilization and the concurrency it allows (Chapter 34). On a hosted API you observe it indirectly through the provider's length limits and the latency of long prompts. Attention: answer accuracy as a function of context length and evidence position, from the length and position sweeps. This one has no runtime gauge. It is measured offline and tracked as an evaluation metric.

**K2.** Pinning means "this request is wrong without this item". If a pinned item fails permission, one of two things is true. Either the caller pinned data the user may not see, which is an upstream authorization bug, or the request cannot be answered correctly for this user. Dropping the item silently would hide the bug and send a prompt the caller considers incomplete. Raising makes the bug visible where it happened and fails the request before any data reaches the model. Non-pinned items are optional by definition, so dropping them for permission is correct behavior and is recorded in the manifest.

**K3.** The notice is part of the stable system prefix. If it appeared only when untrusted items were present, requests with and without evidence would have different prefixes. That splits the prefix cache in two and changes the hash the team monitors. A constant notice costs a few dozen tokens, which are themselves cached, and it keeps the prefix byte-identical for every request on a prompt version. It is also harmless when no untrusted block is present.

**K4.** Any three of the following. Identifiers such as ticket ids, asset tags, and account numbers live in structured facts set by code from tool results or systems of record. Monetary amounts and quantities also live in structured facts, with units and provenance (`source_turn`). Commitments made to the user ("we will call back by Friday") and decisions live in facts of category `commitment` or `decision`, or in the system of record they belong to, such as the ticket. Secrets and credentials do not belong in context at all, and they stay in a secret store. Code patches, configuration, and legal clauses stay as verbatim artifacts in storage, referenced by id and rehydrated when needed. In every case the append-only turn log remains the source of truth behind the structured copy.

**K5.** A cap limits how much a section can take. A floor guarantees how much a section keeps when another section's items have higher priority. Without a history floor, enough high-scoring evidence fills the budget before any turn is considered, because turns usually have lower priority than a top retrieval hit. The Northwind example: a user asks about laptop replacement, then sends "can I get it this week?". Retrieval returns twelve long chunks with scores above 0.9. Without a floor, the two previous turns are dropped, and "it" has no referent. With a floor of a few hundred tokens, the recent turns survive, and the lowest-ranked evidence is dropped with reason `reserved_for_other_sections`.

**K6.** Any two of the following. The provider has a minimum cacheable prefix length that the stable prefix does not reach. The provider requires explicit cache markers, and the request does not set them. The cache entry expires between requests because traffic per prompt version is low. Requests are spread across regions or replicas whose caches are separate. Content the builder does not see is placed before the system message and varies, such as tool definitions rendered by the gateway in a non-deterministic order, so the provider's token prefix differs even though the builder's hash does not. The model or adapter version changed between requests, for example through a fallback in the gateway.

**K7.** First marker after the system section, including tool definitions, schemas, and the constant untrusted-data notice. It is identical for every request on this prompt version, so every request reuses it. Second marker after the conversation state at the end of the system message. State changes only on compaction or a fact change, so consecutive turns of one session reuse the prefix through the state. Third marker after the last history turn. History is append-only between compactions, so the next turn of the same session reuses everything up to that point and pays full price only for the turns added since (the previous question and its answer), the tool results, the evidence, and the request. Nothing after the history is worth marking, because evidence and the request change on every request. After a compaction, the state and history markers miss once and the system marker still hits. If the system section is below the provider's minimum cacheable length, the first marker earns nothing on its own, and the second and third still can.

## Engineering questions

**E1.** Assumptions (illustrative): a 4,000-token base consisting of system prompt and tool specs, tool results averaging 2,000 tokens with a maximum of 4,000, 200 tokens of model output per step, and 30 steps.

Policy:

- **Facts, exact and pinned.** Incident id, affected services and hosts, error signatures and codes, timestamps of the first and last error, the deploy or change ids found, and each hypothesis with its status (confirmed or ruled out), plus the evidence id for that status. These are set by code from parsed tool results where possible.
- **Step ledger, compact and verbatim.** One line per completed step: tool, key arguments, outcome, and the reference to the stored full result. About 60 tokens per step.
- **Summary, narrative.** How the investigation progressed and why the current hypothesis is preferred. Guarded as in the chapter.
- **Verbatim.** The last two tool results in full, and any result whose step returned an error, until the error is resolved.
- **Trigger.** Compact when verbatim tool output exceeds 10,000 tokens, and compact down to the last two results. Run compaction after a step completes, never in the middle of a step.

Without compaction, step k sends about 4,000 + 2,200k tokens, so 30 steps send about 30 × 4,000 + 2,200 × 465 ≈ 1.14 million input tokens. With the policy, the per-step input is bounded by roughly 4,000 + 500 facts + 800 summary + 8,000 verbatim worst case + 1,800 ledger at 30 steps ≈ 15,000 tokens, which is at most about 450,000 in total and usually far less. The per-step cost is roughly flat, not linear in k. Acceptance: a replay of recorded incident runs shows equal or better task success, and every identifier used in the final report appears in facts or in a rehydrated result.

**E2.** Both are volatile per request or per user. They go in the volatile tail: the final user message or a short "request context" block placed after the history, never in the system section. The system contract can say "the user's display name and today's date are provided with each request", which is constant text. Tests: `lint_stable_items` in CI over every prompt version's stable items, which flags dates and timestamps. A stability test builds two requests for different users on different dates and asserts identical `prefix_hash` values. The name needs its own check, because the lint has no pattern for names. Build with two different user names and assert that the stable prefix contains neither name.

**E3.** Places: the raw turn log, which is the source of truth; a fact, if the application stored it as one; the current summary, if the summarizer narrated it; earlier summaries, if summary versions are retained; trace spans that store prompt bodies; provider-side logs, under the provider's retention terms; any cross-session memory store (Chapter 21); and response caches keyed by prompts that contained it. Procedure: redact the turn in the log and keep a tombstone with the deletion request id. Call `forget(key)` on any fact holding it, and purge `fact_history` entries for that key. Rebuild the summary from the redacted log with `rebuild_summary`, because editing the summary text in place is unreliable, and run the literal guard so the number cannot reappear. Delete or redact stored prompt bodies in traces, keeping manifests, which hold no content. Invalidate response-cache entries for the session. Delete matching memory records. Confirm by running a retrieval and summary search for the number, which must return nothing. Prefix caches on the provider expire on their own and contain no state that later requests can retrieve, but document this in the deletion record.

**E4.** Raising the cap risks lost-in-the-middle failures and distraction, plus high cost and latency per question. It works only if the model's position curve is flat at that length. Retrieval over sections risks missing the clause that answers the question when the question's wording differs from the contract's, or when the answer needs two distant clauses, such as a definition and an obligation. Map-reduce summaries risk losing exactly the precise clauses that contract questions need, and they cost a full pass per document. Evaluation: a question set written by someone who knows the contract, covering single-clause lookups, multi-clause reasoning, and definition-dependent questions, with gold clause ids. Measure answer accuracy, citation correctness against the gold clauses, cost, and latency for each design. In practice, retrieval with section-aware chunking plus a definitions section pinned per document tends to win. Raising the cap can serve as a fallback for questions that fail retrieval, but only if the position sweep at that length supports it.

## Practical exercises

**P1.** Expected implementation: `compact_tool_result(item: ContextItem, fields: list[str], store: dict[str, str]) -> ContextItem`. It parses `item.content` as JSON, extracts the dotted paths (`"ticket"`, `"items.0.id"`), stores the original in `store` under a key such as the item id, and returns a new item with the trimmed JSON, the same `source_id` with a `#trimmed` suffix, the same trust (untrusted), and `metadata={"full_ref": key, **item.metadata}`. Missing paths are recorded as `null`, not skipped, so the model can see that the field was absent. Acceptance criteria: required fields have equal values before and after; the trimmed item's token count is lower for a realistic result; `store[item.metadata["full_ref"]]` equals the original content; ACL metadata is preserved, so `acl_filter` behaves identically; non-JSON content raises a clear error instead of being truncated.

**P2.** Expected implementation: `ContextBuilder(..., restate: str | None = None, restate_after_tokens: int = 4000)`. After allocation, if the estimated size exceeds the threshold, `_render` adds the restatement line inside the final user message, before `Request:`. It is not added to the system message. Its tokens must be reserved in allocation: count it as a fixed cost when the threshold could be crossed, or allocate twice. Acceptance criteria: the hash for a small build equals the hash for a large build with `restate` enabled; the line appears only above the threshold; the line sits immediately before the request; the budget test still holds with the line included; the manifest or span records `context.restated = true`.

**P3.** Expected implementation: a script under `context/experiments/attribution.py`. For each evaluation case (question, candidate items, expected answer), it builds the full prompt and records the answer from a `FakeLLM` handler. The handler answers only if a specific source id is present in the prompt, for example by mapping source ids to facts and composing an answer from the facts present. Then, for each included evidence item, it rebuilds without that item and records whether the answer changed. Output: per item, the number of cases where it was included and where its removal changed the answer. Items with zero changes across all inclusions are flagged. Acceptance criteria: on a synthetic set where one item is decisive and two are distractors, the decisive item is reported as influential and the distractors as never influential; the script uses `ContextBuilder` for every build, never manual string assembly; it runs offline.

**P4.** Expected implementation: `run_length_sweep(client, needle, distractors, lengths=(5, 10, 20, 40), position=0.5, trials=..., seed=...)`, which mirrors `run_position_sweep` but varies `n_docs` at a fixed relative position and reports accuracy and mean prompt tokens per length. The test uses a simulated reader whose accuracy decreases with the number of evidence blocks, for example `p = max(0.2, 1.0 - 0.02 * n_blocks)`, seeded by a prompt hash. Acceptance criteria: mean prompt tokens increase strictly with length; accuracy at the shortest length exceeds accuracy at the longest; results are deterministic for a fixed seed; the needle's index matches `round(position * (n - 1))` at every length.

## Debugging exercises

**D1.** Root cause: starved history. The longer chunks have high retrieval scores, so they outrank turns in the global priority order and consume the budget. The newest turn that does not fit is dropped with reason `budget`, and every older turn follows with `history_gap`. Follow-ups lose their referents, so the model treats them as new questions. Single-turn evaluations improve because they contain no history to lose. Telemetry: per-section token gauges show history collapsing and evidence growing at the retrieval deploy, and per-request manifests show `budget` drops on `turn:*` items. Smallest fix: a history floor in `BudgetPolicy`, for example `SectionLimits(floor=800)`, plus an evidence cap so longer chunks reduce the number of chunks instead of crowding everything else out. Add a multi-turn regression case to the evaluation set.

**D2.** The guard only checks that every literal in the summary appears somewhere in its sources. INC-4812 did appear in the folded turns, for example as a related ticket the user mentioned, or a typo the user later corrected. So the guard accepted a summary that attached the right literal to the wrong referent. Literal provenance is not semantic correctness. Telemetry that reveals it: the summary item and the facts item in the same manifest disagree on the ticket, and the folded turns in the log contain both ids. Fixes, from strongest to weakest: forbid identifier-shaped literals in summaries entirely, so the summary must refer to facts by key, and reject any summary that contains an identifier pattern; flag summary identifiers within a small edit distance of a fact value as probable transpositions and reject them; and keep facts rendered after the summary, with the system contract saying that facts override the summary when they conflict. Add the case to the fact-retention suite.

**D3.** Root cause: Tuesday's deploy put volatile content into the stable prefix, or made its rendering non-deterministic. Typical candidates are a timestamp or "today is" line, a request or trace id, the user's name, an experiment variant id interpolated into the system prompt, or tool definitions or examples assembled from a set or dict whose iteration order varies. The prefix hash changing on every request confirms the variation is inside the builder's system section, not in provider configuration. Look for it by diffing the system prompt template and the item construction code in the deploy, and by comparing the system messages of two consecutive requests from the trace. `shared_prefix_tokens` shows where they diverge. Prevention: in CI, run `lint_stable_items` and a test that builds two different requests and asserts equal `prefix_hash` values. In production, alert when the number of distinct prefix hashes per prompt version exceeds a small number, and alert when cached input tokens fall below a fraction of input tokens.

**D4.** Root cause: a lost update. The compaction job loaded version 12, which held turns 0 through 6, and spent several seconds in the summarizer. Meanwhile the request appended turn 7 and saved version 13. The job then saved its own version 13, built from its stale copy: a new summary plus turns 0 through 6. A plain `put` means the last writer wins, so turn 7 vanished from a log that was supposed to be append-only, and the next prompt had no record of the steps. The telemetry clue is two saves of the same session with the same version number and different contents, and a log whose length decreased between consecutive loads. Fix: make the save a compare-and-set on the version (`InMemoryStateStore.save` in this chapter, or `UPDATE ... WHERE version = :expected` in SQL). The compaction job then receives `StaleStateError`, discards its result, and compacts again at the next trigger. Request writers reload and re-apply, which is safe because `add_turn` deduplicates by `message_id`. A stronger structural fix stores turns in an insert-only table with a unique (session, index) key and keeps the summary and watermark in a separate row with its own version, so a compaction can never remove a turn even if its write is accepted. Add an alert on `StaleStateError` rates and a check that the log length never decreases between loads.
