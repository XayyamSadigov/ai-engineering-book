# Chapter 10 — Solutions

Identifiers match the Exercises section of `book/chapters/10-rag-fundamentals.md`. Code references are to `book/projects/examples/ch10/`.

## Knowledge questions

**K1.** Freshness: weights stop at a training cutoff and retraining takes days per revision; a retrieval index updates when the document does. Private knowledge: runbooks and incident reports were never in any training set; retrieval puts them in the context at request time. Citations and auditability: an answer from weights cannot say where it came from; retrieved chunks carry stable ids the answer can cite and a reviewer can open. Permissions: weights cannot be filtered per user, so anything learned can be said to anyone; retrieval filters chunks by the caller's ACL groups before the model sees them. (Cost is a fifth, relative reason: a few relevant chunks are cheaper than the whole corpus, and an index update is cheaper than retraining.)

**K2.** Offline: ingest, chunk, index. Online: query understanding, retrieve, rerank, pack, generate, validate. The minimal pipeline implements query understanding (the raw question is the query) and rerank (cosine top-k is the final order) as identity functions. Ingest, chunk, index, retrieve, pack, generate, and validate exist, several of them naively.

**K3.** Top-k returns the k highest-scoring rows regardless of their absolute score; there is no "none" outcome unless the code adds one. Cosine scores depend on the corpus, the embedding model, and query length, and are not calibrated probabilities. In the chapter's runs, the irrelevant top hit for the sabbatical question scored about 0.22, while the correct chunk for the vacation question scored about 0.16. Any fixed threshold that rejects the first also rejects the second. Thresholds can work when calibrated per model and corpus on a gold set with answerable and unanswerable questions, and even then they should be one signal among several (coverage checks, a reranker score, the generator's abstention).

**K4.** After generation, the model has already read the restricted text; redaction catches exact strings but not paraphrases, summaries, or inferences ("the band tops out around 140k"), and a prompt instruction not to reveal it is a request, not a control. Filtering after scoring but before packing does keep the text out of the prompt, but forbidden chunks still occupy top-k slots, so the caller silently receives fewer than k usable results and quality degrades for exactly the users with narrower permissions; and the filter is a separate step that any new code path can forget. Filtering before scoring makes the forbidden chunk invisible to ranking, so it can neither leak nor crowd out allowed evidence.

**K5.** For it: about 22,600 tokens fits comfortably in many context windows, so stuffing removes the whole retrieval system and its evaluation burden; and whole documents remove chunk-boundary and distractor-ranking failures, since nothing is cut and nothing is ranked. Against it as things grow: input cost and time-to-first-token scale with corpus size on every request (about 25 times the RAG input here, worse as the corpus grows, until it no longer fits at all); and permissions fragment the corpus per scope, so each group combination needs its own prompt, which breaks prefix caching and multiplies cost. Lost-in-the-middle effects also grow with prompt length.

**K6.** At 72 percent recall and 70 percent correctness, almost every question that had its evidence was answered correctly; the generator is close to its ceiling and the work is in retrieval (chunking, ranking, coverage). At 98 percent recall and 70 percent correctness, the evidence is almost always present and the generator is losing it: the contract, evidence ordering, conflict handling, or model choice is the problem. The same end-to-end number calls for opposite investments.

## Engineering questions

**E1.** Ingestion: the source system exposes a status per revision; the loader records `status` (`draft`, `approved`, `retired`), `version`, `effective_date`, and `supersedes` on the document record and copies them onto every chunk. Only one approved revision per document id is active; when a new revision is approved, the indexer writes its chunks under a new version and marks the previous version's chunks `retired` in the same idempotent job, so there is no window where both or neither are active. Retrieval: the filter `status = 'approved' AND effective_date <= today` lives inside the retrieval query alongside the ACL and tenant filters, before scoring, never in the prompt. Drafts may be indexed for an HR-only preview flow with a separate filter scope (`status IN ('draft','approved')` and `hr` in groups). Tests: a draft chunk never appears for an `all` user; approving a revision swaps results atomically; a gold question pinned to the new version passes after approval.

**E2.** Fine-tuning would teach style and common phrasing of the policies; it would not reliably encode specific figures, would not update when a policy changes without another training run, cannot be permission-filtered, and cannot cite. It would likely increase confident errors on specifics. Proposal: RAG over the policies with version metadata, citations, an abstention contract, and ACL filtering; optionally a small fine-tune later for answer format if evaluation shows a persistent behavioral problem. Evidence to settle it: a gold set of policy questions with rubric answers, including recently changed policies and restricted documents; measure correctness, faithfulness, citation validity, and leakage for the RAG system and for a fine-tuned model (and both combined), plus the cost and lead time of updating each after a policy change.

**E3.** One root span `rag.answer` with `request.id`, `user.groups`, `tenant`, `index.version`, `embedding.model`, `prompt.version`. Child spans: `retrieve` with `query`, `k`, `allowed_count` (chunks surviving the ACL filter), `hit.ids` and `hit.scores` in rank order, `zero_hits`; `rerank` (identity here) with `input.ids` and `output.ids`; `pack` with `packed.ids`, `packed.tokens`, `dropped.ids`; `generate` with `model`, `input_tokens`, `output_tokens`, `latency_ms`, `finish_reason`; `validate` with `cited.ids`, `invalid.ids`, `abstained`, `unsupported_claims`. With a gold set mapping questions to required chunk ids, "was it retrieved and where was it lost" is a join: present in `hit.ids` but missing from `output.ids` means rerank dropped it; present in `output.ids` but missing from `packed.ids` means the budget dropped it; present in `packed.ids` but uncited or contradicted means generation.

**E4.** The top cosine score is not calibrated and is relative to the corpus; it is often high for wrong-but-lexically-similar chunks (the distractor and stale-FAQ demos) and low for correct paraphrased ones. Displaying it invites users to trust a number that does not measure answer correctness. Alternative: a categorical indicator derived from deterministic checks the pipeline already has: answer abstained, any invalid citations, any unsupported numeric claims, citations span more than one document version that disagree, number of distinct cited chunks. Show "Answered from: PTO Policy v3.0" with a link, and flags such as "sources disagree" or "could not verify all figures". If a numeric score is required later, train or calibrate it against labeled outcomes on the gold set (Chapter 24) before showing it.

## Practical exercises

**P1.** Expected implementation: in `MinimalRAG.answer`, after `self.index.search(...)`, if `hits` is empty return `RagAnswer(text="INSUFFICIENT_EVIDENCE", evidence=[], abstained=True)` with a `reason="zero_hits"` field added to `RagAnswer` (default `None`), and do not call the model. Optionally make `min_hits` a constructor parameter and abstain when `len(hits) < min_hits`. Acceptance: a test with `FakeLLM(responses=[])` (which raises if called) and an identity with `user_groups={"nobody"}` gets an abstention with `reason == "zero_hits"` and `llm.requests == []`; the existing tests still pass; a test with matching groups still calls the model exactly once.

**P2.** Expected implementation: `pack_evidence` renders `<evidence id="..." title="..." version="3.0" updated="2026-01-15">`. The system prompt gains a rule such as: "If evidence blocks disagree, prefer the one with the later `updated` date, state that an older source disagrees, and cite both." Test: two synthetic docs via `failure_modes.make_doc`, one `version="1.4", updated="2025-06-10"` saying 5 days, one `version="3.0", updated="2026-01-15"` saying 10 days; a `FakeLLM(handler=...)` that parses the `updated` attributes and answers from the newer block. Assertions: both version strings appear in `llm.last_request.messages[-1].text`, the answer contains "10" and cites the newer chunk id, and `validate_citations` reports no invalid ids. A second assertion on the real corpus that the PTO question's prompt now contains `version="3.0"` and `version="1.4"` is a useful regression check.

**P3.** Expected implementation: load with `shared_data.load_retrieval_gold()`; for each question call `rag.index.search(q.question, k, set(q.user_groups))`; a question passes if any `required_doc_ids` document appears in the hits, except questions tagged `forbidden-doc`, which pass only if none of the required documents appears (the required document is the one the user must not see). Report overall and per-tag pass rates. Reference numbers with the offline content-word embedder at 800-character chunks on the 40-question set: answerable questions hit about 30/37 at k=1, 36/37 at k=4, 37/37 at k=10; all three `forbidden-doc` questions correctly return no forbidden document at every k when groups are passed (and fail if the evaluator calls `search` without groups). Paraphrase questions are the weakest slice at small k (about 1/4 at k=1). Acceptance: deterministic output, per-tag table, a test on a tiny synthetic gold file. Note in the write-up that document-level hit rate on lexically similar questions flatters a lexical retriever; fact-level and paraphrase slices are what Chapters 12 and 14 improve.

**P4.** Expected implementation: parse lines, track the heading stack (`#`, `##`, `###`), start a new section at each heading, and emit one chunk per section with text prefixed by the heading path (for example `PTO Policy > 3. Carryover`); sections longer than the limit are split with `chunk_fixed`-style windows, each carrying the same prefix; chunk ids stay `<doc_id>#c<n>`. Acceptance: no chunk crosses a heading boundary; every chunk is within the size limit; concatenating section bodies reproduces the document text; on the P3 evaluator the heading-aware chunker is at least as good as `chunk_fixed` at k=4 and fixes the boundary demo's class of failure. Report the per-tag comparison and chunk counts, and note that table rows inside a section are still split by the fallback window (Chapter 11 handles tables as units).

## Debugging exercises

**D1.** Root cause: the chunk id format changed in the chunker, but two things still assume the old one. The system prompt's citation example is hardcoded as `[hr-pto-policy#c3]`, so the model often copies the example's shape and cites `doc#cN` ids that are not among the `doc::N` ids it was shown, which `validate_citations` correctly flags as invalid. And `CITATION_RE` only matches `#c\d+`, so correctly formatted new citations are not parsed at all, which shows up as answers with zero citations. Retrieval and answer text are unaffected, which is why those metrics are flat. Telemetry: the `validate` span shows `invalid.ids` in the old format while `packed.ids` are in the new one; the share of answers with no parsed citations rises at the same deploy. The id format should have a single source of truth used by the chunker, the regex, and the prompt example, and a test asserting that an id produced by the chunker matches `CITATION_RE` and that the prompt's example id is generated from the same function.

**D2.** Walking the tree: the query is interpreted fine (FAQ chunks retrieved with normal scores); the gold evidence is not in the index (the VPN chunks are gone); so the failure is ingestion, before retrieval. Most likely cause: the edited runbook failed to parse or was dropped on re-ingestion, and the indexer deleted the old version's chunks before (or without) successfully writing the new ones. A common concrete trigger is a front matter change (for example an unquoted value or a removed `acl_groups` field) that makes the loader reject the file. Confirming telemetry: ingestion job logs for `it-vpn-access-runbook` show a parse or validation error at the edit time; the per-document chunk count for that id went from 7 to 0; the index's source-hash-to-indexed-hash comparison flags the document as missing. Fix: write new chunks before retiring old ones in one idempotent job, alert on document disappearance and chunk-count drops, and quarantine unparseable files while keeping the last good version live.

**D3.** The ACL check passed because group membership is the only filter: the user is in `it-oncall`, the incident report allows `it-oncall`, so the group intersection is non-empty. Tenant isolation is missing: the retrieval span has no tenant attribute, so the filter `tenant IN (user_tenant, 'shared')` was never applied, and a `retail`-tenant document reached a `logistics` user. Groups and tenants are orthogonal axes; both must be enforced. The fix is a mandatory tenant argument in the retrieval interface (derived from the authenticated identity), the tenant recorded on every retrieval span, and `Doc.visible_to(user_groups, tenant)` semantics applied inside retrieval. The test that catches it: index one `retail` and one `logistics` incident report with identical ACLs, query as a `logistics` user in `it-oncall`, and assert that no `retail` chunk is ever returned; plus a trace assertion that every retrieval span carries `tenant`.
