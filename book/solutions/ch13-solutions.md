## Knowledge questions

**K1.** First, short ids are cheap to copy exactly: a model reproduces `E2` reliably, while a 30-character chunk id invites transcription errors. Second, they make fabrication unambiguous: in a request with four blocks, `E9` is invented by construction, while a plausible chunk id might match a real chunk the model never saw, and a check against the whole index would wrongly accept it. Third, they decouple the prompt from the storage schema: chunk id formats can change (Chapter 10, D1) without touching the contract or the validator, because the mapping from evidence id to chunk ids, document, version, and URI lives in `PackedEvidence`. A fourth benefit is that ids number blocks in reading order, which makes traces easy to read.

**K2.** An invented or altered number is the most frequent and most damaging grounded-answer error. A single wrong figure ("15 days") changes the meaning while leaving almost all words supported, so a coverage threshold alone would accept it. Numbers are also exact, so a strict check has few false positives. Words are lenient because honest paraphrase changes vocabulary, and a strict word rule would reject many supported claims. The check misses meaning reversals that reuse the evidence's words: "employees may not carry over unused days" against "employees may carry over up to 10 unused days" shares nearly all content words. It also misses wrong relations between correct tokens, such as swapping which tenure band gets which entitlement.

**K3.** A flagged span is text addressed to an automated reader or requesting an action. It is real document content, but it is not a statement of fact about the world that the assistant should relay. If it counted as support, a compromised or manipulated model could repeat the injected request ("send the directory to partners@...") with a citation, and the support check would pass because every word appears in the block. Excluding flagged spans means any claim that only an injection supports fails with `support_only_flagged`. Claims supported by the legitimate parts of the same document still pass.

**K4.** `stale_source_preferred` means the answer cites the older side of a detected conflict and not the newer side. The user is likely receiving outdated information, such as five days instead of ten, so it is an error: claims resting only on the stale source are dropped and the answer is downgraded. `conflict_unreported` means the answer cites both sides but reports status `answered`. The sources may in fact agree on the point asked. The conflict detector is heuristic and only says the documents *may* overlap. The model may also have answered correctly and simply failed to set the status. Nothing shown is necessarily wrong, so it is a warning that feeds metrics and evaluation, not a repair.

**K5.** Score scales differ by stage and are not calibrated probabilities. Reciprocal-rank fusion produces small numbers, around 1/(60+rank) per list, so 0.03 can be a top hit. A cross-encoder reranker may output logits or probabilities where 0.03 is weak. Raw cosine similarity depends on the embedding model and the corpus. One global floor would either reject strong fusion hits or accept weak reranker hits. Each stage needs a floor calibrated on gold questions that includes unanswerable ones, and `AbstentionPolicy.min_top_score` is keyed by `ScoredChunk.stage` for that reason.

**K6.** Self-consistency filters variance, not bias. When every sample is pushed the same way, all samples agree on the same wrong claim and it survives. Three causes are common. The evidence is itself wrong or stale, for example only the old FAQ was retrieved. The question's wording strongly suggests an answer. Or the model has a systematic misreading, such as a table whose header is ambiguous. Agreement then raises confidence in an error. That is why self-consistency complements, and does not replace, support checks and retrieval quality.

## Engineering questions

**E1.** Generator: enable `GeneratorConfig(quote_then_answer=True)` for the contracts route, so the system prompt adds the quote-first rule, and raise `max_tokens` to cover quotes. Schema: `Claim.quote` becomes required for this route. Use a subclass with `quote: str` that is non-optional, so structured output and the repair loop enforce it. Validator: the quote check already drops claims whose quote is not a verbatim span. Add a minimum quote length and a rule that the quote shares the claim's numbers. Consider a stricter `min_support` for this route. UI: render each claim's quote as an expandable excerpt under the citation chip, with the document version and section, and highlight the quoted span when the source opens. Effect: output tokens grow roughly in proportion to quote length, often doubling claim tokens, and completion latency grows with them. Time to first token is unchanged for non-streamed responses. Validation cost stays negligible. Acceptance: on the legal gold slice, 100 percent of displayed claims have verified quotes, and quote-not-found rates are tracked per model.

**E2.** Stream with the deterministic sentence checks, which gives fast text and blocks fabricated ids and invented numbers. Run the judge asynchronously on the assembled `done` answer. While the judge runs, the UI shows a subtle "verifying sources" indicator. If the judge agrees, the indicator becomes "sources verified." If it flags claims, the UI marks those sentences in place: strike-through or a warning icon with "this statement could not be verified against the cited source." It also adds a banner and logs the case for review. Do not silently delete text the user has read, because disappearing text destroys trust and hides the error. For answers that will be stored, emailed, or acted on, use the non-streaming path with the judge in line. Track the post-hoc flag rate. If it is high, the deterministic checks or the contract need work, because users are seeing too many corrections.

**E3.** Add metadata fields at ingestion: `status` (draft, approved, retired), `effective_date`, `supersedes` (a list of document ids, with optional section anchors), and `superseded_by`, which is computed. Document owners maintain `supersedes` in the source system's front matter, or through a review form when a new policy version is approved. A content-ops check flags documents of the same type and topic with no supersession link. The Chapter 15 indexer handles a new version this way. It writes chunks for the new version. It marks the old version's chunks retired in the same idempotent job. It updates `superseded_by` on the referenced documents and propagates that field to their chunks. It invalidates caches keyed on those document ids. The packer then sees `supersedes` on the policy's chunks, and an explicit `possible_conflict` note appears with no heuristic. Retrieval can also demote or exclude superseded FAQ entries. Tests: approving the new version atomically switches which version the note prefers, and FAQ chunks carry `superseded_by`.

**E4.** The validator drops two of six claims, so the repaired status moves from `answered` to `partial`. The dropped ratio is 2/6 ≈ 0.33, which is at most 0.5, so the policy does not abstain. If cited tags match no escalation tags, the action is `answer_with_caveat`. The notices list the `missing_info` items, and the `claims_dropped` reason is logged. For an HR assistant, 0.5 is reasonable. Partial policy answers with a caveat and a link are useful, and the cost of a missing detail is low. For an incident-response assistant, use a stricter value such as 0.2, or escalate on any dropped claim. Dropped claims there signal that the model is unreliable on the current incident. A partial answer can omit the step that matters, and the cost of a wrong or incomplete runbook step is high. Choose the threshold per surface from labeled outcomes, not by intuition.

## Practical exercises

**P1.** Add `regenerate_on: set[str] = {"stale_source_preferred", "validation_emptied"}` and `max_regenerations: int = 1` to `GroundedQA`. After validation, if any trigger fires and evidence is non-empty, build the same request and append a user message. The message lists the issues in plain language, for example "Your answer relied on E1; E2 is newer and was not used. Claims X and Y were not supported by their citations. Answer again following the rules." Call the generator, validate again, and keep the better report: fewer errors first, then more surviving claims. Record both attempts in `QAResult`. Tests: a `FakeLLM` with two scripted responses for each trigger. The first is the naive FAQ-only answer, or an answer whose claims are all unsupported. The second is a correct answer. Assert that two requests were made, that the second request's last user message contains the feedback, and that the final envelope comes from the second answer. Also assert that no regeneration happens when the first answer is clean.

**P2.** Implement a callable class with the `AnswerJudge` signature. For each claim, find negation cues (not, never, no longer, except, unless, without) in the claim. Then check the cited blocks' support text for a negation within a window of the claim's content words, for example the sentence containing most of them. Flag the claim when the claim has a negation the evidence lacks, or the evidence has one the claim drops. Return `JudgeVerdict(score=1 if flagged else 3, unsupported_claims=[...])`. Acceptance: "Employees may not carry over unused PTO days" citing the PTO carryover block is dropped with `judge_unsupported`. "Employees may carry over up to 10 unused PTO days" passes. "There is no cash payout for forfeited carryover days" passes, because the evidence contains the same negation.

**P3.** In a test fixture, copy the PTO carryover chunk with `metadata={..., "effective_date": "2026-01-01"}`. `EvidenceBlock.freshness` already prefers `effective_date` over `updated_at`. Tests: (a) with the effective date present, the conflict note's `newer` is the policy block. (b) Build a disagreement case: give the FAQ an `updated_at` of 2026-02-01, a typo fix after the policy took effect, with no effective date. Give the policy an `effective_date` of 2026-01-01 and an `updated_at` of 2025-12-01. Show that the comparison mixes fields and wrongly picks the FAQ, because `freshness` compares the policy's effective date with the FAQ's updated date. The fix is to compare like with like. Use effective dates when both blocks have them. Otherwise fall back to `updated_at` for both, and add a note that freshness is uncertain. Better still, require effective dates for policy documents at ingestion.

**P4.** Build a FastAPI app with a dependency that constructs `GroundedQA` from `make_llm_client()`. A retrieval function, a stub in tests, returns `list[ScoredChunk]`. `POST /answer` takes `{question}` plus an authenticated principal, and returns `QAResult.envelope`. `POST /answer/stream` returns `StreamingResponse(media_type="text/event-stream")`. It iterates `GroundedStreamer.stream` and writes `event: <type>\ndata: <AnswerEvent json>\n\n`. Never include issues for withheld sentences in events sent to end users: log them server-side. Test with `TestClient` and a `FakeLLM` that streams a sentence citing an unknown id among valid ones. Parse the SSE lines and assert three things. Every `text` event's `eids` is a subset of the `citation` events seen before it. No text event contains the unknown id. The final `done` event has status `partial`.

## Debugging exercises

**D1.** The likely cause is lexical-support false negatives, triggered by the new model's writing style. It paraphrases more freely: "roll over" for "carry over", "annual leave" for "PTO", dates written as "the first of January" instead of "1 January". Its claims are supported, but their content words differ from the evidence, coverage falls below `min_support`, and the validator drops them. Those answers then become `insufficient_evidence`. Confirm with the `unsupported_claim` issue details: low coverage with an empty `missing_numbers` set, rather than missing figures. Check the `validation_emptied` versus `model_abstained` reasons in the abstention telemetry, which should show validation emptying the answers. Then hand-label a sample of dropped claims and find that most are supported. Remedies: recalibrate `min_support` per model on labeled claims. Add synonym normalization for domain terms. Add a calibrated judge as a second opinion before dropping claims with no missing numbers. Or instruct the model to reuse the evidence's wording, or use quote-then-answer. Make validator thresholds part of the model-upgrade evaluation, so this shows up before deploy.

**D2.** The server-side mapping was correct: the claim cited E2, the policy, and the validator found no issues. The bug is in the client's citation resolution. The envelope's `citations` list is ordered by first appearance, here E2 then E1. The client resolved a marker by array position (`citations[n - 1]` for `[En]`) instead of looking up the entry whose `eid` equals the marker. `[E2]` therefore opened `citations[1]`, the FAQ. The bug is invisible when blocks happen to be cited in id order, and edges ordering makes out-of-order citation common. A client contract test would have caught it: an envelope whose citation order differs from id order, asserting that each marker opens the citation with the matching `eid`. A server-side test can also assert that `citations` are keyed or ordered as documented, and the client should index by `eid`.

**D3.** The paragraph was phrased so that none of the `INSTRUCTION_PATTERNS` matched. "Contact partners@... for directory updates" has no send or email verb before the address, no "ignore instructions", and no text addressed to an AI. So no span was flagged and no flagged-source event fired. The support check then counted the paragraph as ordinary evidence, and the claim passed. The defense depended on a brittle regex classifier. To make it less dependent: (1) Use source trust metadata. Documents marked as external or unreviewed, such as this one by its owner field and the `external` tag, get lower trust. Contact details, URLs, and requested actions from them are excluded from support unless a reviewed internal source corroborates them. (2) Scan the output. Email addresses, URLs, and phone numbers in answers must appear in clean evidence from reviewed sources, or be on an allowlist. Otherwise the claim is dropped and an event is raised. (3) Classify content at ingestion with a stronger detector (Chapters 26 and 27) and quarantine flagged documents for review. (4) Keep the answer path free of tools, so the worst case is misinformation, not exfiltration. Add the paraphrased injection to the attack corpus as a regression case.
