# Chapter 14 — Solutions

## Knowledge questions

**K1.** Deduplicate the chunk list into documents first: the acceptable document A is at document rank 1, an irrelevant document at rank 2, and the first required document R1 at rank 3 (its second chunk at chunk rank 4 adds no new document). The top five documents are A, X2, R1, X5, X6.

- **hit@5 = 1.0**, because R1 is in the top five documents.
- **recall@5 = 0.5**, because one of the two required documents was found.
- **precision@5 = 0.6** at chunk level: the top five chunks are A, X2, R1, R1, X5, and three of them belong to a relevant document.
- **Reciprocal rank = 1/3**, because the first required document is at document rank 3. The acceptable document at rank 1 does not count for MRR, which uses required documents.
- **nDCG@5 ≈ 0.464.** DCG = (2^1 - 1)/log2(2) + (2^2 - 1)/log2(4) = 1 + 1.5 = 2.5. The ideal list is R1, R2, A: IDCG = 3/1 + 3/log2(3) + 1/log2(4) = 3 + 1.893 + 0.5 = 5.393. 2.5 / 5.393 = 0.464.

The case cannot be answered completely whatever the generator does, because recall is 0.5. That is the point of encoding both required documents.

**K2.** For a forbidden-document case the only document that answers the question is one the principal may not see. A system that leaks it would score perfect recall, so recall rewards the exact failure the case exists to detect. The conversion moves that document to `forbidden_doc_ids` and clears the required list, so the case contributes nothing to ranking metrics. Two checks replace recall. The leak check requires that no forbidden or ACL-invisible chunk appears in the hits, the packed evidence, or the citations. The abstention check requires that the system declines to answer.

**K3.** Faithfulness asks whether every claim in the answer is supported by the evidence that was packed. Correctness asks whether the answer states the facts the rubric requires. They diverge in both directions.

- **Faithful but incorrect:** the packer includes the outdated HR FAQ, and the answer says "you can carry over 5 PTO days", citing it. Every claim is supported by the evidence, and the answer is wrong under PTO Policy 3.0.
- **Correct but unfaithful:** the packed evidence contains only the remote-work policy, and the answer correctly states the 10-day carryover limit from the model's prior knowledge or another conversation. The fact is right and nothing in the evidence supports it, which is a hallucination that happened to be true.

**K4.** The five parts and what each catches that a judged end-to-end score misses:

- **Thirty questions with required evidence and an asker.** Encoding the required document and the principal is what makes every later check possible. A judge-only score has no notion of which evidence was needed or who asked, so it cannot say whether a failure is retrieval or generation, and it scores the answer the same whoever asked.
- **Hit@k run as each user.** Separates "the evidence never reached the prompt" from "the model ignored it". A judged score that stays flat while prompts change, as in the opening story, is often a retrieval or packing problem no prompt can fix. Running as the real user also exposes over-filtering that an admin run hides.
- **A leak check on every case.** Catches restricted or cross-tenant chunks in hits, packing, or citations. An end-to-end judge rewards a correct answer drawn from a leaked document, so it counts the incident as a success.
- **Citation validity.** Catches cited chunk ids that were never packed (invented or copied from evidence text). A judge reading fluent prose with plausible markers rarely checks ids against the prompt.
- **Abstention on trap cases.** Catches false answers on forbidden and unanswerable questions. A quality score over answered cases does not count questions that should not have been answered at all, and a judge may rate a confident invented answer highly.

**K5.** The earliest loss is the one that bounds the outcome. If a required document never reached the candidate pool and another was truncated in packing, fixing the packer leaves the answer incomplete; fixing retrieval is necessary first and then exposes the packing problem. Reporting the last loss would send engineers to a stage whose fix cannot change the result. A permission leak overrides everything because it is a security failure independent of answer quality: an answer can be correct precisely because it used a document the user may not see, and labeling that case `ok` or `citation-error` would hide the incident.

**K6.** Recall and evidence sufficiency ask whether the needed evidence is present. Context relevance asks how much of what was packed is relevant. A configuration that packs many chunks almost always has the evidence and also hands the generator distractors, stale versions, and possibly injected text, at a higher token cost. Only context relevance (or precision@k) makes that noise visible.

## Engineering questions

**E1.** Expected elements of a good design:

- **Labels.** Document ids for routing questions ("which contract covers vendor X?"), plus span labels for field questions on long contracts and multi-page invoices, because a document-level hit does not prove the right clause or line item was retrieved. Spans should be short verbatim strings matched whitespace-insensitively, since OCR output varies.
- **Tags.** `scanned` versus `born-digital`, `ocr-low-confidence` (from Chapter 11's OCR confidence), `table` for line-item questions, `contract` versus `invoice`, `exact-id` for invoice numbers and PO numbers, `numeric` for amounts and dates, `multi-hop` for questions linking an invoice to its contract.
- **Permission contexts.** Finance groups, procurement, each tenant; invoices are typically restricted, so most cases run as a finance principal and a deliberate set runs as ordinary employees.
- **Abstention and forbidden cases.** Ordinary employees asking for invoice amounts (forbidden-doc, abstain), questions about vendors with no contract (no answer exists, abstain), and questions whose answer is on an illegible page (abstain or escalate).
- **Size and split.** Start with 60 to 100 hand-labeled cases across the slices, group the split by document so that questions about one contract stay together, and keep OCR-heavy cases as their own reported slice because their failures trace to ingestion, not retrieval.

**E2.** The response should say that the composite hides three things. It hides which subsystem regressed: a recall drop compensated by a faithfulness gain leaves the score flat. It hides leaks entirely, or worse, lets a leak be outweighed by quality. And it averages over different populations: faithfulness is defined only on answered cases, recall only on answerable cases, so the weights apply to different denominators and the number changes when the abstention rate changes. The dashboard should show retrieval (recall@5 with CI, MRR), answers (faithfulness, rubric coverage, citation precision and recall), abstention outcomes (false answers and false abstains as counts), the leak count (required to be zero), and the stage-isolation distribution. The gate should require zero leaks on every case, every forbidden-doc case leak-free, no significant regression on recall@5, faithfulness, or abstention correctness beyond a tolerance, no large-slice regression beyond a tolerance, all citations valid, and latency and cost within budget.

**E3.** Expected elements:

- **Lists and metrics.** Compute recall@50 (or the rerank depth) on the fused list before reranking, and hit@1, hit@3, MRR, and nDCG@10 on the reranked final list; evidence-packed at the packing budget; context relevance. Report the same metrics for the baseline without reranking so the delta isolates the reranker.
- **Interpretation.** If recall at rerank depth is low, the reranker cannot help and the work is in first-stage retrieval. The reranker should raise MRR and hit@1 at constant recall at depth.
- **Slices.** Paraphrase, multi-hop, conflicting-versions (does the reranker prefer the newer policy?), exact-id (cross-encoders sometimes demote exact identifier matches), and adversarial (does it promote instruction-heavy passages?).
- **Stage isolation.** The count of `dropped-by-rerank` cases must not rise; any case moving from `ok` to `dropped-by-rerank` is read individually.
- **Latency.** Measure rerank latency at p50 and p95 for the chosen depth and batch size from the trace, and gate on p95 end-to-end latency (for example, within the 2 s time-to-first-token target).
- **Gate rules.** Block if MRR or hit@1 does not improve significantly, if recall@5 or evidence-packed regress beyond tolerance, if `dropped-by-rerank` grows, if any slice of at least five cases regresses beyond tolerance, or if the latency budget is exceeded.

**E4.** The judge must not gate the `conflicting-versions` slice on its own: a 30 percent false pass rate there means roughly one in three unfaithful answers passes. Options, in order of preference: gate that slice on a deterministic signal instead (Chapter 13's stale-source validator, or citation of the newer document required by the rubric), route its failures and a random sample of its passes to human review, and keep the judge as a reported, non-gating metric for the slice. Overall, an 8 percent false pass rate may be acceptable for a gating metric with a sampled human review of passes. To improve the judge, add anchored examples of conflicting-version answers to the verification prompt, include document version and effective date in the evidence rendering so the judge can see which source is current, and consider making "supported by an outdated source" a fourth verdict. On the dataset side, add more `conflicting-versions` cases so the slice is large enough to calibrate (a handful of cases cannot estimate a 30 percent rate with any precision), and recalibrate after any change.

## Practical exercises

**P1.** Expected implementation: `RagExpectation.required_spans: list[str] = []`, carried through `gold_row_to_case` from an optional `required_spans` field. `span_recall_at_k(output, spans, k)` normalizes whitespace and case in both chunk text and spans and counts a span as found when it occurs in any of the top k hit texts. The retrieval evaluator emits `span_recall@k` only when spans exist. Acceptance criteria: unit tests with a span split across two chunks (not found in either, so recall is lower than document recall), a span found in a lower-ranked chunk of the right document, and a case where document recall is 1.0 because the right document's preamble chunk was retrieved while the span-bearing section was not. The write-up names the labeled cases where the two metrics disagree and what that says about chunking.

**P2.** Expected implementation: a `FunctionEvaluator` named `first_stage` that calls `stage_lists(output.retrieval)`, keeps lists of kind `candidate`, maps chunk ids to document ids with `doc_id_of` (or the output's chunk map), and emits `first_stage_recall@50:<list name>` per list plus `first_stage_recall@50:union`. It returns no scores for cases that are not answerable. Acceptance criteria: a test with two candidate lists where each finds a different required document (per-list recall 0.5, union 1.0), a test with Chapter 12's trace layout including a transform stage, and a report section showing union recall next to final recall.

**P3.** Expected implementation: a `JudgeCache` protocol with `get(key)` and `set(key, result)`, an in-memory backend and a JSONL backend that appends records and loads them on start. The key is a SHA-256 over the judge's `version`, the answer text, and the ordered packed chunk ids (plus their content hashes, so a re-chunked corpus misses the cache). `FaithfulnessJudge` checks the cache before the two calls and stores the `FaithfulnessResult` after. Acceptance criteria: a test with a `FakeLLM` that counts requests shows N calls on the first `score_run` and zero on the second over the same stored run; changing the judge model string changes the version and misses the cache.

**P4.** Expected implementation: an optional `embeddings: EmbeddingClient` argument; when present, dedupe compares the candidate's embedding with kept questions' embeddings by cosine similarity against a threshold (Jaccard remains the fallback). A multi-chunk mode pairs chunks from different documents (for example a policy and its FAQ, or an incident report and the runbook it references), asks for a question that requires both, and requires one verbatim evidence quote from each chunk; the answerability check receives both passages. Kept multi-chunk candidates produce cases with two required documents and a `multi-hop` tag. Acceptance criteria: tests with `FakeEmbeddings(vocabulary=...)` showing a paraphrase pair deduplicated and an unrelated pair kept, a multi-chunk candidate dropped when one quote is missing, and a report comparing the difficulty distribution with and without the new mode (more `paraphrase` and `reasoning`, fewer `lexical`).

## Debugging exercises

**D1.** Root cause: the refactored pipeline stopped recording fusion and rerank candidate lists in the trace, or records them under keys the reader does not recognize (for example a new `kind` value or a `ranked_ids` field), so `stage_lists` sees only the candidate lists and the final hits. Every loss after the candidate stage then has no recorded intermediate stage, and losses between fusion and the final cut fall through to the "blame the last stage recorded" branch, which with no fusion or rerank lists is `not-retrieved`. First-stage recall@50 being unchanged confirms that the candidate pool did not get worse. Inspect `trace["stages"]` entries for one affected case: their `name`, `kind`, and whether `candidate_ids` or `chunk_ids` is present for fusion and rerank; compare with a run from before the refactor. The fix is to restore the trace contract and add a canary test that asserts a known case is labeled `dropped-by-rerank`.

**D2.** The prompt change made the generator abstain more often on difficult questions. Faithfulness is computed only on answered cases, so removing the hardest answers raised it without making any answer more faithful; coverage on answered cases stayed flat, and false abstains nearly quadrupled. The report should have made it obvious by printing the abstention outcome table directly under the judged metrics, by stating that judged averages cover answered cases only, and by showing stage-isolation shifts: the eleven new false abstains appear as cases moving from `ok` to `generation-ignored-evidence` with the detail "abstained although the evidence was packed". A gate rule on `abstention_correct` regression would have blocked the change.

**D3.** Likely gaps, most likely first:

1. **The gold set never asks as a retail store manager about logistics content.** The ACL rule is checked on every chunk retrieved during evaluation, but only for the principals and questions in the set. Add cross-tenant probes for each tenant pair and each restricted group, and generate them systematically from the document ACLs.
2. **The evaluation ran with a different retrieval path than production**, for example without the semantic cache, a different index, or an evaluation-only admin token. The leak happened in a component the evaluation never exercised. Run the evaluation through the production request path as the case's principal, and include the cache in the system under test.
3. **The leak entered after retrieval**, for example through a cached answer keyed without tenant, or a citation resolver that looks up documents without an ACL check. Extend the leak check to the cited documents as resolved by the production citation mapper and to cached responses, and add a test that replays a cached answer to a user of another tenant.
4. **The document's ACL metadata was wrong at ingestion** (the incident report tagged `shared`), so the ACL rule itself considered it visible. Add ingestion-time checks that documents of restricted types (incident reports) cannot carry `shared` tenancy, and a gold case that asks about that document as an outsider with the document in `forbidden_doc_ids`, which catches mislabeled ACLs through the gold label rather than the rule.

The telemetry that reveals which one applies: the production trace's principal, tenant, retrieval stage candidate ids, cache hit flag, and citation resolution records for the offending request.
