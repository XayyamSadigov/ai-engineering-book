# Chapter 16 — Solutions

## Knowledge questions

**K1.** The model never executes anything. It emits a structured request (a tool name and arguments) that the application may or may not honor; the application runs the code and returns the result as a message. Because the request is just model output, it can be wrong, confused, or produced under the influence of injected text, and the protocol carries well-formed bad requests exactly as well as good ones. Therefore authorization cannot live in the model or the prompt. It lives in deterministic code on the application side, decided from trusted state (the authenticated user's identity, tenant, groups, scopes) and applied at execution time to every call, whatever tools were offered.

**K2.** `read` (search_tickets, lookup_employee, get_service_status): no state change. `reversible_write` (create_ticket, draft_reply): changes Northwind state but can be undone. `irreversible` (deleting a record, changing access, issuing a refund): cannot be undone. `external` (send_reply): the effect leaves Northwind's boundary. External is separate because leaving the boundary adds disclosure risk: an internal irreversible action damages your own data, while an external one can carry your data to someone else. An agent holding both sensitive reads and an outbound channel has an exfiltration path, which needs destination allowlists, data classification, and approval showing full content, controls that irreversibility alone does not imply.

**K3.** A key that names one logical action, so the first execution performs the effect and records the result while later executions with the same key return the recorded result. The application chooses it from trusted values (tool, tenant, session or user, normalized-argument hash, or a client-supplied header or runtime step id), never the model, which would generate a new key on a retry. A timeout on a non-idempotent tool means the request may have reached the downstream system and taken effect; the harness does not know. Retrying could duplicate the effect, and declaring failure could lose it, so the record is marked `unknown` and the error says not to retry. Resolution comes from asking the system of record (a `reconcile` function querying by key) or from a human.

**K4.** `validation`: arguments wrong; the model repairs and calls again; not retried by the executor. `permission`: caller not allowed; nobody recovers automatically, the model explains to the user; not retried. `not_found`: target missing; the model asks the user or searches; not retried. `transient`: may succeed later; the executor retries with bounded exponential backoff and jitter (honoring `retry_after_s`); for non-idempotent tools only when the handler knows the effect did not happen. `fatal`: broken or outcome unknown; a human recovers; not retried.

**K5.** The approval record stores the tool name and the hash of the validated, normalized arguments, plus the principal and an expiry. Verification succeeds only if the call being executed has the same tool, the same hash, and the same user and tenant, while the approval is approved, unexpired, and unused; it is consumed after success. Any change to recipient, subject, or body produces a different hash and needs a new approval. If `send_reply` took only a draft id, the approver would approve the id, and the draft's text could be edited after approval without changing the hash, so what was sent could differ from what was approved. Taking the full content makes the approved bytes and the sent bytes provably identical.

**K6.** Bounded: wall-clock time (parent kills the process group), CPU seconds, address space (where the kernel honors it), maximum file size, open files, captured output size, inherited environment (scrubbed to PATH, locale, timezone), working directory (fresh temp dir, deleted). Not isolated: the filesystem outside the temp dir (the child can read anything the service account can) and the network (unless `network="deny"` on Linux with `unshare`). It also does not filter syscalls or drop privileges.

## Engineering questions

**E1.** Split into operation-specific tools: `get_account`, `update_account_contact`, `suspend_account`, `close_account`, each with its own args model. Selection improves because each description states one purpose and when to use it, instead of the model getting both an `action` string and a matching `payload` shape right. Validation becomes possible: each tool has a closed, typed schema; a polymorphic `payload` is effectively untyped. Policy maps cleanly: read, reversible write, irreversible each get their own permission scope, rate limit, and approval requirement; a single tool forces the strictest policy on everything or the loosest on dangerous actions. Approval summaries are specific ("Close account 4411") rather than generic. The menu-size concern is solved by per-task filtering (`ToolRegistry.select` by tags or names), not by merging risk classes. Acceptable middle ground: group only operations of the same side-effect class and permission.

**E2.** Shared state is needed for: the idempotency store (otherwise a retry routed to another replica re-executes the side effect, so duplicate suppression silently works only by luck of routing); the approval store (an approval created on replica A cannot be found when the approve request lands on replica B, and single-use is not enforced across replicas); rate-limit counters in `PolicyEngine` (each replica allows the full limit, so the effective limit is six times higher); conversation sessions in `SupportAssistant`; and the audit sink (events scattered across six local files or lost with in-memory logs). Back idempotency with PostgreSQL (`INSERT ... ON CONFLICT DO NOTHING` on the same schema) or Redis `SET NX EX`; approvals with a PostgreSQL table; rate limits with Redis counters or sliding windows; sessions with Redis or PostgreSQL; audit with an append-only table or a log pipeline. The policy rules themselves are configuration and can stay in process, versioned.

**E3.** Class: irreversible (money leaves) and arguably external if it calls a payment provider. Permission `refunds:issue`, held by support agents in the retail tenant only; contractors denied via group deny. Args: `order_id` with a pattern, `amount` as a positive decimal with two places, `reason` as an enum (damaged, not delivered, wrong item, goodwill) plus optional bounded note. Rules: the order must belong to the caller's tenant (handler check, `not_found` otherwise); amount must not exceed the order's remaining refundable amount (handler, `validation`); amount at most an illustrative auto-limit (for example 50 currency units) for agents, otherwise escalate to approval by a lead; goodwill refunds always escalate. Rate limits: per agent per hour and per order (one refund per order per day). Idempotency: explicit key from order id plus amount plus reason, scoped to the order rather than the session so two agents cannot refund the same thing twice; pass the key to the payment provider; implement `reconcile` by querying the provider by key. Approver sees order id, customer, original amount, prior refunds, requested amount, reason, and the agent; approval bound to the args hash, expiry short (for example 30 minutes), four-eyes on.

**E4.** First measure: build a labeled set of outage conversations, check the audit trail for tool order, and look at whether the skipped cases share wording (for example "please open a ticket" phrasing). Check `tool_fingerprint` history to see whether a description changed. Likely causes: the `create_ticket` description does not say to check status first; the user's explicit request to create a ticket outweighs the system prompt; the status tool's description does not mention outages in user language. Fixes without changing the model: rewrite `create_ticket`'s description to say "use only after get_service_status and search_tickets show no existing incident"; add user-language triggers ("down", "not working") to `get_service_status`; and, if the order is a business rule rather than a preference, enforce it in code: a policy rule (or workflow step, Chapter 17) that denies or escalates `create_ticket` with category `vpn_network` unless a status check for the relevant service occurred in this session, returning a validation error telling the model what to do. Rerun the selection evaluation to confirm.

## Practical exercises

**P1.** Expected: `CloseTicketArgs(ticket_id: pattern TCK, resolution: str 10..2000)`; `Tool(name="close_ticket", side_effect=REVERSIBLE_WRITE, required_permission="tickets:write", idempotent=False, reconcile=...)`. Handler loads the ticket with `tickets.get(id, tenant=ex.tenant)` (`not_found` if missing), checks `ticket.created_by == ex.user_id` or the caller is a lead. This can be a policy rule if the rule receives a ticket lookup, but the cleanest is the handler raising `ToolError.permission("not_owner", ...)` because it needs data. Sets status closed and resolution. Tests: creator closes their own ticket (ok); another agent is denied with category permission and the ticket stays open; a lead closes any ticket in tenant; a ticket in the other tenant returns not_found; closing twice with the same arguments returns `duplicate=True` and one state change. Acceptance: all pass offline; the description says when to use it.

**P2.** Expected: `begin` does `SET idem:{key} <json in_progress record> NX EX ttl`; on success return None; otherwise GET and parse, converting stale in_progress (updated_at older than lease) to unknown with a compare-and-set (a Lua script or WATCH/MULTI) so two callers cannot both take over. `complete` writes the succeeded record preserving the TTL (`SET ... KEEPTTL` or `EX` remaining). `mark_unknown`, `release` (`DEL`), `get`. Run `test_duplicate_side_effect_suppressed_in_memory_and_sqlite` parametrized with the new store; with a fake Redis (for example an in-memory dict implementation of the used commands) offline, and against a real server under `@pytest.mark.integration`. Acceptance: same behavior as the other stores, including key reuse rejection by the executor.

**P3.** Expected: `FetchArgs(url: HttpUrl, max_length)`; handler parses the URL, rejects schemes other than https, compares the host (after lowercasing, without userinfo, rejecting IP literals or resolving and checking against private ranges) to an allowlist, and raises `ToolError.permission("egress_denied")` before any request. The request uses `httpx.Client(timeout=ex.remaining_s(), follow_redirects=False)` (redirects re-checked manually against the allowlist), streams the body and stops at a byte cap, and returns status, content type, and truncated text marked as untrusted. Tests use `httpx.MockTransport` and assert the transport was never called for `https://attacker.example/?q=secret`, that redirects to non-allowlisted hosts are refused, and that oversized bodies are cut. Better still, implement the allowlist as a policy rule so denials appear in the audit trail with a rule id.

**P4.** Expected: a JSONL file of `{request, expected_tool}` with "none" allowed; a runner that, for each item, runs `ToolLoop(llm, executor, max_rounds=1)` with a fresh session and records the first tool called (or none); metrics: accuracy, per-tool precision and recall, and a confusion matrix printed as a table. Offline test uses a `FakeLLM(handler=...)` that maps requests deterministically to tools so the runner's counting is verified exactly. The real-model run is marked integration and reports results without asserting a fixed number, or asserts a regression threshold stored in the repo. Acceptance: the runner is reusable in CI (Chapter 25) and the set includes adversarial cases (requests that should call no tool, overlapping tools).

## Debugging exercises

**D1.** Root cause: the same logical send was requested from two sessions (for example the agent asked in two browser tabs, or reopened the chat), and the default idempotency key includes the session id, so the two executions had different keys and neither was a duplicate of the other. The approval manager deduplicates only *pending* requests for the same user and hash; the first was already approved and consumed when the second was requested, so a fresh approval was created and the lead approved it without noticing it was a repeat. Telemetry: identical `args_hash` on both `tool.executed` events, different `idempotency_key` and `session_id`, no `tool.duplicate_suppressed`. Fixes: scope `send_reply`'s key to the action rather than the session, for example an explicit key from tenant, ticket id, recipient, and body hash, so repeats within a window are suppressed regardless of session; have the outbox reject identical content to the same recipient within a short window; show the approver "an identical message was sent 11 minutes ago" by querying recent executions by `args_hash`.

**D2.** The deploy changed `get_service_status`'s description or schema (fingerprint changed), most likely removing the enumerated service names from the description or loosening the parameter in a way that left the enum in validation but not visible to the model, or renaming values. The model now guesses names (`"VPN"`, `"vpn-service"`), gets validation errors, and loops repairing them, adding rounds. Confirm by diffing the tool schema at the two fingerprints and checking that the error details list allowed values. Fix: put the closed set back in the schema as an enum the model sees (and list the values in the description), make the validation error include the allowed values so a single repair succeeds, optionally normalize harmless variants (case) in a `field_validator` before the enum check, and add the selection and argument-validity evaluation to CI so a description change that raises invalid-argument rates fails the build.

**D3.** The ticket system slowed down (p99 6 s) past `create_ticket`'s 5-second timeout. Each call that hit the timeout may or may not have created the ticket, so the executor marked the keys `unknown` and returned `outcome_unknown`. No retries happened, which is why there are no duplicates, but the outcomes are unresolved. Right now: query the ticket system by the idempotency keys from the `tool.failed` events (the handler passes the key to the store), complete the records that exist and release the ones that do not, and tell affected users their ticket ids; consider temporarily raising the timeout while the downstream recovers. Permanently: set the timeout from measured latency with headroom (and pass the remaining deadline downstream), add a `reconcile` function to `create_ticket` that looks tickets up by idempotency key so unknown outcomes self-resolve on the next attempt (Project 4 already does this, so check whether it was deployed and whether the store records the key), alert on `outcome_unknown` rate, and consider an asynchronous create with a job id when the downstream is slow.
