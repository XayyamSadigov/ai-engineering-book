# Chapter 17 — Solutions: AI Workflows and Orchestration

Identifiers match the exercises in `book/chapters/17-ai-workflows-and-orchestration.md`.

## Knowledge questions

**K1.** LLM-enhanced application: application code decides every step and calls the model as a function for one value (Northwind example: a one-line summary of each HR policy shown next to its search result). Deterministic workflow: orchestration code decides every step, and any model output is validated against a schema before the fixed next step (example: a weekly job that collects changed IT runbooks, summarizes each change, validates the summary length and links, and emails the digest). Probabilistic workflow: code decides from a validated model value which of a fixed set of edges to take (example: an IT request router that sends `access` requests to an approval path and `how-to` questions to the RAG answerer). Agent: the model names the next action at each iteration and code only checks that the action is allowed (example: a laptop troubleshooting assistant that chooses which read-only diagnostics to run based on the previous result). Multi-agent: several such loops with different roles or permissions coordinated by a supervisor or protocol (example: vendor-contract review where a legal-scoped agent and a finance-scoped agent hold disjoint permissions and a supervisor merges their findings). The chapter's own examples (tag suggestion, invoice extraction, triage, incident research, Project 6) do not count.

**K2.** Under independence the chain succeeds with probability 0.99 × 0.98 × 0.97 × 0.99 × 0.95 ≈ 0.885, so roughly one job in nine fails. The real figure is usually lower because step failures are positively correlated with hard inputs: a confusing ticket lowers the classifier's and the drafter's success together, and a poor draft lowers the validator's chance of passing it. It can be higher when later steps are designed to repair earlier ones: a validator that routes a fixable draft back to the drafter recovers some of the failures that the raw product counts as lost, so the chain-with-repair's success rate exceeds the naive product.

**K3.** The approval node's job is to wait, so the durable fact that matters is "we are waiting here with this state." Writing that fact before the node is the only way to have it recorded while the process is gone. Every other node's checkpoint records "this node completed and produced this state"; writing it before the node would record completion that has not happened. If all checkpoints were written before their nodes, a crash inside a node would leave a checkpoint pointing at the node after it, and `resume_from_checkpoint` would skip the interrupted node entirely, losing its work and, for `send`, silently never sending.

**K4.** Transient, validation, and fatal errors are exceptions (`TransientError`, `StepValidationError`, `FatalError`), because they are detected by the step or by infrastructure at the moment of the call and the engine's response (retry, fail) is generic. Impossible tasks surface indirectly through repeated validation failures and an attempt counter in the state. Semantic errors must be state because nothing raised: the model returned valid, well-formed, wrong output. Only a later node that examines the output (a validator) can detect it, and it records a verdict in the state so a router, which is domain logic, can decide between re-draft, escalate, and send. The engine has no business knowing what "wrong" means for a ticket reply.

**K5.** It is an agent. The set of possible paths is no longer enumerable because the model can emit any node name, including ones out of order (for example `send` before `validate`). What is lost is the closed-set guarantee that every router in a probabilistic workflow provides: that model text becomes control flow only after being mapped onto one of a fixed, reviewed, tested set of edges. The minimal fix is to keep the model's field but map it through a dictionary of allowed transitions from the current node, rejecting anything else; at that point the design is a probabilistic workflow again.

**K6.** From simplest to most complex: LLM-enhanced application, deterministic workflow, probabilistic workflow, single agent, multi-agent. The rule: start at the leftmost position that can meet the acceptance bar, and move one position right only when measured failures show the current position cannot fix them, typically failures where the path, not a step, was wrong. "The model can figure out the steps" is not evidence because it is true of every position and says nothing about whether the extra freedom improves outcomes on real cases; the evidence is a failure analysis plus a side-by-side run on the same cases with success rate, calls, p95 latency, and cost per successful task.

## Engineering questions

**E1.** A reasonable `InvoiceState`: `invoice_id: str`, `tenant: Literal["retail","logistics"]`, `source_uri: str` (object storage reference, not the PDF bytes), `extracted: InvoiceFields | None` (pydantic model with line items, totals, vendor, currency), `extraction_attempts: int`, `totals_ok: bool | None`, `po_match: POMatch | None` (po_number, confidence, matched_by: Literal["exact","model"]), `requires_approval: bool` (set by code from a threshold, never by the model), `approved: bool | None`, `approver_id: str | None`, `approved_total_hash: str | None` (hash of the approved fields so a changed extraction invalidates the approval), `posted_ledger_id: str | None`, `log: list[str]`. Append-only fields: `log`, `extraction_attempts`, and a `po_candidates: list[str]` if matching retries. The irreversible node is `post_to_ledger`. Its idempotency key is `f"{tenant}:{invoice_id}:{approved_total_hash}"`: same invoice, same approved content, one posting; a changed total after approval yields a new key only after a new approval, and the node refuses to post when `approved_total_hash` does not match the current extraction.

**E2.** Duplicate deliveries can start a second run at the consumer: two workers each receive the same ticket message and each call `graph.run`. Prevent it at submission with an idempotency key equal to the ticket id (or ticket id plus ticket version) stored in a table with a unique constraint; the second consumer sees the existing `run_id` and either attaches to it or drops the message. Inside `send`, a duplicate can also arise from a resume after a crash between delivery and checkpoint. Prevent it by making the sender idempotent: it receives the engine's `step_key()` (`run_id:node:visit`, stable across re-execution of the same visit), optionally extended with a hash of the draft, checks a sent-messages table before calling the mail or ticket API, and records the key in the same transaction as the send when the downstream API offers an idempotency header, or immediately after when it does not. The engine must give `send` no retry policy; the only acceptable repeat path is a deliberate resume, which the idempotent sender turns into a no-op.

**E3.** Table `workflow_checkpoints(run_id text, seq int, graph_name text, graph_version int, node text, next_node text, status text, state jsonb, created_at timestamptz, primary key (run_id, seq))` with an index on `(status, created_at)` for finding stale paused runs, and a `workflow_runs(run_id primary key, idempotency_key unique, tenant, graph_name, graph_version, created_at)` table. `latest` is `order by seq desc limit 1`; `history` is `order by seq`. On resume, the engine compares the stored `graph_version` with its own. If they differ, it looks up a registered migration function `migrate_v3_to_v4(checkpoint) -> checkpoint`; for the rename, that function rewrites `node` and `next_node` from `approval` to `review` and leaves the state unchanged. If no migration is registered, resume refuses with a labeled error (`graph_version_mismatch`) and the run goes to a dead-letter queue for a human, rather than failing inside pydantic with an opaque message or, worse, resuming at a node that no longer exists.

**E4.** Replace the static edge `retrieve_policy -> draft` with a single node `gather_context` whose step function runs `fan_out([lambda: retrieve_policy_async(state), lambda: lookup_customer_history_async(state)])` and then merges: it copies `policy` from the first result and `customer_history` from the second into a new state. Fan-in rules: the policy branch is required, so if its result is a `TransientError` the node re-raises it and lets the node's `RetryPolicy` retry the whole fan-out (both branches, since they are cheap and idempotent). The history branch is optional, so if its result is an exception the node sets `customer_history = None`, appends `"history unavailable"` to `log`, and continues; the drafter prompt already handles a missing history. Any non-transient exception in either branch is re-raised unchanged so a bug is not masked as a missing enrichment. Latency for the node becomes max of the two lookups instead of their sum.

**E5.** Activities: `classify`, `draft`, and `validate` (they call the model, which the workflow function may not do because replay must be deterministic), `send` (a side effect), and, if it becomes a real retrieval call, `retrieve_policy`; `escalate` is an activity if it writes to a ticket system. The workflow function keeps the control flow: the sequence of activity calls, the redraft loop with its attempt counter, `needs_human`, and the two routers, all as ordinary code over validated activity results. Model nodes get an activity retry policy that retries only transient errors and marks validation and fatal errors non-retryable; `send` gets a single attempt. Approval becomes a wait for a signal (an external message carrying the decision) with a durable timer as its timeout, for example three days, after which the workflow escalates. The stale-handle check moves into the workflow: the approval UI sends back the hash of the draft it showed, and the workflow compares it with the hash of the current draft before accepting the decision, rejecting a mismatch. The history will contain every activity's inputs and results, so ticket text and drafts are stored in the engine; it must get the same retention and access rules as the ticket system, and large payloads should be stored elsewhere with a reference in the result. What `send` still needs: an idempotency key that the receiver honors (for example built from the workflow id and the activity id, which stay stable across retries of that activity), because activities execute at least once and the engine cannot know whether a timed-out send was delivered.

## Practical exercises

**P1.** Expected implementation: `build_triage_graph` gains a `fallback_model: Model | None = None` parameter. The `draft` node's step function becomes a small wrapper that calls `patterns.retry` around the primary draft with the node's attempt count, catching `TransientError`, and on exhaustion calls `draft_reply(state, fallback_model)` once if a fallback is provided, appending `"draft via fallback"` to `log`; the node's own `RetryPolicy` is set to `max_attempts=1` to avoid multiplying attempts. Acceptance: a test with a primary that always raises `TransientError` and a secondary `FakeModel` that returns a valid draft completes with `outcome == "sent"` for a shipping ticket, the log contains the fallback marker, and `model.calls` on the secondary has exactly one `draft` entry. A second test with a primary raising `StepValidationError` must fail without invoking the fallback.

**P2.** Expected implementation: `JsonlCheckpointer(path)` whose `save` appends one JSON line per checkpoint (dataclass fields, state already a dict), and whose `latest` and `history` read the file, filter by `run_id`, and sort by `seq`; for the crash test the two graphs are built with two separate `JsonlCheckpointer` instances pointing at the same temporary file (`tmp_path`). Acceptance: the existing crash test passes unchanged except for the checkpointer; the file contains six lines for the run after resume; a corrupted trailing partial line (simulated by truncating the file mid-line) is skipped with a warning rather than crashing `latest`, which is the realistic failure of append-only logs.

**P3.** Expected implementation: `_execute` collects `trace[i].node` into `RunResult.path` (or derives it from `trace`), and `compare.py` builds twenty tickets with scripts chosen per category, runs the graph, and prints a `Counter` of tuple paths. Acceptance: a `test_golden_paths` parametrized over the twenty tickets asserts, for each, the exact tuple of node names, for example `("classify","retrieve_policy","draft","validate","send")` for shipping and `("classify","retrieve_policy","draft","validate")` followed by a paused status for refund; the test fails if any router change alters a path even when the final outcome is unchanged.

**P4.** Expected implementation: a `research_agent` node that runs a bounded loop of at most three iterations in which the fake model returns either `{"action":"retrieve_more","query":...}` or `{"action":"draft"}`; each `retrieve_more` appends a policy snippet to the state and costs one simulated model call. The agent graph replaces `retrieve_policy` with this node. Both graphs run over the same twenty scripted tickets (including three that the fixed graph escalates because the needed policy is not the category's default). Acceptance: the report prints success rate, mean model calls per ticket, and total simulated latency for both; the expected shape is that the agent graph recovers some of the three escalations at the price of one to two extra calls per ticket on average, and the write-up states whether that trade is worth it under an 8 s p95 budget.

## Debugging exercises

**D1.** Root cause: the retry policy on consecutive model nodes multiplies traffic during an incident and the backoff is too short to outlast a two-minute outage; raising `max_attempts` makes both worse. The run failed correctly; what is missing is a circuit breaker at the gateway level (Chapter 29) that opens on repeated `TransientError` and fails fast, plus a longer `max_delay_s` or a fallback model on the `draft` node. Telemetry that confirms it: `attempts` per node rising to the cap across all runs in the incident window, provider error rate at the gateway, and after the fix, a short open-circuit period with fast failures followed by recovery, instead of nine calls per run for two minutes.

**D2.** Sequence: the first `send` delivered the message, then the process died (or hit a `FatalError`) before the engine wrote the completed checkpoint, so the engine wrote a failed checkpoint for `send` with `next_node == "send"`. Four minutes later a resume (automatic or manual) re-ran `send`, which delivered again and completed. Defect one: the sender is not idempotent; it has no key derived from `run_id`, node, and draft hash and no sent-message record, so the resume could not detect the earlier delivery. Defect two: the failed checkpoint has no error text, which means the exception was swallowed or the process was killed without the engine recording the cause; the engine must record `error` on every failed checkpoint and the operator should see "failed inside irreversible node" before resuming. A third contributing factor is operational: automatic resume of a run whose last node is a side effect should require a human look.

**D3.** The deploy changed the validator prompt (or the deterministic checks in `validate`), making it stricter: more drafts are judged `fixable`, the second draft is also rejected, and the router escalates. Per-node success is unchanged because every node still returned valid output, and the eval suite is green because it asserted final outcomes on a golden set that lacked borderline drafts and did not assert paths. The metric that found it is the path distribution, specifically the `escalate` fraction by graph version. Missing from the eval suite: path assertions (golden paths), a path-distribution regression check against the previous version on the same ticket set, and borderline cases that exercise the `fixable` edge.
