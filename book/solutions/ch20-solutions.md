# Chapter 20 — Solutions: Agent Architectures

## Knowledge questions

**K1.** Best case means the smallest successful run: one tool call per agent, first drafts accepted.

| Pattern | Owner of "what next" | Sequential model calls, best case |
|---|---|---|
| ReAct | the model, at every step | 2 (one tool call, one answer) |
| Router | rules or one classifier call, then the specialist model | 2 with a rule match, 3 with model routing |
| Planner-executor | planner up front; deterministic rules decide replans | 4 for one step (plan, tool call, report, synthesis); 2n + 2 for n steps |
| Supervisor/worker | supervisor model, through delegate tools | 4 (delegate, worker tool call, worker answer, supervisor answer) |
| Hierarchical | a supervisor model at each level | 6 for depth two (two delegations, worker's two calls, two summaries) |
| Reflection | the model; the critic inside the DoD can veto | 3 (tool call, answer, critic) |
| Evaluator-optimizer | controller code; independent evaluator scores | 2 with deterministic checks only, 3 with a judge |
| Parallel | code fans out; aggregator merges | 3 (slowest branch's two calls, aggregator); 2 with a code merge |
| Sequential | code, fixed order | sum of steps, e.g. 4 for triage call, two-call agent step, write call |

**K2.** ReAct resends the whole transcript on every call, so input at step i is roughly base + i times the average observation size; summing over n steps gives n times base plus observation size times n squared over two. Each planner-executor step starts from a short step prompt plus only the findings it depends on, so per-step input is roughly constant and total input grows linearly; the planner and synthesis calls grow with the number of findings, which are short summaries. The advantage disappears when observations are small relative to the base prompt, when n is small, when every step depends on every earlier finding (so step prompts grow too), or when prompt caching makes the resent prefix cheap enough that only uncached tokens matter.

**K3.** In reflection the runtime owns the loop: a rejected final answer becomes a harness note and the same agent revises in the same context. The critic sees the answer and the observations, and the only stop rule is the bound on rejections; there is no plateau rule and no best-so-far, because the run ends with the last draft accepted or with `VERIFICATION_FAILED`. In evaluator-optimizer, controller code owns the loop. The evaluator is independent of the generator (different prompt or model, deterministic checks first) and sees the candidate and whatever evidence it is given, not the generator's transcript. The controller implements pass, round budget, and plateau stops and always keeps the best candidate.

**K4.** The deterministic checks are exact, cheap, and explainable; a failure means the report breaks its contract (an uncited claim, an invented runbook, a citation to something never observed), which is unsafe to publish regardless of how good it reads. The judge is a calibrated but fallible instrument with false passes and false failures. As a hard gate, its false failures would block valid reports during an incident; as an advisory signal shown to the approver, it informs without blocking. Reversing them would let a fluent report with an invented runbook reach approval whenever the judge falsely passes it, block correct reports whenever it falsely fails them, and spend judge calls on every malformed draft.

**K5.** `all` assumes branches are complementary and each is necessary: verifying an access request requires the HR record, the directory entry, and the badge system to agree, and a partial answer is a wrong answer. `quorum` assumes branches are redundant measurements of the same fact: three independent checks of whether Trackline is degraded (status page, synthetic probe, latency metrics), where a majority is trustworthy. `any` assumes branches are best-effort enrichment: gathering context for a support reply from past tickets, docs, and recent incidents, answering with what arrived and naming what did not.

**K6.** So that what the human approved is exactly what gets posted. A model retyping a long report can truncate, paraphrase, or alter it, and a prompt injection in a retrieved document could steer the arguments. Passing a reference keeps the tool's arguments small and easy to validate and audit, makes the posted body a function of the stored, reviewed artifact, and avoids spending tokens on a copy.

## Engineering questions

**E1.** A router in front, with rules first. Harassment and safety terms match a rule that never reaches an agent: code creates a confidential case (`create_confidential_case`, write, restricted to the `hr` group) and notifies on-call HR; the employee gets a fixed acknowledgement. Policy questions route to a grounded answering step (one retrieval-plus-answer call with citations, Chapter 13) or a small ReAct agent with `search_policies` (read) if questions need several lookups. Leave requests route to a sequential workflow: extract dates and type (structured call), check balance and blackout rules (`lookup_balance`, read, plus code), draft the request (`draft_leave_request`, write and reversible), show it to the employee, and submit only on the employee's explicit confirmation (`submit_leave_request`, write, approval by the requester); manager approval stays in the HR system. Approval points: submission (the employee) and nothing else automated; case creation is code-triggered, never model-triggered. Diagram: request, rules, then three branches (human escalation, policy answer, leave workflow with a confirmation pause).

**E2.** Rule one, `deploy_precedes_onset`: inputs are the deploy step's data (deploys with timestamps, kinds, services) and the anomaly onsets already in the evidence ledger (extend the rule signature with the investigation). It fires when a deploy to service X lands within a configurable window before the earliest onset and no planned step examines X's metrics or searches incidents for that change kind. Reason: "deploy CHG-2026-0907 (migration on pg-logi-prod) at 05:15 precedes onset 05:50 and no step examines pg-logi-prod or past migration incidents." Tests: a scenario with a migration on a service outside the dependency map fires once and the replan adds the steps; a deploy after the onset, or one already covered, does not fire. Rule two, `onset_before_all_deploys`: fires when the earliest onset precedes every deploy in the window, meaning the "recent change" hypothesis is wrong; the reason asks for traffic and capacity evidence (dependency metrics, incidents about load). Tests: shift the deploy after the onset and assert the rule fires; keep it before and assert it does not.

**E3.** Keep a separate bounded runtime per step and keep the DoD; change what sits on the critical path. Execute independent steps concurrently by `depends_on` (P1); give the planner the dependency map so its first plan includes dependency steps, which usually removes the replan; let a step report deterministically from the tool's structured output (one call per step instead of two, still a separate run with its own budget and log); and use a template plan for known alert rules, falling back to the planner for novel ones. The critical path becomes roughly: one tool call for the first batch, one for the second batch, writer, writer revision if needed, judge: about five to seven sequential calls instead of seventeen, which at an illustrative one to three seconds per call fits thirty seconds with tool latency included.

**E4.** Baseline: Project 5 as is. Candidate: the hierarchy with the same tools at the leaves. Dataset: a frozen set of recorded scenarios (for example forty alerts with gold root causes and gold runbooks), including distractors such as unrelated deploys, healthy dependencies with noisy metrics, a dependency anomaly, and an injected document. Metrics: correct-cause rate, valid-runbook rate, first-round DoD pass rate, judge score, citation survival from leaf to root, model calls and tokens per investigation, p95 latency, engineer minutes to diagnose a sampled failure, and safety invariants (no unapproved posts, no cross-tenant evidence). Paired comparison with bootstrap confidence intervals. Decision rule fixed in advance: adopt only if correct-cause rate improves by an agreed margin with the interval excluding zero, cost stays within an agreed multiple (for example 1.5 times), p95 latency stays within budget, and no safety metric regresses; otherwise keep the baseline. Per-level metrics locate where the hierarchy helps or hurts.

## Practical exercises

**P1.** Add `depends_on: list[str] = []` to `PlanStep` and validate references. In `investigate`, repeatedly select the ready set (steps whose dependencies are done), execute it with a `ThreadPoolExecutor(max_workers=...)`, then append step records in plan order, merge evidence in plan order, and evaluate deviation rules per step in plan order before selecting the next batch; a replan replaces the queue after the batch. The in-memory and JSONL event stores and `MeteredLLM` are already locked; keep the evidence merge single-threaded. Acceptance: on the main alert, the evidence ledger keys and the set of (tool, target) pairs equal the sequential version; the number of batches is smaller than the number of steps; trajectory tests still pass when they compare sets per batch; a test with `max_workers=1` reproduces the sequential trajectory exactly.

**P2.** Wrap each read-only, idempotent tool in a memoizing adapter keyed by `action_key(name, arguments)`, scoped to one `EvaluatorOptimizer.run` (pass the cache into `agent_generator`), never shared across tasks, and never applied to tools whose side effect is not `READ`. The runtime still records a `ToolResult` per call, so measure backend executions with a counter inside the tool function. Acceptance: in the `compare.py` evaluator-optimizer case, backend executions drop from eight to four, the accepted answer is unchanged, and `Meter` shows the same number of model calls.

**P3.** In `decide`, refuse with `NotAllowed` when `user == inv.requested_by`, before resuming the run; add `decided_at` and keep `requested_by` and `decided_by` on the record. Tests: the requester's approval is refused (service raises, API returns 403, CLI exits 3) and the record stays `awaiting_approval`; a different on-call user's approval publishes. Existing tests already use different requester and approver.

**P4.** Write a small script that builds the service with `RecordingLLM(make_llm_client(), tape)` and fixed investigation ids, runs both alerts, and writes `tests/cassettes/real.jsonl`. Add an offline test that builds the service with `ReplayLLM(tape)` and asserts status, trajectory, plan count, and the exact report. The recording is nondeterministic only at recording time; replay is exact. After editing the planner prompt, the replay raises `CassetteMiss` on the first planner call, the investigation ends `failed` with the miss in its detail, and `misses` holds one key; re-record deliberately when the change is intended and review the diff of the new report.

## Debugging exercises

**D1.** The planner's queries changed: they now include identifiers and abbreviations ("CHG-2026-0907", "seq scans") that do not occur in the incident corpus, so BM25 returns nothing, `no_evidence` fires, the replan writes another over-specific query, and the replan budget runs out. The likely cause is a planner prompt or model change in the release. Confirm by comparing the search-step targets in `plans` across releases, checking that those steps have empty `evidence_ids`, and running counterfactual replay of last week's recorded runs with the new planner to see divergence at the planning call. Fixes: instruct and exemplify keyword queries, normalize queries in the tool (strip ids, expand abbreviations), add hybrid retrieval (Chapter 12), and on empty results try one deterministic broadened query before consulting the planner.

**D2.** The delegate tool returns worker answers wrapped as `[incident_analyst result] ...`, and the variant builds its evidence ledger only from the supervisor's own tool data, which has no `sources`. Metric and deploy ids therefore never enter the ledger, so any citation to them is an `unknown_citation`, and the writer falls back to citing the only bracketed token it sees, the wrapper label, which is also unknown. The event logs show child `ToolResult` events carrying sources that the parent never records. Fix: propagate child evidence through the delegate tool (aggregate `sources` from the child's `ToolResult` events into the delegate's `data`), render the wrapper label outside citation syntax, and require `citations_grounded` in each worker's Definition of Done so worker answers keep their citations.

**D3.** After the approved post executed and its `ToolResult` was written, the process died before the step closed. Recovery resumed the run and called the model again; the model, rereading the transcript, proposed `post_report` once more. The identical-call limit allows a second execution of the same action key by default, the auto-approving callback approved it without a human, and the idempotency key is derived from the run and request ids, so the new request id produced a new key and a second message. Defects: approval scoped to the investigation instead of the specific proposed call; an idempotency key scoped to the request instead of the business operation (investigation plus channel); and no one-shot limit on the external tool (`max_tool_calls=1` or `max_identical_calls=1` for the publish run). The project's `Publisher` avoids all three: a deterministic proposer, a tool-call budget of one, and human approval per call; keying the channel post on the investigation id would add a further safety net.
