# Chapter 33 — Solutions: Fine-Tuning for Engineers

All numbers are illustrative unless they follow from arithmetic in the question.

## Knowledge questions

**K1.** A fine-tune compiles examples into weight changes; it does not store a document you can read back. A weekly policy change would require a new dataset build, a training run, the full evaluation protocol, and a rollout every week, and even then nobody could inspect which policy version the model "believes." Auditability: with retrieval, every answer logs the evidence it used, so you can show which policy text produced it; with weights, the behavior is implicit and unexplainable. Revocability: when a policy is superseded you delete or replace the document and the next request is correct; a weight update cannot be undone except by retraining without the example, and the old behavior may persist in diluted form. Retrieval supplies current, permissioned, citable facts at request time at a cost of some context tokens, which is the right trade for anything that changes weekly.

**K2.** `d_out = 2048`, `d_in = 8192`, full parameters `2048 · 8192 = 16,777,216`. LoRA trains `r · (d_in + d_out) = r · 10,240`. Rank 8: `81,920` parameters, ratio about 205×. Rank 32: `327,680` parameters, ratio about 51×. LoRA does not reduce: the memory for the frozen base weights (the full model is still loaded and run forward and backward), and the memory for activations (proportional to batch tokens and sequence length, needed for the backward pass). Compute per step is also barely reduced, since the forward and backward passes still traverse the whole network.

**K3.** The model should be penalized only for what it is supposed to produce. The system and user turns are inputs; predicting them teaches the model to generate ticket text, spends capacity on the wrong distribution, and dilutes the signal on the short assistant turn (in a classifier the assistant turn is one token, the user turn is hundreds, so an unmasked loss is dominated by predicting tickets). A hand-written trainer that forgets to mask will show low training loss that is mostly "I can predict ticket prose," slower convergence on the label, and a model that sometimes continues the user text instead of answering. With sequence packing, forgetting the attention mask across example boundaries additionally lets one example condition on its neighbor.

**K4.** Accuracy is dominated by frequent classes; macro-F1 weights every class equally. A gap this large means the model is strong on a handful of large classes and poor or collapsed on many small ones, which is exactly the failure a 40-class ticket taxonomy produces when rare categories have few examples. Ask for the per-class table: support, precision, recall, F1 for each of the 40 labels. It will show which classes have near-zero recall, and whether critical categories are among them.

**K5.** DPO removes the separately trained reward model and the on-policy reinforcement learning loop (sampling generations, scoring them, estimating advantages, updating policy and value models). It replaces them with a supervised-style loss over `(prompt, chosen, rejected)` pairs anchored to a reference model. An application team would still not run it because: (a) the data is the hard part, you need a written rubric that produces consistent preferences, which requires rater training and agreement measurement, and preference sets encode verbosity, position, and cultural biases; (b) the result still needs the full regression and safety evaluation of any fine-tune, and preference tuning can shift refusal and tone behavior across every product the model serves; (c) for the judgment-light tasks application teams usually have (classification, extraction, format), SFT with clean data gets the benefit at a fraction of the risk. Providers have the data pipelines and evaluation infrastructure for it; most application teams do not.

**K6.** Exact deduplication hashes normalized text and removes identical rows; it catches the same ticket exported twice or the same template submitted verbatim, which near dedup and entity grouping also catch only if the copies share an entity. Near deduplication embeds texts and removes rows above a similarity threshold; it catches an outage reported by forty users in slightly different words across forty different accounts, which exact hashing misses (texts differ) and entity grouping misses (different entities). Entity-grouped splitting keeps all rows of one account on one side of the split; it catches an account's recurring, distinctively worded problem appearing with different texts in train and test, which both dedup methods miss because the texts are genuinely different but share account-specific vocabulary and patterns.

## Engineering questions

**E1.** Use one shared small base with three LoRA adapters served dynamically if the serving stack supports adapter loading (one deployment, three routable adapter ids), otherwise three merged models (three model ids). Either way there are three logical model ids, one per task, each pointing to a specific adapter version. The registry records, per task version: base model id and revision, adapter artifact hash (or merged weights hash), data card hash and training file hashes, the system prompt and user template version the adapter was trained with, hyperparameters, the evaluation report and ship decision, and the escalation threshold if any. A prompt change on one task is gated by the CI eval gate: a change to the prompt version bound to a fine-tuned route triggers the full evaluation protocol on that task's frozen holdout plus the regression suites of the other two tasks (because they share the base, and because merged-weights deployments may share infrastructure). The change ships behind the flag only if the ship rule passes. Prompt versions and adapter versions are pinned together in the registry entry; deploying one without the other is rejected.

**E2.** Rows become training targets when the agent's final category equals the strong model's label (confirmed) or when the agent overrode it, in which case the agent's label is the target (overrides are the most valuable rows: they are exactly where the teacher was wrong). Drop rows where the ticket was closed without a confirmed category, merged, or reassigned more than once. Sample for human review: all rows from categories with under a few hundred confirmed examples, all conflicting near-duplicate pairs, and a random 1 to 2 percent of the rest; the review sample also yields the kappa measurement. Rare categories: oversample confirmed rows up to a floor per class, collect human labels for the tail, and generate synthetic rows from category definitions only to fill remaining gaps, marked as synthetic, capped at a minority share per class, and excluded from validation and test. Record every policy choice in the data card.

**E3.** Signals: escalation rate (share of predictions below the confidence threshold), agent override rate per category, and label mix divergence from the data card distribution. Thresholds and durations (illustrative): escalation above 20% for two consecutive weeks or override rate above 1.5× its canary baseline for two weeks triggers a scheduled retrain; a taxonomy change (new, merged, or split category) triggers an immediate retrain because the label set is wrong, with the new categories routed to the strong model or humans until then; a PII or safety incident attributable to the model triggers immediate rollback to the previous version, then retrain. A retrain only replaces the model id after a new dataset build with a fresh card, the full protocol (three baselines are not re-run every time, but the strong reference is), a pass of the ship rule including the regression suite, and a canary that matches the strong model's override rate within noise. Enough new data is a precondition: at least a few thousand new confirmed labels with the drift visible in them, otherwise the retrain reproduces the old model.

**E4.** Day 0: confirm from the registry which adapters and model ids depend on the retiring base, which dataset versions and prompts they were trained with, and that the training files and cards are still available. Day 1 to 10: select the successor base, run the prompted small-model baseline on it against each task's frozen holdout to see where it stands before training. Day 10 to 30: rebuild datasets from the current trace export (refreshing labels and the time-split test set), train on the successor, run the full protocol with the ship rule, and compare the composed system against the current production system, not only against the strong reference. Day 30 to 60: canary behind the flag, with rollback to the old base still possible. Day 60 to 80: complete the rollout, update the registry and dashboards' baselines. Buffer until day 90. The plan is routine only if the registry already holds the base id, the training file hashes and the files themselves, the data card, the prompt version, the threshold, the eval report, and the regression suite reference; without those you are reconstructing the project instead of repeating it.

## Practical exercises

**P1.** Expected implementation: `build_dataset` gains an optional `embedding_space: dict | None` argument (or computes it: `{"method": "tfidf"}` when `embed_fn` is None, otherwise the dict from `aie_bridge.embedding_space(client)` plus `"method": "client"`), and `data_card` writes it under `dedup.embedder` together with `near_threshold`. The builder module itself still does not import `aie_core`; the caller passes the provenance it already has. Acceptance: (1) with rows such as "vpn will not connect from home office" and "home office: cannot connect to the vpn" and a vocabulary covering vpn, connect, home, office, `dedupe_near` with `embed_fn_from_client(FakeEmbeddings(vocabulary=...))` removes one row while `tfidf_embed` at the same 0.90 threshold removes none (assert both, so the test documents the difference rather than assuming it); (2) two builds of the same raw data, one per embedder, produce cards whose `dedup.embedder.method` differ and whose `near_removed` counts differ; (3) for a `CachedEmbeddings` client the card's `space_fingerprint` equals `client.space_fingerprint`. A note in the test explains that a bag-of-words vocabulary catches rewordings over known terms, not paraphrases with new words; production uses a semantic embedding client, cached, with its fingerprint recorded so a later rebuild can tell whether dedup ran in the same space.

**P2.** Add to `data_card` a `stratification` section: for each label, `{"train": share, "val": share, "test": share}` as fractions of that split, plus `warnings`: labels with zero rows in test, labels below a configurable train floor (default 50 rows), and labels whose test share differs from train share by more than a factor of two. Acceptance: a test building a corpus where one label has rows in only one entity (so it lands entirely in one split) produces a warning naming that label; a balanced corpus produces no warnings; the warnings appear in `data_card.json`.

**P3.** `memorization_probe(train_rows, predict: Callable[[list[ChatMessage]], str], sample: int, threshold: float) -> ProbeReport` takes a sample of training rows, prompts with the system message and the first half of the user turn, and compares the returned text with the second half of the user turn (and with the assistant turn) using normalized longest-common-substring or TF-IDF cosine. Report the count and share above the threshold and the offending ids. Acceptance: a fake predictor that returns the stored second half for known rows yields a share near 1.0; a fake that returns a constant category id yields 0.0; the report is JSON-serializable for the registry.

**P4.** Implement for example `AltFineTuneProvider` with endpoints `/v2/datasets` (upload), `/v2/tunes` (create), `/v2/tunes/{id}` (status) and statuses `PENDING`, `TRAINING`, `DONE`, `ERROR`, mapped to the chapter's `JobStatus`. Tests use `httpx.MockTransport` and assert the request bodies and the status mapping. Acceptance: `run_fine_tune(AltFineTuneProvider(...), ...)` returns a `FineTuneRecord` with the vendor's model id, the existing tests in `test_ch33.py` are unchanged and still pass, and the only vendor-specific code is inside the adapter class.

## Debugging exercises

**D1.** Root cause: leakage through near-duplicates across the split. An outage storm produces hundreds of near-identical tickets from many accounts; with entity-grouped splitting those land on both sides because they belong to different accounts, and with both dedup counts at zero the near-dedup step either was skipped or ran with a threshold too high to fire. The holdout therefore contained paraphrases of training rows, which inflated macro-F1, and production traffic after the storm does not. The card fields that should have warned: `dedup.near_removed == 0` on a corpus known to contain an outage (implausible), and `split.strategy == "entity"` without a time cutoff, so the test set was not drawn from the future and could not reveal the storm's over-representation. Telemetry that confirms it: override rate concentrated in the storm's category after the storm ended, and offline macro-F1 far above the canary estimate.

**D2.** Root cause: over-training collapsed calibration. Four epochs memorized the training set; confidences moved toward 1.0 on nearly everything, so almost nothing fell below the escalation threshold (escalation 14% to 3%) and the strong model stopped catching the hard cases, which is why overrides rose. Lower training loss and a slightly higher validation macro-F1 are consistent with this: the standalone model got marginally better on average while its confidence stopped meaning anything. The ship rule's `max_ece` check should have blocked the release (ECE would have jumped), and the composed-system evaluation on the holdout with the production threshold would have shown the escalation rate collapsing and the cascade's macro-F1 falling below the reference.

**D3.** Failure: a label artifact learned as the task, here a channel boilerplate footer that was present in every training row and acted as a format anchor (and possibly correlated with specific fields or labels). The check that would have flagged it before training is artifact detection on the training split: footer tokens with very high support and, if the footer varied by category or template, high label purity; even without purity, a token present in nearly 100% of rows is a template to strip. The slice that would have caught it in evaluation is source channel (or "footer present versus absent"), ideally with an adversarial variant of the holdout where the footer is removed. Fix: strip boilerplate in cleaning, add footer-free examples, add the channel slice to the protocol, and retrain.
