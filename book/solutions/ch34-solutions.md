# Chapter 34 — Solutions: Inference and Serving Essentials

All numbers below are illustrative and use the chapter's reference shape (32 layers, 8 KV heads, head dimension 128, 8B parameters) unless an exercise states otherwise.

## Knowledge questions

**K1.** Queue time: arrival at the server until the scheduler starts prefill. TTFT: request send until the first content token, which includes network, queue time, prefill, and the first scheduling step. TPOT (inter-token latency): mean gap between consecutive content tokens after the first. End-to-end: send until the final token including post-processing. Throughput: aggregate output tokens or requests per second across the server. Goodput: throughput counting only requests that met the SLO. An interactive chat product cares most about p95 TTFT, because the pause before anything appears is what users perceive as "slow"; TPOT matters second (streaming pace), and throughput only through cost. A nightly batch classification job cares about goodput, or equivalently cost per completed item within the job's deadline; TTFT and TPOT are irrelevant because nobody is watching a stream, and only total completion time and error rate matter.

**K2.** Each decode step produces one token per sequence but must read the entire weight set (and the sequence's KV cache) from GPU memory. The arithmetic per token is small relative to the bytes moved, so the step time is dominated by memory traffic, not computation. Because the weight read happens once per step regardless of how many sequences are in the batch, adding a second, fourth, or sixteenth sequence adds little time: the weights are already streaming through. Batching during decode therefore multiplies throughput for almost no latency cost until the batch runs out of KV memory or the arithmetic finally becomes the bottleneck.

**K3.** Formula: `kv_bytes = 2 × layers × kv_heads × head_dim × tokens × bytes_per_element`, where 2 covers keys and values, `kv_heads` is the number of key/value heads (not query heads), `head_dim` is the per-head dimension, `tokens` is the sequence length (prompt plus generated), and `bytes_per_element` is 2 for BF16/FP16 or 1 for FP8/INT8. For 48 layers, 8 KV heads, head dimension 128, BF16: per token 2 × 48 × 8 × 128 × 2 = 196,608 bytes (192 KiB). Per 16,384-token sequence: 196,608 × 16,384 = 3,221,225,472 bytes = 3.0 GiB. With an FP8 cache (1 byte per element) both numbers halve: 96 KiB per token, 1.5 GiB per sequence. `kv_cache.kv_bytes_per_sequence(ModelShape(layers=48, kv_heads=8, head_dim=128, params_billion=8), 16384)` returns 3,221,225,472.

**K4.** Static batching groups N requests, runs them together, and returns when the longest finishes; continuous batching admits and retires sequences at decode-step boundaries. LLM requests have highly variable output lengths (and prompt lengths), so under static batching most slots sit idle waiting for the longest sequence, and new arrivals wait for the whole batch. Continuous batching fixes utilization but introduces a scheduling problem: admitting a long prompt into a busy batch runs a large prefill that stalls every active sequence's next decode step, producing TPOT spikes for interactive users. Engines address this with chunked prefill, prefill/decode priorities, and caps on batched tokens, which trade a little throughput for predictable tail latency.

**K5.** Perplexity is an aggregate next-token likelihood over generic text. It can move by a fraction of a percent while behavior on narrow, product-critical tasks regresses badly, because quantization error concentrates in specific layers, channels, or token patterns. Three slices that commonly regress while aggregates look stable: structured output (JSON-schema validity and field accuracy), tool calling (argument formatting and name fidelity), and long-context tasks (faithfulness to evidence far from the question, especially with KV quantization). Multilingual and code slices are also common casualties. The correct test is the release evaluation suite sliced by task family, run on the actual quantized deployment.

**K6.** Little's Law: `L = λ × W`, average requests in the system equals arrival rate times mean time in system; it holds for any stable system regardless of scheduling. Forward: peak arrivals of 6 requests per second with a 4-second mean E2E means about 24 requests in flight, which sized at the p95 sequence gives the KV demand (chapter worked example). Reverse: if a replica can hold 40 sequences in KV memory and mean E2E is 5 seconds, the sustainable arrival rate before queueing is 40 / 5 = 8 requests per second, and the planning figure is lower once headroom is applied. `capacity.in_flight` and `capacity.arrival_rate` implement both directions.

## Engineering questions

**E1.** Both tenants call the same application code and the same `ModelGateway`. The router (Chapter 7) selects a `ServingTarget` list per tenant: for `logistics` the list contains only in-network targets (for example `LOCAL_VLLM` on `inference.internal`), with no hosted fallback; for `retail` it is hosted first and the local engine second, or the reverse if cost dictates. `local_target.envelope_for` computes the request's envelope, `choose_target` picks the first target whose envelope fits, and `make_client` builds an `OpenAICompatibleClient` for that target, with `provider` set to `engine:target`. Each target has its own `ModelGateway`, whose fallback chain holds only interchangeable replicas of that target; moving from the local engine to the hosted endpoint is a router decision, taken only for tenants whose list allows it, so a retryable error on the local engine can never fall through to a hosted endpoint for `logistics`. A policy test asserts that no request carrying `tenant=logistics` ever produces a span with a hosted `provider`. Every trace span must carry tenant, target name, `engine`, model name, engine version, and replica, so a residency audit can be answered from traces alone (Chapter 31). The authorization decision happens before the engine, which is just another `LLMClient` to the application.

**E2.** At 16k tokens a sequence needs 2 GiB of cache; at 64k it needs 8 GiB. With about 55 GiB usable on the illustrative 80 GiB device, maximum concurrency drops from about 27 sequences to about 6, a fourfold cut for every request so that a rare feature can run. (`max_concurrent_sequences(shape, 65536, 80 * GiB).max_sequences` returns 6.) Alternatives: (1) route the long-document feature to a separate pool or replica configured for 64k, or to a hosted long-context endpoint, keeping the main pool at 16k; (2) change the feature so it does not need 64k resident at once: chunk the document and summarize or retrieve over it (Chapters 5 and 12), or use a map-reduce over sections. A third option is to accept 64k only with admission control that reserves cache for a small quota of long requests, but that still costs the main pool capacity whenever the quota is in use.

**E3.** Prefix caching requires an identical token prefix. A `request_id` on the first line makes every request's prefix unique from token one, so the 2,000-token system prompt is prefilled from scratch on every call. TTFT impact: prefill cost is roughly proportional to prompt tokens, so prefill work per request goes from about 300 tokens (user message only, system prompt cached) to about 2,300 tokens, nearly an eightfold increase in prefill time, which at a busy replica also increases queue time for everyone else. Fix: keep the system prompt byte-stable and move per-request identifiers to the end of the prompt (after retrieved evidence, right before or inside the user turn), or better, carry them out of band in the request `metadata` and trace attributes, where the engine never sees them. Add a CI check in the prompt registry (Chapter 4) that the first N tokens of the system prompt are unchanged across versions intended to share a cache.

**E4.** TPOT is flat and KV utilization is only 60 percent, so neither decode speed nor cache is the limit; queue depth rising with TTFT means requests are waiting to be admitted or to be prefilled. With the prompt mix of a RAG endpoint, this is the prefill constraint: aggregate prompt tokens per second exceed what the replica can prefill while keeping TTFT under 2 seconds. In `replicas_needed` terms, `prefill_bound_replicas` is the largest. The fix is more replicas (data parallelism), fewer prompt tokens (compaction, tighter evidence packing, prefix caching for the shared system prompt), chunked prefill to keep interactive requests from waiting behind long ones, or a separate pool for long prompts. Quantizing the KV cache does not help because cache was not full; it reduces memory, not prefill compute, and the binding resource here is compute during prefill, not bytes of cache.

## Practical exercises

**P1.** Expected implementation: add `metrics_url: str | None` to `LoadTestConfig`; after each level, `GET` the metrics endpoint, parse the Prometheus text format for a configurable set of metric names (for example running sequences, waiting sequences, KV-cache usage fraction), and attach them to `LevelSummary` as `engine_metrics: dict[str, float]`. `format_report` prints the chosen columns. `FakeServer` gains a `/metrics` route that reports its current `active`, a waiting count derived from `active - capacity`, and a KV fraction `active / capacity`, in Prometheus text format. Acceptance: tests run offline; at a concurrency above the fake's capacity the recorded waiting count is positive and the KV fraction is at or above 1.0; at concurrency 1 both are zero; the report contains the new columns; an unreachable metrics endpoint is recorded as an error field, not an exception.

**P2.** Expected implementation: `sweep` results are serialized with `LevelSummary.model_dump_json`; `plot_sweep.py` reads the JSON list and uses matplotlib (optional dependency) to produce two figures: (a) x = requests per second, y = TTFT with two lines for p50 and p95 and a horizontal SLO line; (b) x = p95 E2E, y = output tokens per second, with a vertical SLO line. The operating point found by `find_operating_point` is marked on both plots. Acceptance: running the script on the sample JSON from the fake-server sweep in the chapter produces both PNGs; a test renders to a non-interactive backend and asserts the files exist and are non-empty; the script exits non-zero with a clear message if no level met the SLO.

**P3.** Expected implementation: `admit(free_kv_bytes, input_tokens, max_tokens, shape, queue_wait_s, max_queue_wait_s) -> Decision` where `Decision` is an enum `ADMIT | QUEUE | REJECT` with a `reason`. Required tokens are `input_tokens + max_tokens`; required bytes come from `kv_bytes_per_sequence`. Admit if required bytes fit in `free_kv_bytes`; queue if they do not fit now but would fit in an empty replica and the caller's queue wait is below the bound; reject with a retryable reason if the request can never fit (longer than the replica's maximum) or the queue bound is exceeded. Acceptance: a property-style test feeds a random sequence of mixed-length requests against a fixed budget, tracking admitted bytes, and asserts that the sum of admitted bytes never exceeds the budget; a request larger than the whole budget is rejected immediately; a request that fits only after others complete is queued, then admitted when the budget frees; rejections carry a `retry_after_s` hint.

**P4.** Expected deliverable: a one-page comparison with the full configuration record (model and weights identifier, quantization, engine and version, hardware, scheduler settings, sampling parameters, prompt and output distributions), two sweep tables, both operating points with goodput, and a quality table with per-slice deltas (at minimum schema validity and field accuracy on a small structured-output set). Acceptance criteria: both runs used the same prompt file, SLOs, and warm-up; the operating point is reported as the highest concurrency with zero errors and both p95s under SLO; the conclusion states explicitly whether the quantized variant's goodput gain is accepted or rejected given the quality deltas, and which slice drove the decision. The result will differ by hardware; the grading is on protocol discipline, not on which variant won.

## Debugging exercises

**D1.** Root cause: the engine upgrade disabled or broke prefix caching (a changed default, a new cache key that includes a field that now varies, or a tokenizer change that altered the shared prefix's token IDs). TTFT doubled because every request prefills the full system prompt again; TPOT, errors, utilization, and traffic are unchanged because decode is untouched and the GPU absorbs the extra prefill at the cost of latency. Prompt registry and input token counts rule out a prompt change. The confirming metric is the engine's prefix-cache hit ratio (or cached-prompt-tokens counter), which will have dropped to near zero at the deployment timestamp. Secondary confirmation: `Usage.cached_input_tokens` in traces fell to zero while `input_tokens` stayed constant.

**D2.** The replicas are KV-bound. The cache is full (99 percent), so new requests wait for blocks and the scheduler preempts running sequences to make room, then recomputes or swaps them back in; the preemption counter climbing is the signature. Output tokens per second is high because the GPU is doing a lot of decode work, including work it later discards or repeats, and GPU utilization at 85 percent looks healthy; neither number measures queue time, which is what users experience as "hangs before answering." Goodput, not throughput, would have shown the problem. Immediate change: lower the engine's maximum batched sequences or maximum model length, or enable admission control on KV budget so excess requests are rejected fast with a retryable error and the gateway queues or sheds them (Chapter 29), restoring TTFT for the admitted ones. Structural change: add replicas sized from the KV constraint in `replicas_needed`, reduce per-request context (compaction, tighter evidence packing), switch to FP8 KV cache after the quality suite passes, or move long-context traffic to its own pool. Alert on KV utilization and preemptions as leading indicators rather than on utilization.

**D3.** Zombie generations: clients disconnected, but the engine never learned of the cancellation and kept decoding until `max_tokens`, holding KV blocks for sequences nobody is reading. Forty running sequences versus a handful of gateway connections is the mismatch. The responsible layer is almost always the proxy or gateway between client and engine: it keeps the upstream connection alive after the downstream closes (buffering, missing cancellation propagation, or a client library that does not close the stream on task cancellation in the agent loop). Overnight traffic with large `max_tokens` and abandoned agent steps filled the cache. The test that should have caught it: open N streams, close them early, and assert that the engine's running-sequence and KV-utilization metrics return to baseline within a bounded time; and a gateway test that an upstream request is cancelled when the downstream client disconnects. Remediation also includes conservative `max_tokens` defaults and server-side idle timeouts.
