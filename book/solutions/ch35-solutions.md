# Chapter 35 — Solutions

All prices and rates are the chapter's illustrative inputs (2 / 8 / 0.2 USD per million input / output / cached tokens for a capable model; one tenth for a small model). Where an exercise asks for a design, the solution gives a model-answer outline and the criteria a strong answer must hit; it is not the only acceptable design.

## Knowledge questions

**K1.** Correctness is the property the evaluation set (step 8) measures and the property every later component is tuned toward; without it, step 2 selects components by habit and step 8 has nothing to score. Consequences per case: knowledge assistant without "supported by a citable chunk the user may read" ends up tuned for fluent answers and ships hallucinated or forbidden citations; support copilot without "no account fact outside the tool result" optimizes draft acceptance and ships confident wrong balances; document processing without "per field, critical fields weighted" reports a document-level accuracy that hides wrong totals; coding assistant without a deterministic Definition of Done becomes a code generator whose PR descriptions claim tests passed.

**K2.** Little's Law: average number in the system L equals arrival rate λ times average time in system W. 12 rps × 7 s = 84 requests in flight on average. A gateway capped at 64 concurrent calls will queue about 20 requests at steady state, and every queued request adds its wait to W, which raises L further; near saturation this feedback produces the tail-latency knee. Either raise the limit to about 84 × 1.5 ≈ 126 with headroom, cut W (shorter outputs, streaming does not help here, faster model), or shed load before the queue.

**K3.** Tenant omitted: a `retail` user receives an answer built from `logistics` documents, a cross-tenant leak. Group set omitted: a user without `hr` gets an answer cached by someone with `hr`, so the ACL filter is bypassed through the cache even though retrieval was correct. Index version omitted: after a re-embedding or document update, stale answers citing old chunk ids or old policy text are served until TTL. Prompt version omitted: a prompt change (new abstention rule, new citation format) does not take effect for cached questions, so evaluation and production diverge and a rollback appears not to work.

**K4.** Chapter 17's criteria: is the action sequence known in advance, does each step have deterministic inputs and outputs, is the number of steps bounded, and does correctness depend on observing intermediate results. Document processing: the graph (classify, extract text, split, extract fields, validate, route) is identical for every document, bounded, and each step is independently testable, so a workflow with model calls inside two steps is strictly better: fewer steps, replayable, cheaper. Coding assistant: which files to read, how many edit-test-repair cycles, and whether to stop depend on observations the model makes along the way (test output, search results); the path cannot be written down per task, so a loop is required, but its termination is still deterministic (Definition of Done, budgets).

**K5.** Endpointing (VAD plus end-of-turn decision) is most often the real bottleneck: a conservative 800 ms silence window alone consumes most of a one-second budget, and it sits before any model work can start on a final transcript. Model TTFT is one additive term among seven; cutting it from 400 ms to 200 ms saves 200 ms, while the total without overlap is about 1,200 ms. Reaching one second requires overlapping stages (start the model on a stable partial for read-only intents, stream text into TTS by sentence) and tuning endpointing, not a faster model.

**K6.** Model cost for invoices is about 15 USD per day on the cascade; human review at 15 percent is 1,200 reviews × 2 minutes = 40 hours × 30 USD = 1,200 USD per day, roughly eighty times the model cost, so any token-price optimization is noise against review rate. Dropping to 10 percent: 800 reviews × 2 min = 26.7 hours = 800 USD per day, a saving of 400 USD per day (about 100,000 USD over 250 working days), equal to 5 points × 80 USD per point.

**K7.** (1) A finalized transcript to confirm writes against and to separate partials from finals, which is what gates side-effecting tools; (2) a point to redact PII before logging and trace export; (3) per-stage latency spans (endpointing, recognition, model, synthesis) that tell you which stage to tune. Also acceptable: an auditable record of what was said, and the freedom to pick a domain-tuned recognizer or a different text model. A speech-to-speech design must obtain a transcript of both sides (from the model or a parallel STT stream) and gate writes on its finalized form plus an explicit confirmation turn; keep tool execution in its own orchestrator behind the same policy, approval, and idempotency rules rather than letting the integrated session execute actions; run redaction on that transcript before anything is logged; record what the caller actually heard on barge-in; and instrument the session's own events (speech start and end, first audio, tool call) so latency can still be attributed. A strong answer adds that built-in turn detection must be measured against the endpointing requirement, not assumed.

## Engineering questions

**E1.** Steps that change: 1 (a side effect and a new correctness clause: a ticket is created only with fields the employee confirmed), 2 (tool layer and approval UI added to the diagram; the request path now has a confirmation turn), 3 (a tool-capable model for the drafting step or a separate intent classifier), 5 (new tool table row: reversible write, scoped to the employee's own identity, approval bound to category/summary/priority, idempotency key per conversation turn, 2 s timeout, machine-readable errors), 7 (injection in a retrieved runbook can now target an action; mitigation: approval on every write, tool results as data, no free-form arguments), 8 (gold cases for tool selection, argument correctness, confirmation adherence, and injected-document-attempts-ticket adversarial cases), 10 (new rows: duplicate ticket after timeout, ticket on wrong behalf, approval replay). Security table gains: injection-to-action, confused-deputy (ticket for another user), argument tampering between confirmation and execution. Failure table gains: duplicate ticket (detect by idempotency collisions), approval shown for different arguments than executed (detect by hashing arguments at approval and execution), tool outage (detect by error rate; degraded mode: offer the ticketing portal link).

**E2.** Causes: (a) the prompt prefix order changed so the per-turn content (latest message, retrieved evidence) now precedes the stable system and account block; telemetry: cached-token fraction drops uniformly across all conversations immediately at deploy time, prompt version field changes. (b) Account context is re-fetched and re-rendered each turn with a volatile field (timestamp, random ordering of open orders); telemetry: cache misses correlate with account-context hash changing between consecutive turns of the same conversation. (c) Traffic shift to one-turn conversations where there is no second turn to hit the cache; telemetry: turns-per-conversation distribution, cache misses concentrated in first turns, no change in prompt version. Cost: cached fraction 50 percent gave 603 USD per day; at 10 percent, cached tokens = 41.8 million and uncached = 375.8 million: 375.8 × 2 + 41.8 × 0.2 + 144 = 751.7 + 8.4 + 144 ≈ 904 USD per day, a 300 USD per day regression. Caching had saved 979 − 603 = 376 USD per day, so about 80 percent of the saving is gone, and cost per six-turn conversation rises from about 0.05 to 0.075 USD, close to the 0.10 ceiling.

**E3.** 12 extra chunks × 400 tokens = 4,800 extra input tokens per question; 6,000 × 4,800 = 28.8 million extra input tokens per day, more than doubling input (27 to 55.8 million). Cost: 28.8 × 2 = 57.6 USD per day extra, from 68.4 to 126 USD per day (0.021 per question). Latency: prefill roughly doubles, threatening the 2 s TTFT budget. Required metric before accepting: recall@8 versus recall@20 after rerank on the gold set, and answer correctness and groundedness at 20 (more distractors often lower groundedness, Chapter 13). Alternative first: fix recall where it is lost (recall@50 after fusion versus recall@8 after rerank tells you whether retrieval or ranking is at fault), improve the reranker or candidate pool, use parent-child retrieval to include a section when a paragraph matches, and only then widen the evidence budget.

**E4.** Indexes: a symbol index (definitions, references, call graph) rebuilt incrementally per commit; a trigram or lexical index over code and tests sharded by top-level package; an optional semantic index over function-level chunks with docstrings for "where is X handled" questions, built asynchronously and never required for a task to start; a repository map (packages, owners, build and test commands per package). Tools: `find_symbol`, `find_references`, `search_code` with a package scope parameter, `read_file` with mandatory ranges, `list_tests_for(path)`, and `run_tests` scoped to the affected package by default with the full suite only at the final verification. Working-set policy: cap around 40,000 tokens, pin the task and the repo map, evict by least recent reference, keep a compact "visited" list of paths with one-line notes so eviction does not cause re-reading, and compact history while preserving paths, line numbers, test failures, and decisions. Evaluation: file-localization recall (did the working set contain the files the human fix touched) measured per task before and after the change, steps spent searching, token spend per step, and task success on the historical suite; a separate "needle" suite of 50 tasks whose relevant code lives far from the obvious package.

## Practical exercises

Acceptance is judged on the worksheet being complete (ten rows, no empty cells), the diagram showing the trust boundary and the sync/async split, step-9 arithmetic reproducible with `back_of_envelope.py`, and a failure table whose rows each name a detection signal.

**P1. HR onboarding assistant.** Model answer outline: requirements include new hires in their first 30 days, correctness as "policy answers cited from current HR documents; form pre-fill values match the HR system; sessions scheduled only on confirmation"; tools `lookup_hr_record` (read, scoped to the new hire's own record), `prefill_form` (reversible write to a draft, no approval), `schedule_training` (external calendar write, confirmation bound to session id, date, and attendee, idempotency key = hire id + course id), `notify_manager` (external communication, approval). Retrieval over HR documents with `hr` and `all` ACLs; memory is the onboarding checklist state per hire, deleted at 90 days. Scaling: for example 40 new hires per week × 30 questions and 8 forms each; cost per new hire computed as tokens plus any human HR time saved or added. Degraded mode when the scheduling system is down: show available sessions from a cached snapshot, queue the booking with a pending status, and never claim it is booked. Strong answers: classify every tool's side effect; bind confirmation to arguments; notice that form pre-fill from HR data must not pass through a shared cache; include an adversarial case where a policy document contains injected instructions to schedule a session.

**P2. Voice at 3,000 calls per hour.** Concurrency: 3,000 / 3,600 × 360 s = 300 concurrent calls, so 300 audio, STT, and TTS streams and a model turn rate of 300 / 12 = 25 turns/s. Latency table must total at or under 1,200 ms p95 with named overlaps, for example VAD 150 (adaptive), STT final 150 overlapped with model start on stable partial for read-only intents, model TTFT 350 at p95 with a reserved capacity pool, TTS first audio 150 with sentence streaming, network 150, orchestrator 50: serial sum 1,000 ms, with STT/LLM overlap saving another 100 to 150 ms. Barge-in path: VAD speech-onset event cancels TTS within 200 ms, sends cancellation to the in-flight model stream, and records the last played sentence boundary in call state. Required rule: no tool with a side-effect class of write or external communication may be invoked from a partial transcript; writes require a finalized transcript and a separate confirmation turn. Strong answers also size the handoff queue (what fraction of 300 concurrent calls can be waiting for 60 humans) and compute speech cost per minute as the dominant line.

**P3. Contract-renewal alerting.** Pipeline adds two critical fields (renewal date, notice period) and a derived deadline; evaluation is field-level with these two weighted highest, plus date-normalization correctness and evidence-location correctness, sliced by contract family and language. Notification design: deterministic scheduler computes deadline minus 60 days, idempotency key = contract id + schema version + deadline date, so re-extraction with the same result sends nothing and a changed date sends exactly one corrected alert with a reason. Fine-tuning decision with numbers: for each of the two largest families, state current review rate and error attribution by stage; justify fine-tuning only if errors are model behavior on a stable layout, the family volume makes the review-hour saving exceed the project cost within a year (reuse the chapter's 80 USD per review-point-per-2,000-documents scale), and hold-out is by counterparty and template. A strong answer includes the "do not" case: a family failing on OCR should get a vision path, not a fine-tune.

**P4. Fix-the-failing-build mode.** Definition of Done as deterministic checks: the failing CI job's tests pass locally in the sandbox; the full affected-package suite passes; lint and type checks pass; diff touches no forbidden paths (CI configuration, dependency lockfiles unless the failure is a dependency, secrets, deployment manifests); diff under N lines; a PR exists with the runtime's test log attached. Budgets: for example 40 steps, 1.5 million tokens, 20 minutes, 1.50 USD, with the task pausing for a human at any budget. Evaluation suite: historical CI failures with the commit that fixed them and the test that went green, including at least 20 cases where the correct action is to stop (flaky test, infrastructure outage, failure caused by a dependency outage) and report rather than patch. Strong answers treat "make the test pass by deleting or skipping it" as an explicit forbidden-change rule enforced by a diff check, not by prompt wording.

## Debugging exercises

**D1.** Stage: reranking (recall@50 after fusion normal, recall@8 after rerank collapsed). Root cause candidates: (a) the reranker model or its tokenizer changed under you (hosted reranker updated, or a local model file replaced by an ops job) so scores shifted; confirm by the reranker version attribute in spans, score distribution shift over the week, and re-running the gold set against the pinned previous version. (b) Candidate text fed to the reranker changed: a chunker or ingestion change (truncation, missing title context, encoding issue) altered the chunk text while ids stayed the same, so dense recall@50 still finds them but the reranker scores the degraded text low; confirm by comparing chunk content hashes between index versions and by checking the index version attribute on traces. "Nothing was deployed" refers to the application; the index and the reranker are deployments too.

**D2.** Compare timestamps: the orchestrator's decision span that invoked `create_ticket`, the STT partial events before it, and the final event. If the decision timestamp precedes the final transcript's timestamp for that turn, the tool was called from a partial. Check the confirmation turn the same way: the confirmation detection may have matched a partial "yes" that was later finalized as "yes, but don't cancel." Code paths: the orchestrator's gating that decides whether a turn's transcript is final before dispatching write tools, and the confirmation parser that should require a finalized transcript and an exact match on the rendered confirmation fields. The fix is a code guard (tool dispatch rejects non-final turns for write-class tools), plus an adversarial gold case where a partial reverses meaning.

**D3.** The cached-input-token fraction per step. Cost per task is dominated by input tokens; with steps and output flat, the only term that can double cost is the share of input billed at full price rather than cached price. Daily cost is 900 × (1 − f) × 2 + 900 × f × 0.2 + 144 = 1,944 − 1,620 f USD for a cached fraction f; at f = 0.8 that is 648 USD (0.54 per task), and doubling to 1,296 USD (1.08 per task) means f fell to about 0.4. A fully uncached prefix would triple the cost to 1.62 per task. Mechanism: the prefix cache only hits when the leading tokens of consecutive requests are identical; anything volatile placed early in the prompt invalidates the whole prefix every step. Most common context-builder change: inserting per-step content (timestamp, step counter, latest tool result, or re-sorted working set) before the stable system prompt and repository summary, or reordering the working set on every step. Confirm with the gateway's cached tokens per request over time and the prompt version attribute; fix by restoring the stable-prefix-first layout.
