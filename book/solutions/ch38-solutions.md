# Chapter 38 — Solutions

## Knowledge questions

**K1.** The key's job is to make a retry of the same logical action recognizable as a retry. After a crash, the recovering process must produce the same key as the process that died, and the only information both share is the event log. agentkit derives `"<run_id>:<request_id>"`, where the request id is fixed by the `ToolCallRequested` event, so the key is identical before and after recovery. A key generated at execution time (`uuid4()` per attempt) differs on every attempt: the external system sees two unrelated requests and performs the action twice, the local ledger has no record under the new key, and reconciliation has nothing to look up.

**K2.** (1) Before the request leaves: the ledger record is `in_progress`, the external system has nothing; reconciliation finds nothing and the call executes. (2) After the external commit, before the response is read: ledger `in_progress`, the external object exists; only the external system knows, so the harness must ask it (lookup by key) or rely on its key-based deduplication. (3) After the response is read and the ledger is marked `succeeded`, before the `ToolResult` event is appended: the ledger holds the output, so the harness returns it without calling anything. (4) After the `ToolResult` event: the log itself shows the call is done; resume never re-executes it. A fifth moment, before the ledger reservation, is equivalent to case 1 without a ledger record.

**K3.** A lease says who should own the run until a time, but the owner cannot observe that its lease expired while it was paused (GC pause, partition, suspended VM). Without fencing, a worker that wakes after its lease was reassigned keeps writing events and calling tools, so two workers drive one run. A fence token increases with every ownership change and is checked in the same transaction as each write, so the stale owner's first write fails (`LeaseLost`) and it stops before acting further.

**K4.** An approval gate exists because a human must consent to a risky action. If silence turned into approval, the gate would become a delay, and the actions most likely to go unanswered (overnight, holidays, ambiguous requests) would be executed by default. Expiry as denial fails safe: the agent sees a denial, explains what was not done, and a human can restart the work. Waiting time does not count against the run-time budget because that budget limits computation (steps, tokens, active time) to stop runaway loops; a run waiting a day for approval consumed none of it. Business deadlines are enforced separately, by interrupt expiry and timers.

**K5.** Progressive disclosure loads skill content in three levels: the catalog (name and description of every skill) is always in context; the body of a skill is loaded only when the task matches; resources inside a skill are loaded only when the procedure asks for them. The permanent context cost is the catalog, not the sum of all procedures. The description is what selection matches against, whether the selector is a keyword ranker, an embedding search, or the model reading the catalog; a skill with a perfect body and a vague description is never loaded, or is loaded for the wrong tasks.

**K6.** The next turn's reasoning is based on the history. If the history contains the planned reply, the agent believes the caller heard content they never heard: it may assume a question was asked ("would you like me to change the address?") and interpret the caller's next words as an answer to it, or skip information it thinks was already delivered. Recording only the heard prefix plus an interruption marker keeps the agent's model of the conversation equal to the caller's.

## Engineering questions

**E1.** Put an internal payments service between the agent and the provider and make that service own the key. The refund tool sends `ctx.idempotency_key` to the service. The service writes an outbox row (key, order id, amount, status `intent`) in its own database in the same transaction that accepts the request, then calls the provider, then records the provider's refund id. If the provider has any free-text field that is returned by its search or reporting API (a merchant reference, a description, metadata), embed the key there so it becomes searchable. Reconciliation then queries the provider for refunds on that order within the time window and matches on the embedded key; if no field is available, match on (order id, amount, time window) and treat ambiguous matches (zero is clear, one with the same amount is likely, two or more is ambiguous) as unknown. Unknown outcomes create a human task in the payments team's queue and stop the agent run; the outbox row records the operator's resolution. Acceptance criteria: a crash injected after the provider call produces exactly one refund across 100 repetitions, and every ambiguous match produces a human task, never a second call.

**E2.** Allow package installation only inside the task sandbox, only from an internal mirror (network egress allow-listed to the mirror, nothing else), with pinned versions and hashes. Installing packages already present in the lockfile is automatic. Adding a new dependency or changing a version is a tool call (`add_dependency(name, version, reason)`) that requires approval from a code owner, because it changes the supply chain and runs install scripts. Install scripts run with the same CPU, memory, time, and filesystem limits as tests, never with credentials. The Definition of Done adds: lockfile consistent with the manifest, no unapproved new dependencies (diff the lockfile against the baseline), license and vulnerability checks pass for new packages, and the tests pass in a clean environment built from the lockfile, not in the environment the agent mutated.

**E3.** Two workable designs. (a) Short lease, about 30 s, with a heartbeat: the worker renews every 10 s from a background thread, using the same fenced conditional update as appends, including during long tool calls. A crashed worker's runs are recovered within about 30 s; a paused worker loses the lease after 30 s and its next write fails. (b) Long lease of more than four minutes with no heartbeat: simpler, but recovery after a crash takes up to five minutes and a stuck worker blocks its runs that long. Prefer (a). For rolling deploys, handle SIGTERM: stop starting new steps, let the current step finish if it fits in the grace period (set the pod's termination grace period above the slowest tool, or make long tools resumable), append the step's events, and release leases explicitly so another pod resumes immediately instead of after expiry. Duplicate execution is impossible in either design as long as side-effecting tools are wrapped with reconciliation and every write is fenced; the lease choice affects recovery time, not correctness.

**E4.** Steps (activities): every model call, every tool call (wrapped as today, with the idempotency key passed to the external system), every read of configuration that can change (tool set, policy table, prompt version), and any blob write to object storage. Workflow function: the loop itself, budget accounting, policy and authorization checks over validated values, routing, and the Definition of Done's decision over recorded check results; it uses the engine's clock and derives request ids from the step counter, never `uuid4()` or `time.time()`. Replacements: the engine's history replaces the SQLite event store, its dispatch and heartbeat timeouts replace `LeaseManager` and fencing, durable timers replace the timer table, and signals (persisted if they arrive early) replace the inbox. `ReconcilingTool` still matters: a tool step that died mid-call is retried by the engine, so the external system must still deduplicate on the key or be asked by lookup, and the "neither" case must still stop for a human. Approval policy (owner chain, escalation, expiry as denial) is rebuilt as a signal plus timers and stays your code. Deploying a new policy check while runs are paused: wrap it in the engine's versioning marker so histories recorded before the change replay the old path, or route old runs to workers on the old build until they drain; test it by replaying a recorded pre-change history against the new code. Silent breakages, any two of: (1) a `uuid4()` or wall-clock read in the workflow function, which makes recovered runs diverge from their history days later; (2) an unversioned change to the loop, which fails only when a paused run resumes; (3) full prompts and tool outputs stored as step payloads, which hit payload or history limits on long runs (store blobs by reference and use continue-as-new with the ledger); (4) relying on engine retries for side effects without an external key, which duplicates tickets exactly as an unwrapped tool would.

## Practical exercises

**P1.** Implementation: `reopen(run_id, request_id, outcome: ToolOutput, operator: str)` verifies that the run is `stopped` with `fatal_error`, that its last `ToolResult` for `request_id` is the unknown-outcome failure, and that the operator is authorized. It writes the true outcome to the ledger with `complete(key, ...)`, acquires the lease, and appends events through the fenced store: `Resumed(by="operator", note=...)` and a `Note(kind="outcome_reconciled", to_model=True, text="An operator confirmed: <outcome content>")` so the model sees the corrected observation. Then it calls `runtime.resume(run_id)`, which treats the run as interrupted and continues. Because agentkit refuses to resume non-budget stops, append the `Resumed` event before calling `resume`, so the derived status is `running`. Acceptance tests: an unknown-outcome run reopened with "ticket TCK-1000 exists" completes without calling the tool again; reopening a completed or budget-stopped run is refused; a non-operator is refused; the operator's identity appears in the log.

**P2.** Implementation: add `approvals_required: int = 1` to `EscalationPolicy` and a `votes` JSON column (or table) to interrupts. `decide(approve=True)` records a vote if the decider is on the chain up to the current level and has not voted yet; the interrupt resolves only when the count of distinct approvers reaches the requirement. Any rejection resolves immediately as a denial. Escalation adds eligible deciders but keeps existing votes; expiry denies regardless of partial votes. Acceptance tests: one approval leaves the run paused; the same person approving twice does not count twice; a second distinct approver resumes the run and the tool executes once; a rejection after one approval denies; expiry with one vote denies; an approver who is not on the chain is refused.

**P3.** Implementation: a `Summarizer` protocol with an `aie_core`-backed implementation that sends old tool results in batches with an instruction to summarize in one line each and to copy identifiers verbatim; run `LITERAL` extraction on the original content and append any literal that the summary omitted, so recall of identifiers never drops below the extractive baseline. Use `FakeLLM` with a scripted summary in tests. The evaluation runs a scripted 30-step investigation whose final answer must cite identifiers seen at steps 3, 9, and 17; compute identifier recall (identifiers in the final answer that appear in the last compacted request) and tokens per request for both digests. Acceptance criteria: both variants keep every request under budget and keep tool-call pairing valid; the summarizer variant's recall is at least the extractive variant's; the report shows tokens saved and summarizer cost.

**P4.** Implementation: `run_linter()` runs a linter (for example `python -m pyflakes` or `ruff` if available) in the sandbox on a copy of the workspace and returns findings as `path:line: code message`. Compute the baseline once at workspace creation by running the linter on the baseline snapshot; store findings as a set of `(path, code, normalized message)` without line numbers, since edits shift lines. The new check `no_new_lint` runs the linter on the current snapshot and fails if the set difference is non-empty, listing the new findings. Acceptance tests: a seeded pre-existing unused import does not fail the check; a patch that adds an unused import fails it with the finding named; a patch that fixes the pre-existing finding passes.

## Debugging exercises

**D1.** Root cause: the outcome ledger is not shared or not durable. The most common form is `SQLiteIdempotencyStore()` with the default `":memory:"` path or a file on the pod's local disk. The worker that recovers the run after a rollout has an empty ledger, so `begin` returns None, and `ReconcilingTool` never sees the `in_progress` record. It executes the tool again without asking the ticketing system. The forty-second gap is the lease TTL plus the recovery loop interval. Leases and fencing work, which is why there are no `LeaseLost` errors: the old pod is really dead. Confirming telemetry: the reconciliation log or span attributes for recovered runs show a fresh execution, not `reconciled_found` or `reconciled_absent`. Both tickets carry the same `client_ref`, which proves the key was stable and the ledger was the missing piece. The ledger's configured path differs per pod. Fix: put the ledger in the shared database, add a startup check that refuses in-memory ledgers outside tests, and add an integration test that recovers on a second process with a fresh ledger object.

**D2.** Root cause: the identifier was lost during compaction and the model reconstructed it from memory, transposing digits. The step-6 observation contained more literals than the digest's cap of eight, and `INC-2213` came after the cap, so it was not kept. With `keep_recent_steps=1`, the raw observation was gone from every request after step 14. The ledger never recorded the incident as a fact, and the Definition of Done did not check identifiers against observations. Telemetry: the compaction statistics show the drop to one kept step. Comparing the final answer's identifiers with the last compacted request shows `INC-2231` in neither the request nor the log. `INC-2213` is in the log at step 6 but absent from every request after step 14. Fixes: (1) a verifier that rejects answers containing identifiers absent from the log's observations, like `citations_grounded` applied to the full log; (2) prioritize literals by later use or raise the cap, and prompt the agent to write key identifiers into the ledger's facts. A third fix is to keep two recent steps and fall back to shorter digests before dropping steps.

**D3.** Root cause: the refactor merged expiry handling into the timer path, or changed its call, so expired approvals now go through `_resolve_and_resume` with the default `status=RESOLVED` and `approve=True`. The evidence is `decided_by = "clock"` on interrupts whose kind is `approval` and whose status is `resolved`, not `expired`. The run logs show `ToolCallApproved` followed by `send_reply` results at night, and no `ToolCallDenied` with reason expired. The test that catches it is the chapter's `test_unanswered_approval_expires_as_a_denial`. It advances the clock past expiry, runs `tick()`, and asserts three things: the interrupt status is `expired`, the resumed run contains a `ToolCallDenied` whose reason mentions expiry, and nothing was sent. Add a production alert on any approval-kind interrupt resolved by `clock` with `approved: true`.
