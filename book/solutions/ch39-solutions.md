# Chapter 39 solutions — Capstone: Northwind Assist

## Knowledge questions

**K1.** `prepare` decides admission, the spend reservation and the degraded plan before any byte of the response is written, so a rejection can be a real HTTP status: `503` for replica overload (our problem), `429` for tenant quota or budget (the caller's problem), both with `Retry-After`. If the rejection were an `error` event inside a `200` stream, three things go wrong. Clients, load balancers and SDK retry logic see a success and do not back off, so overload is amplified instead of shed. Metrics built on status codes report the outage as healthy traffic. And the rejected request has already opened a long-lived streaming connection, consuming exactly the capacity admission control exists to protect.

**K2.** Approval is enforced by toolkit: the executor's policy returns `needs_approval` for `send_reply`, the `ApprovalManager` stores the normalized arguments and their hash, and only `execute_approved` runs the stored arguments after a lead's decision, re-verifying the hash and consuming the approval. guardrails' `ToolPolicyCheck` with `requires_approval=True` (what `support_tool_rules()` does unless called with `require_send_approval=False`, as the capstone does) would demand an approval *token* in `GuardContext.approvals` that matches the call; no component mints such tokens in this design, so every proposal would be blocked at the guardrail and toolkit would never create the approval request. The lead's inbox would be empty and no reply could ever be sent. Two independent approval mechanisms with different identities for "the same action" is not defense in depth, it is a deadlock.

**K3.** The bug writes `tenant="shared"` and `acl_groups=["all"]` into the indexed chunks. The pipeline's final check uses `visible(chunk, principal)`, which reads the chunk's own metadata, so a corrupted chunk looks visible to everyone and no violation is recorded. The check that catches it compares retrieved documents against the source of truth: `KnowledgeBase.doc_visible` reads the source document's ACL, and ragkit's `no_permission_leak` metric, the `forbidden-doc` critical rule and the canary probes in the security suite use it. In production the equivalent is a trace query that joins retrieval hits to the document registry, not to the index.

**K4.** The retrieval cache stores chunk ids per (query, tenant, ACL scope, index version, retriever configuration); hits are re-hydrated from the live chunk table and re-checked against the principal, so deletions and permission changes win over the cache. The answer cache stores generated text per (question, tenant, ACL scope, prompt version, index version, model, plan level); a cached answer is replayed as is, so a document deleted after caching can still be quoted until the index version changes or the tenant is purged. The retrieval cache is therefore safe to keep on; the answer cache sits behind a flag whose safe variant is off, is purged on deletion, and only stores clean, fully validated answers.

**K5.** The input guardrail replaces e-mail addresses with vault tokens before the model sees the text, so the model's correct proposal contains a token. Validating that proposal against a strict e-mail pattern would reject every correct send; the model-facing schema (`guardrails.token_tolerant_schema`) accepts either form. The real address appears only after re-hydration inside the tool boundary (`guard_tool_call` with `rehydrate_kinds("email")`, limited to the arguments the rule names), where toolkit validates it against the original schema, the policy checks the recipient allowlist, and the guardrail checks outbound content. Re-hydrating only there means the model never handles the raw value (it is not in prompts or provider logs), and an address the model invents, or a token copied from another user's conversation, cannot be turned into a real recipient, because the vault is scoped to one tenant and one session and leaves unknown tokens untouched.

**K6.** `attack_detected` is the share of attack cases where some guard flagged the attempt (an input or context injection score, a blocked tool call, a rejected memory write). It is reported because detection rates are useful for tuning and alerting, and not gated because the system's safety must not depend on detection: the controls are authorization, approvals, allowlists and the write policy, which hold however the attack is phrased. Gating on detection would push the team toward ever more aggressive heuristics, raising false positives on legitimate text (Chapter 27's false-positive rate) while giving attackers a target to evade, and it would reward blocking over building controls that make the attack harmless.

## Engineering questions

**E1.** In order: (1) source metadata and the loader: documents carry `acl_groups` for the new departments; ragkit already refuses documents without ACLs, so add fixtures and a loader test. (2) Identity: the IdP emits the department groups in the `groups` claim; add a token test. (3) Retrieval: no code change, because both indexes filter on groups, but add department documents to the cross-tenant test and principal variants for a finance and a non-finance employee to the dataset (the variant derivation computes expectations from metadata). (4) Caches: the ACL scope hash already includes groups; add a key test with a department group. (5) Memory and tools: nothing department-specific unless tools expose department data, in which case add policy rules. (6) Guardrails context and output: unchanged. (7) Gate: add a `principal:finance` slice and keep `no_permission_leak` must-pass-all. (8) Dashboards: the cross-tenant query becomes a cross-scope query on groups. Each step's test is in place before the next step starts, so a failure points at one change.

**E2.** Earning the discount requires a byte-stable prefix: the grounded-answer system prompt and the evidence notes must come first and be identical across requests, and per-request content (evidence, question) last. ragkit's request already puts the system prompt first; the capstone would keep the `meta`-only fields out of the prefix and sort evidence deterministically. The gateway must pass the provider's cache hint where required and record `cached_input_tokens` from the provider's usage. `PricingTable` already prices cached input separately (`cached_input_per_1m`), so `UsageMeter` and the ledger pick the saving up automatically; to show it, add `cached_input_tokens` and an `avoided_cost_usd` column computed as the uncached price minus the charged price, and report the prefix-cache ratio per tenant (Chapter 30's `prompt_cache_ratio`). Double counting is avoided by keeping charged cost and avoided cost in separate columns and never adding them.

**E3.** Run the candidate model on a 5 percent arm assigned by user id through the flag evaluator (stable buckets), with the manifest fingerprint distinguishing arms in traces. Compare per arm on interactive traffic only (exclude synthetic and eval traffic by `traffic.source`): abstention rate, withheld-sentence rate, thumbs-down rate, guardrail block rate, citation validity on sampled answers scored by the calibrated judge, p95 time to first delta and completion, error rate, and cost per successful answer. Before the canary, the offline gate must pass with the candidate model and Chapter 32's sample-size calculation must show the canary can detect the minimum effect that matters in the planned window. Roll back automatically if any safety metric moves (leak query non-empty, block rate up, approvals for off-allowlist recipients), if error rate or p95 breach the SLO for 10 minutes, or if the quality metrics' paired difference is significantly worse; promote manually otherwise.

**E4.** For, narrowly. A templated resolution notice to the ticket's own requester carries little risk if three things hold: the recipient is not chosen by the model (it is the requester stored on the ticket, looked up by the tool), the body is a fixed template with at most the ticket id and status interpolated (no free text from the model), and the ticket is actually resolved in the system of record. Implement it as a separate tool (`send_resolution_notice`, side effect `external`, no approval) rather than relaxing `send_reply`, with policy rules: recipient must equal the ticket requester, template id from an allowlist, one notice per ticket per day (idempotency key on ticket id and status), and a rate limit per tenant. Evidence required first: a trajectory suite where every attempt to put model text into the notice fails, red-team cases with injected ticket bodies trying to change the recipient, and a shadow period where the tool logs what it would send and humans review a sample.

## Practical exercises

**P1. Durable approvals.** Expected implementation: a capstone `ApprovalStore` port with two adapters (toolkit's in-memory manager for tests, Chapter 38's `InterruptManager` on SQLite for production). When `ToolLayer.note_output` sees `pending_approval`, it records an interrupt with the tool name, normalized arguments, argument hash, requester context (user, tenant, groups, scopes, session), expiry (15 minutes) and escalation policy (second lead after 10 minutes). `GET /v1/approvals` reads pending interrupts for the tenant; approve verifies the approver's scope and four-eyes, then executes the stored arguments through `executor.execute` with the stored requester context and an idempotency key derived from the interrupt id, and marks the interrupt resolved in the same transaction as the idempotency record. Acceptance: restart test (create pending approval, rebuild the container on the same SQLite file, approve, outbox has one message); expiry test with an injected clock (approve after 16 minutes is refused, outbox empty); escalation test (after 10 minutes the item lists the second lead as assignee); argument-tamper and cross-tenant tests unchanged and passing.

**P2. Real-provider integration suite.** Expected implementation: `tests/integration/` with `pytestmark = pytest.mark.integration` and a skip unless `LLM_PROVIDER` is not `fake` and credentials are present. Tests run one grounded question with a known answer, one agent action against the synthetic ticket store, and one extraction; assertions are structural (status, citations resolve to packed evidence, the expected document is cited, tool trajectory within budget, schema-valid extraction), never exact text. An eval run writes a report next to the offline reference and a comparison of metrics, latency per stage from real spans (`llm.complete` time to first token, retrieval, rerank) and cost per case. Acceptance: skipped in default CI; with credentials, all pass twice in a row (flakiness check); the report shows non-zero real latency and cost and the gate passes or fails with an explained difference.

**P3. Intent classifier with a baseline.** Expected implementation: a labeled dataset (200 messages, workflow labels, split by user to avoid leakage), a classifier (a small model with a structured-output prompt via the Chapter 4 registry, or an embedding nearest-neighbor classifier as in Chapter 8), and a router that consults it first and falls back to the rules below a confidence threshold chosen on a validation split with Chapter 24's threshold sweep, using a cost matrix in which routing a question to a side-effecting workflow is expensive. The decision, confidence and fallback flag go into `meta.intent_rule` and the `router.decide` span. Acceptance: macro-F1 on the held-out split at least 5 points above the rules; zero cases on the held-out split where a below-threshold prediction routed to an action workflow; latency added per request reported; a regression test that the rules alone still serve when the classifier errors.

**P4. Calibrated online judge.** Expected implementation: a sampler in the API that writes 1 percent of `done` events (request id, evidence chunk ids, answer) to a queue; an evaluation worker that loads the packed evidence by chunk id, runs ragkit's `FaithfulnessJudge` (a groundedness judge) with a separate model, and emits an `eval.score` span with `response.id`; a human-labeled sample of 50 answers; `evalkit.calibrate_judge` producing agreement and kappa per judge version, stored with the judge's prompt version. Acceptance: the calibration report exists per judge version; a configuration guard refuses to use a judge with kappa below 0.6 in any gate; the dashboard shows groundedness by version fingerprint with confidence intervals; sampled content follows the capture policy (hashed by default, redacted on sampled traces).

**P5. Compose end to end.** Expected implementation: `docker compose up -d`, `docker compose run --rm sync`, wait until Project 3's status endpoint shows the queue drained and all documents active, then an HTTP-mode eval target that calls `POST /v1/chat?stream=false` with tokens minted for the eval principals (hs256 dev mode in the Compose environment) and maps the response to `RagOutput` (citations carry chunk ids; retrieval hits come from a debug field enabled only in test environments, or the target accepts answer-only metrics). A deletion test calls the admin delete endpoint and polls until the document no longer appears in answers, measuring the freshness lag. Acceptance: same gate passes over HTTP; deletion visible within `RAG_FRESHNESS_SLO_S`; the collector shows one trace per chat request and separate traces for worker jobs with their own spans; restarting the worker mid-sync loses no job.

## Debugging exercises

**D1.** Spend fell and quality fell together while breakers are closed, and most requests run at degrade level 1: the reduced plan (smaller k, no reranker, shorter answers) is being applied broadly. With breakers closed, the remaining inputs are admission load, the spend guard and operator switches. The deploy is the change, so the likely cause is configuration: a lowered `NA_TENANT_DAILY_BUDGET_USD` for retail (for example a unit mix-up, 2.5 instead of 25) puts every request past the soft limit, so the spend guard answers `degrade`. Confirm with `meta.degrade_reasons` (or the root span's degrade attributes): `spend:soft_limit` rather than `admission:1` or `operator:1`, and with `/v1/cost/daily`, where retail `utilization` is above 0.8 early in the day. Fix the configuration, and add a config validation rule that a tenant budget below the trailing seven-day average spend fails the deploy.

**D2.** The proposal-time hash is computed on re-hydrated arguments: when the original request ran, `guard_tool_call` (inside the capstone's `GuardedTool`) turned the model's `<PII:email:...>` token into the real address using that request's vault, and the approval stored those arguments and their hash. The execution-time hash differs, so execution did not use the stored arguments. The most likely path is that approval was implemented, or customized, as "re-run the agent and call `send_reply` with `approval_id`" in a *new* request: the new request has a new vault, cannot re-hydrate the old token, so the arguments contain the token and hash differently, and the executor correctly answers `approval_mismatch`. The audit trail shows two `tool.proposed` events with different hashes for the same approval id. The fix is to execute approvals only through `execute_approved` with the stored arguments, and to keep the vault scoped to the session (not the request) if conversations legitimately span several requests.

**D3.** The server produces the first sentence early (provider TTFT 0.9 s) but the client sees it at 7.8 s, close to the end of the request at 8.1 s, with no errors. Two causes fit. First, a buffering hop between server and client: an ingress or proxy with response buffering on, or a compression middleware that buffers small chunks, delivers the whole stream at the end. This shows as server-side `delta` emission timestamps (span events or logs per event id) early in the request while the client's first-byte time equals completion; check the `X-Accel-Buffering` and `Content-Encoding` headers at the client and the ingress annotations. Second, the validator withholds the early sentences (citation style mismatch) and the first sentence that passes comes near the end; this shows on the server as well: `notice` events with `withheld` before the first `delta`, and `answer.withheld` greater than zero on `llm.generate` spans, with the first `delta` event's server timestamp late. The first is a deployment fix; the second is a prompt or model behavior issue, and the withheld-rate panel should have shown it.
