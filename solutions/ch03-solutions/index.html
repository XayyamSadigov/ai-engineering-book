    Chapter 3 — Solutions¶

    Knowledge questions¶

    K1. The provider validates that every tool message answers a tool call that appears in the immediately preceding assistant turn. The assistant message with tool_calls is that turn: it carries the ids the results reference and the model's own text, which the next generation step conditions on. Omitting it produces an invalid request (an InvalidRequestError, typically a 400 complaining about an unmatched tool_call_id) in the OpenAI dialect, and in the Anthropic dialect a tool_result block with no matching tool_use block. Even on a lenient server, dropping the assistant turn deletes the model's reasoning about why it called the tool, which degrades the final answer.

    K2. Where it lives: the exact-match response cache lives in your process or your Redis; provider prompt caching lives inside the provider's inference stack. Key: the response cache is keyed by a hash of the whole request (model, messages, tools, schema, temperature, max tokens, stop); prompt caching is keyed by an exact prefix of the token sequence the provider has recently computed. What it saves: the response cache saves the entire call, so latency is near zero and cost is zero on a hit (the gateway records the price it would have paid as avoided_cost_usd, separate from cost_usd); prompt caching saves part of the prefill compute, so the call still happens, output tokens are still generated and billed, and cached input tokens are billed at a reduced rate. The response cache is only safe for deterministic requests; prompt caching is always safe because the output is still freshly generated.

    K3. At most three attempts, by max_attempts. It may make fewer because of the deadline. After attempt one the delay is uniform in [0, 0.5]; after attempt two it is uniform in [0, 1.0]. The gateway checks _fits(delay, deadline) before sleeping: if elapsed time plus the drawn delay reaches two seconds, it stops retrying that client and moves to the next one (or gives up with a TimeoutError whose cause is the last 503). Since each attempt also consumes real time at the provider, a slow 503 (say 1.2 seconds) plus a drawn delay of 0.9 would already exceed the deadline after attempt two.

    K4. Fallback is triggered by the retryable classes: RateLimitError, TimeoutError, and ProviderUnavailableError. These describe the provider's state, so another provider may well succeed. InvalidRequestError describes your request; another provider will reject it too, or worse, accept something you did not mean. ContentFilterError is a policy decision about the content; routing around it is both futile and a governance problem. MalformedResponseError is excluded because the HTTP call succeeded and the problem is the generated content; the right remedy is the structured-output repair loop (re-ask with the error), not a transport retry or a different vendor, and a retry at the gateway level would hide the fact that the model is producing unusable output.

    K5. A text fragment is useful on its own: a reader can start reading, and concatenation is lossless. A tool-call argument fragment is a slice of a JSON string that cannot be parsed, validated against the tool's schema, or authorized until the closing brace arrives; emitting it would push every consumer to implement incremental JSON parsing and defer validation. Nothing useful can be done with half a tool call, so the adapter buffers fragments per call index and emits one complete, parsed ToolCall when the stream closes the call. The cost is that tool execution cannot begin until the call is fully described, which for millisecond tools is negligible.

    K6. Streaming reduces the user's perceived wait: the time until text first appears on screen. Without streaming, that wait equals the whole generation time; with streaming it drops to roughly the server-side time to first token (TTFT), which governs whether the interface feels responsive. Server-side TTFT itself (queueing plus prefill, Chapter 2) is unchanged; only prompt size and load move it. Total completion time (TTFT plus time per output token times output length) governs how long until the answer is complete and usable, and, for structured outputs, when parsing can start; streaming does not change it either, and max_tokens is the lever that bounds it. Northwind's targets separate the two server-side numbers for exactly this reason: p95 TTFT under two seconds, which is the user's perceived wait only because answers are streamed, and p95 completion under eight.

    K7. Empty answers: a reasoning model generates hidden thinking tokens before the visible answer, and on most APIs those count against max_tokens. On harder tickets the thinking alone uses up the 150-token budget, so generation stops with finish_reason length before any visible token is produced; Completion.truncated is true, and complete_structured raises TruncatedOutputError rather than repairing. Bill: thinking tokens are billed as output tokens at the output rate, which is typically several times the input rate, so each request now pays for hundreds of invisible output tokens; the price per token is not the right comparison, cost per completed task is. The spans show it as a jump and a long tail in output_tokens with unchanged visible answer length. Fixes: raise max_tokens to cover thinking plus answer (measured from the output_tokens distribution, for example its p99), and use the provider's reasoning-effort or thinking-budget setting to cap thinking for a task this simple; or route the classifier back to a non-reasoning model if the evaluation set shows no accuracy gain, which is the usual outcome for short classification. Add an alert on the length share so the next model change cannot reintroduce the problem silently.

    Engineering questions¶

    E1. Bug: the cache key is a hash of the request content. If two tenants send identical prompts (same system prompt, same question) and permission is enforced in the tool layer rather than reflected in the prompt, the second tenant receives the first tenant's cached completion, including any tool calls or data the first tenant's request legitimately produced. That is a cross-tenant leak, which violates the zero-leakage target.

    Fix A, identity in the key: set metadata["cache_scope"] to the tenant (and the user id where personalization matters) on every request; it is the one metadata field the gateway's cache_key includes. Construct the shared gateway with require_cache_scope=True so a request that arrives without a scope is never cached. Simple, no prompt changes, keeps hit rates within a tenant. Cost: the scope must be set by the request-handling layer from the authenticated identity, never from model or user input, and hit rates drop roughly by the number of scopes. A test sends two identical requests with different scopes and asserts two provider calls.

    Fix B, identity in the prompt: put the tenant and permission scope into the system prompt (Tenant: retail. Allowed tools: ...). The existing key now differs automatically. Cost: the system prompt is no longer a stable shared prefix across tenants, so provider prompt-cache hit rates fall, and permission text in the prompt is advisory to the model, so the tool layer must still enforce it.

    Tradeoff: A is the engineering fix (explicit, testable, no prompt coupling); B also gives the model useful context but spends prompt-cache efficiency and tempts people to treat the prompt as the enforcement point. Most systems do A, and add B only where the model needs to know the tenant to answer well.

    E2. Illustrative numbers; the method matters. Suppose the provider allows 500 requests per minute and 400,000 tokens per minute, and each ticket is about 600 input tokens with a 100-token structured answer.

    • Rate limiter: RateLimiter(requests_per_minute=450, tokens_per_minute=360_000), about ten percent under the published limits, because the token estimate counts the full max_tokens and other services may share the key. Set max_tokens=150 so the estimate (600 + 150) is tight; the token bucket then admits about 480 requests per minute, so the request bucket is the binding constraint.
    • Concurrency: with a two-second typical latency, 450 requests per minute needs about 15 in flight; max_concurrency=24 leaves headroom for tail latency without flooding.
    • Cache: enable the exact-match cache. Tickets repeat (automated alerts, duplicate submissions) and temperature is zero; a hit rate of even ten percent is five thousand free calls.
    • Retries: RetryPolicy(max_attempts=4, base_delay_s=1.0, max_delay_s=30.0, jitter=True). A batch job can afford longer backoff; the limiter already prevents self-inflicted 429s.
    • Timeout: timeout_s=60 per ticket; a nightly job prefers completing over being fast.
    • Fallback: a second model on the same provider or a second provider, but only after running the evaluation set against it, because classification labels drift between models.
    • Alternative: if the provider has a batch API, submit the whole night's work there at the discount and skip the limiter entirely; keep the gateway path for the daytime trickle.

    E3. Implement stream as a thin emulation over complete: call complete, then yield one text_delta with the whole text, one tool_call_delta per tool call, a usage event, and done with the real finish reason. This satisfies the protocol and keeps callers working. Do not lie about latency: do not chunk the text and sleep between chunks to fake typing, because TTFT would then be total latency plus artificial delay, and the span would misrepresent the provider. Set a class attribute such as supports_streaming = False so that UIs can choose to show a spinner instead of a cursor, and record stream=False on the span even when called through stream. The done event should carry the finish reason exactly as complete would have returned it; usage should carry the real usage so cost accounting is unchanged.

    E4. Key: the embedding of a normalized form of the request (system prompt version id, tool set hash, and the user text), stored alongside the exact-match hash so exact hits still short-circuit. Threshold policy: a cosine similarity threshold per task class, not global; classification and FAQ-style questions tolerate a higher threshold than open questions, and any request with tools or a response schema should require an exact match on the schema and tool set plus the similarity threshold on text. Invalidation: flush on prompt version change, model change, or embedding model change; TTL by task; and never serve a semantic hit across tenants. Evaluation before enabling: take a sample of production request pairs that would have been served as hits at the candidate threshold, generate fresh answers for the second request, and have a judge (Chapter 24) grade whether the cached answer would have been acceptable; plot the false-hit rate against the threshold, pick the threshold where false hits are below your tolerance, and measure the resulting hit rate to see whether the saving justifies the new failure mode.

    Practical exercises¶

    P1. IdempotentGateway. Expected implementation: a wrapper holding inner: LLMClient, a lock, a dict of completed results keyed by idempotency key, and a dict of in-flight threading.Event (or asyncio.Future) objects. complete reads req.metadata.get("idempotency_key"); with no key it delegates. With a key, under the lock it returns a stored result, or if another call is in flight waits on its event and then returns the stored result, or otherwise registers itself as in flight, releases the lock, calls inner.complete, stores the result, and sets the event. Failures must also be stored (or the in-flight marker cleared) so waiters do not hang. Acceptance: eight threads calling with the same key against a FakeLLM produce exactly one entry in fake.requests and eight identical completions; a scripted ProviderUnavailableError on the first call does not deadlock the waiters; different keys produce different calls; an optional TTL evicts completed entries.

    P2. Streaming tool loop. Expected implementation: a loop with a step limit; each iteration calls client.stream(req), prints text deltas as they arrive, collects tool_call_delta events, and on done appends an assistant Message reconstructed from the text and tool calls (use collect_stream). If there are tool calls, execute each against a dict of callables, append Message.tool(call.id, json.dumps(result)), and continue; otherwise return. Script FakeLLM(handler=...) so the first request (no tool results in messages) returns a lookup_employee call, the second (which contains a tool message) returns search_tickets, and the third returns final text. Acceptance: three requests recorded; the second request's last two messages are the assistant turn with the tool call and the tool result with the matching id; the loop stops on the step limit when the handler always returns a tool call; a ContentFilterError from the stream propagates rather than being retried.

    P3. RedisResponseCache. Expected implementation: a class with get/set matching the ResponseCache protocol, serializing with completion.model_dump_json() and Completion.model_validate_json, using SET key value EX ttl when a TTL is given. Provide a FakeRedis with get, set(ex=...), and a manual clock so TTL expiry is testable. Acceptance: a parametrized test runs the same gateway scenarios (hit, miss, TTL expiry, no caching at temperature 0.8) against InMemoryResponseCache and RedisResponseCache(FakeRedis()) and both pass; a serialization round trip preserves usage, tool_calls, and raw; the gateway's cache_hit annotation is true on the second call with either cache.

    P4. PrefixStabilityCheck. Expected implementation: a helper assert_stable_prefix(render, min_bytes) that renders the prompt for two requests with different user content and asserts rendered_a[:min_bytes] == rendered_b[:min_bytes], reporting the first differing offset and a few bytes of context on failure. Apply it to a Northwind system prompt that opens with Today is {date}; the test fails with the offset pointing at the date. Fix by moving the date (and anything else volatile, such as the user's name or tenant) after the stable instructions and tool definitions, or into the first user message. Acceptance: the test fails on the original prompt and passes on the fixed one; a second test asserts the prompt still contains the date somewhere so the fix did not simply delete it.

    Debugging exercises¶

    D1. Candidate causes and the evidence for each:

    1. The request's timeout_s is not reaching the gateway. A middle layer builds a new CompletionRequest and drops the field, so the gateway uses its 60-second default. Confirm: the first attempt's span should carry the request timeout; log attempt_req.timeout_s or check the HTTP request's read timeout, which would show 60 instead of 10.
    2. Retry-After hints are large and the deadline check is being bypassed. The 429s carry retry-after: 15, and the policy honors the hint. The gateway's _fits should refuse a 15-second sleep against a 10-second budget, so if sleeps happened, either the budget was 60 (cause 1) or a custom RetryPolicy subclass overrode delay_for without the deadline check. Confirm: the retry_after_s attribute on the recorded exceptions and the gaps between span start times (about 15 seconds apart would match the hint).
    3. The rate limiter is sleeping outside the deadline check. A limiter constructed with the real sleep but without passing deadline (a custom admission wrapper) can block indefinitely before the span even opens. Confirm: queue_ms on the spans; a large queue_ms on attempt one points at the limiter, not at retries.
    4. Provider A is slow to return 429. Each 429 took several seconds; three attempts plus two backoffs add up. Confirm: latency_ms on the error spans (should be near zero for a real 429) versus span duration.

    The single most informative attribute is the first span's effective timeout; the second is the gap between consecutive span start times.

    D2. The deploy made the system prompt's leading bytes volatile. Typical culprits: a timestamp or date inserted at the top (Today is 2026-...), a request or session id, the user's name, or reordering so that a per-request section (retrieved documents, user profile) now precedes the shared instructions. Provider prompt caching keys on an exact token prefix; a byte that changes per request breaks the prefix for every call, so cached_input_tokens collapses and every input token is billed at the full rate. Thirty-five percent is consistent with a long system prompt and tool list that previously hit the cache on most requests. The test that would have caught it is the prefix-stability check from P4 (render the prompt twice with different user content and assert the first N bytes are identical), run in CI on every prompt change, plus an alert on the cached_input_tokens / input_tokens ratio in production.

    D3. The symptoms exclude the obvious causes: finish_reason="stop" with low output_tokens means the provider believes it finished, not that it hit max_tokens, and no error events means the adapter did not see a stream error. The gateway span is ok, so the semaphore and relay completed normally. Two places remain. First, upstream of the gateway: the application's own SSE or WebSocket layer to the browser may be dropping the final chunks when the client's buffer flushes late, or an intermediate proxy buffers and truncates streams at a size or time boundary; in that case the gateway saw the whole answer and the user did not. Second, downstream: a stop sequence in the request (stop=[...]) that the model legitimately hits mid-sentence, for example a stop string like \n\n or ### that also appears in normal prose; the provider reports stop and a short answer, which is exactly this signature at a low rate.

    Experiments: (1) Compare the text reconstructed from the gateway's events (log collect_stream output, or the final text length, on the span) with what the browser rendered for an affected request; if they match, the truncation is in generation (check the stop list); if the gateway has more text than the browser, the loss is in your delivery path or a proxy. (2) Replay the affected request's messages with the same stop list against complete instead of stream; if the answer is truncated identically, it is the stop sequence, and removing or tightening the stop list fixes it.
