    Chapter 6 — Solutions: Structured Output and Extraction¶

    Identifiers match the exercises in book/chapters/06-structured-output-and-extraction.md.

    Knowledge questions¶

    K1. Example one: {"total": "3237.48", ...} for an invoice that prints 3,327.48. It is a valid decimal in a valid object. The business-rule gate catches it (TOTAL_MISMATCH, because subtotal plus tax no longer equals the total), and the grounding gate catches it independently (EVIDENCE_VALUE_MISMATCH, because the quoted line does not contain 3,237.48). Example two: {"po_number": null} for an invoice without a purchase order, or {"invoice_date": "2027-01-14"} for an invoice issued in 2026. Both are schema-valid. The business-rule gate catches them (MISSING_PO, DATE_IN_FUTURE). Other acceptable answers: a currency code the schema allows but the vendor never bills in (reference check against the vendor master), or a well-formed PO number that belongs to another vendor (reference check against purchasing).

    K2. Provider schema modes: strict structured-output modes commonly require every property to be listed as required and reject optional properties; "required, nullable" is the shape that is accepted everywhere. Evaluation: a missing key is ambiguous (did the model forget, or did it judge the field absent?), while an explicit null is an assertion that can be scored as a correct abstention or a false negative. A third, behavioral reason is also valid: forcing the model to emit every key makes it consider every field instead of silently skipping one.

    K3. A schema re-ask fixes the shape of the answer: the validator's message names a missing key, a wrong type, or invalid JSON, and the model resends the object. A targeted rule repair addresses content: the object is well-formed, but the values violate a business invariant, so the model is asked to re-read the document. The rule-repair prompt forbids balancing the numbers because the cheapest way for a model to satisfy "the total must equal subtotal plus tax" is to change one number, which converts a detectable inconsistency (either a misread or a vendor error) into a fabricated value that passes every arithmetic check. Keeping printed values and quoting them preserves the signal; a real vendor error then reaches a person, as it should.

    K4. You need labeled validation data and, at minimum, the accuracy of the documents the threshold would accept: among documents with confidence at least 0.9, what fraction are fully correct on critical fields? Better, build a reliability table (bins of score versus observed accuracy) on held-out data, and choose the threshold for a target precision with choose_threshold, reporting the coverage it costs. Expected calibration error summarizes the reliability table as the count-weighted average absolute gap between the mean score and the observed accuracy in each bin; zero means scores can be read as probabilities.

    K5. A wrong value makes two separate mistakes: it asserts something false (a false positive, which hurts precision) and it fails to produce the true value (a false negative, which hurts recall). A missing value asserts nothing, so it cannot be a false positive; it only misses the truth. Counting this way keeps precision honest about the cost of confident wrong answers, which are worse for downstream systems than blanks.

    K6. The classifier can abstain (the other document type, or confidence below EXTRACT_CLASSIFY_THRESHOLD); the ticket schema can abstain on category (other, which raises CATEGORY_ABSTAINED); and routing can abstain at the document level (score below EXTRACT_ACCEPT_THRESHOLD, or remaining error violations). An infrastructure failure, such as a provider outage or a rate limit that outlasts the retries, says nothing about the document. Sending it to review would create human work that a later retry would make unnecessary, and a provider outage would flood the queue. The service returns HTTP 503 (or 502 when the provider error is not retryable) or a batch error entry with a retryable flag instead.

    K7. Recalibration learns a monotone map from the raw score to observed accuracy on a validation split, so it changes what the number means: after it, a 0.9 should be right about 90% of the time. Because the map is monotone, it does not reorder documents, so for a single accept-or-review decision it does not change which documents can be accepted; the same accepted set is reachable with a threshold on the raw score, and choose_threshold finds it directly for a target precision. It is worth doing when the number itself is consumed: shown to reviewers as a probability, combined with other scores, compared across model versions, or used for expected-cost calculations. It must be fit on a split separate from the one used to report results, and refit when the model, prompt, or document mix changes. For the sample size, the rule of three gives a 95% upper bound of about 3/n on the error rate when n accepted documents show zero errors, so 3/n < 0.005 requires n of about 600 error-free accepted documents, and more if any error is observed.

    Engineering questions¶

    E1. Wire schema ContractDraft: counterparty: str | None, effective_date: str | None (as written), term_months: Number | None, renewal_type: Literal["auto", "manual", "none", "unclear"], renewal_date: str | None, notice_period_days: Number | None, notice_period_text: str | None (the clause verbatim, because "ninety days before the end of the then-current term" must be interpreted by code or a person), liability_cap_amount: Number | None, liability_cap_currency: str | None, liability_cap_text: str | None, and evidence: list[ContractEvidence] where each item has field, quote, page: int, confidence. The domain model holds date, Decimal, a currency enum, an integer notice period, and evidence spans with page and character offsets computed by code within that page. Evidence must carry the page because offsets into an 80-page concatenation are useless to a reviewer and because quotes repeat across pages (definitions sections). Splitting: parse to pages with layout-aware extraction (Chapter 11), classify pages or sections by heading (term and renewal, liability, notices), and run one extraction call per relevant section with a section-specific sub-schema, each well below the output limit. Merge per field with explicit conflict rules (a later amendment overrides the main body; two different caps go to review). Treat finish_reason == "length" as a hard error per section.

    E2. Month-end batch: a provider batch API if available, because the work is not interactive, a turnaround of hours is acceptable before payment runs, the discount applies to every call, and the batch does not compete with interactive traffic for rate limits. Confirm with: batch turnaround guarantees versus the payment deadline, the discount on your account, whether the batch path supports your structured-output mode, and how repairs are handled (they become a second, smaller batch). Otherwise run online with bounded concurrency sized by Little's law against the tokens-per-minute limit. The single-receipt upload page: online calls, because the user is waiting. Confirm with: p95 latency of classify plus extract plus a possible repair against the page's latency budget (skip classification, since the form already says "receipt"), and whether a job-id-and-poll pattern is needed for the repair tail.

    E3. Must change: a DocumentType.CREDIT_NOTE value; a CreditNoteDraft wire schema and CreditNote domain model (possibly sharing line-item types with invoices, with a required original_invoice_number reference); a process_credit_note function with its rules (the total is negative or the document says "credit", the referenced invoice exists, the credited amount does not exceed the original); a system prompt; a DocTypeSpec registered in SPECS; the classifier prompt's description of types; the API's _DOMAIN_MODEL map for validating corrections; a gold set and evaluator comparators for the new fields; and the review UI's knowledge of the type. Must not change: ExtractionService, routing (decide), the repair loop, metering, the review-queue port and adapters, and the invoice rules, except that NON_POSITIVE_TOTAL keeps sending negative "invoices" to review because a credit note misclassified as an invoice is exactly what that rule exists to catch.

    E4. Build two variants of InvoiceDraft that differ only in field order: values then evidence (current) versus per-field objects {quote, value, confidence} with the quote first. Keep model, prompt text, temperature, and normalization identical. Run both over the same gold set with held-out templates, at least a few hundred documents, with repeated runs if sampling is nonzero. Metrics: per-field exact match and F1, critical-field accuracy, evidence-location correctness, false-accept and review rates after routing, output tokens and latency per document. Slices: format, vendor, document length, and fields that need disambiguation (total versus subtotal versus previous balance). Switch if interleaving improves critical-field accuracy or lowers false accepts by more than run-to-run noise (use the paired comparison and confidence intervals from Chapter 24) at an acceptable cost in output tokens; keep the flat shape if differences are within noise, because it is simpler to validate and evaluate.

    Practical exercises¶

    P1. Expected implementation: a PurchaseOrderDirectory protocol in application/ports.py with get(po_number) -> PurchaseOrder | None (fields po_number, vendor_name, currency, open_amount); an InMemoryPurchaseOrderDirectory in adapters/ loaded from a small JSONL fixture; ProcessContext gains an optional directory; a pure rule check_po_reference(invoice, po) in domain/rules.py returning PO_NOT_FOUND (error, not repairable when the extracted PO is grounded in the text) or PO_VENDOR_MISMATCH (error, not repairable), and optionally PO_CURRENCY_MISMATCH; process_invoice looks up the PO when present and appends the result. Acceptance criteria: tests show a valid PO accepts, an unknown PO routes to review with PO_NOT_FOUND without a repair call, and a PO belonging to another vendor routes with PO_VENDOR_MISMATCH; the domain layer still has no I/O (the lookup happens in the application layer and the rule receives the looked-up record).

    P2. Expected implementation: complete_structured hides finish_reason, so the service calls the client for the extraction step through a small wrapper that inspects each completion (or the metered client records the last finish_reason per task). When the last extraction completion has finish_reason == "length", the service retries once with max_tokens doubled up to a configured ceiling, and on a second truncation returns human_review with reason TRUNCATED and a violation describing the limit. Acceptance criteria: a test scripts a Completion with finish_reason="length" and partial JSON, then a valid draft, and asserts acceptance with exactly one enlarged retry and no schema re-ask; a second test scripts two truncations and asserts TRUNCATED without further calls; the extract.llm span records truncated=True.

    P3. Expected implementation: RoutingPolicy gains field_thresholds: dict[str, float] with a default for unlisted fields; decide receives the field-score map and lists every critical field below its threshold as LOW_CONFIDENCE:<field>. run_eval collects, for rule-clean documents, (field_score, field_correct) pairs per critical field and calls choose_threshold per field with a target precision per field (for example stricter for total). Thresholds are written to a JSON file that AppSettings loads. Acceptance criteria: unit tests for decide with mixed field scores; an evaluation test where one field is perturbed in the replay data shows its threshold rising while others stay; fitting and reporting use different splits.

    P4. Expected implementation: a ProcessedDocumentStore port with get(key) and put(key, result); key = sha256(document_id + "\n" + normalized text); in-memory and SQLite adapters, the SQLite one with a unique key constraint and INSERT ... ON CONFLICT DO NOTHING. ExtractionService.extract checks the store first and returns the stored result (marking it replayed=True), and stores results after routing; the review item is created in the same unit of work as the store write so a crash cannot leave one without the other. Acceptance criteria: submitting the same batch twice makes model calls only the first time and leaves exactly one review item per inconsistent document; a document with the same id but changed text is processed again.

    Debugging exercises¶

    D1. Root cause: the new model reformats quoted dates into a different style instead of copying them verbatim. The values are right, but locate cannot find the quotes, so EVIDENCE_NOT_FOUND fires on invoice_date, the field scores drop to zero, and documents route to review. Nothing in the code changed; a dependency's behavior did. The right fix has two parts: strengthen the instruction that quotes are verbatim copies (and add an example), and re-run the evaluation set before accepting the model version; do not loosen locate to accept semantically equivalent dates, because that would turn the grounding check into a second parser that can be fooled. What would have caught it: pinning the model version and running run_eval as a release gate for model updates (Chapter 25), with an alert on the per-code violation rate and on evidence-location correctness. Telemetry that reveals it: the violation-code distribution by field and the review rate, both sliced by model version recorded on the gateway's spans.

    D2. Root cause: currency is a critical field that Project 1 cannot ground for this vendor. The documents print only $, normalization maps a bare $ to the configured EXTRACT_DOLLAR_MEANS (USD), and value_supported_by_quote deliberately skips currency, so the grounding check does not object, the rules are all arithmetic and pass, and the score is high. The design gap is that an ambiguous symbol was resolved by a global default instead of by a fact about the vendor. Fix without the model: a reference check against the vendor master (exercise P1's pattern), so each vendor's billing currency comes from the system of record; a $-only document whose vendor bills in CAD becomes CURRENCY_REFERENCE_MISMATCH or is normalized to CAD with a recorded reason, and a vendor with no master record routes to review when the currency is ambiguous. Add a slice of evaluation by vendor and a test with a $-only Canadian invoice.

    D3. Chain of events: the batch endpoint is synchronous, so the client holds one HTTP request open for the whole batch. Rate limits slow the batch (the gateway correctly waits and retries), it runs past the client's one-hour timeout, and the client retries. The server never learns that the first request was abandoned, so the first run keeps going while the second and third start, each processing the same documents under new request ids and each enqueueing review items for the same inconsistent invoices, which also triples model spend and makes the rate limiting worse. Fixes: turn large batches into asynchronous jobs with a job id and polling (Chapter 29), make processing idempotent per document (exercise P4), and cap synchronous batch size well below what fits in a client timeout. Telemetry that would have shown it live: overlapping extract.batch spans with the same size and document ids, a rising llm.complete retry count with RateLimitError, http.request spans whose duration exceeds the client timeout, and duplicate document_id values in the review queue's pending items.

    D4. Root cause: the document carried an indirect prompt injection that targeted a value, not the instructions. The model followed the "note" and copied the planted PO. Every gate passed because each checks something the attacker controls: the schema is satisfied, the quote really occurs in the document (the grounding gate proves presence, not authority), and the business rules are arithmetic and say nothing about which PO is right. Evidence-weighted scoring even rewarded the answer, because the model was confident and its quote was found. The design treated "occurs in the document" as "true", and in effect let untrusted content choose a value that drives an action, which violates the book's sixth mental model, "the model proposes, code authorizes": a document is untrusted input, and only a system of record can authorize a PO. Fixes, none of which depend on the model resisting the injection: a reference check against the purchasing system (exercise P1), so a PO must exist, belong to this vendor, and have enough open amount; a rule that a document containing two different PO-shaped identifiers is ambiguous and goes to review; optionally a positional rule that the PO quote must come from the header block; and a detector for instruction-like text addressed to automated systems, recorded as a warning that lowers the score (Chapter 27). Telemetry that reveals it: the location of evidence quotes (offset relative to document length), the count of distinct PO-shaped tokens per document, and reference-check mismatches by vendor. Test: the injected fixture must route to review with a reference-check or ambiguity violation.
