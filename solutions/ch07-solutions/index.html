    Chapter 7 — Solutions¶

    Knowledge questions¶

    K1. Hard constraints: context window, tool use, multimodality, data residency, and output length (part of the window). Trade-off axes: task capability, reasoning depth, latency, price, reliability and availability. Structured-output quality can be either. It is hard when the consumer needs a guaranteed schema and has no repair path, or when the provider's schema mode is required for correctness. It is soft when prompt-and-parse with validation and repair (Chapter 6) is acceptable, because then a model without native schema mode still works, only with a different failure rate. The router encodes this as a soft gap with a warning.

    K2. A false accept is a cheap-model answer that was wrong and was accepted without escalation. It costs quality, or a retry plus rework if something downstream catches it. A false escalation is a cheap-model answer that was right and was escalated anyway. It costs the strong model's price and latency but never quality. Router accuracy is the share of correct accept-or-escalate decisions, so it weighs the two errors equally. Their real prices usually differ by orders of magnitude, so the threshold that maximizes router accuracy is generally not the one that maximizes utility. In the chapter's sweep, router accuracy chose the same threshold in all three error-cost regimes, while utility chose three different policies.

    K3. A point estimate from a small set carries large sampling error. Sixty cases give a 95% interval about fifteen to twenty points wide around 0.80. Choosing on the point estimate selects candidates that were lucky on this set as often as candidates that are good. The lower bound only passes a candidate when the data supports the floor. The cost is conservatism: a genuinely adequate cheap model can be rejected until the evaluation set is large enough to narrow its interval. The remedy is more cases, not a looser rule.

    K4. Expected calibration error is the case-weighted average, over confidence bins, of the absolute gap between a bin's mean confidence and its accuracy. An overconfident top bin means wrong answers carry the highest confidences the model reports. A threshold escalates only answers below it, so errors at the top confidence are caught only by a threshold that also escalates nearly every correct answer. The cascade's achievable quality is bounded by the errors the signal can separate from correct answers, regardless of where the threshold is set.

    K5. When the main difficulty is access to knowledge rather than multi-step inference; when the task is bounded and the needed facts are in your corpus; when latency and cost matter; and when an evaluation on your data shows the small model is sufficient once it receives the evidence. If the task needs several dependent inference steps over the facts, retrieval alone will not close the gap.

    K6. Pinning protects against behavior changes without a deploy (a provider updating a floating name), makes every trace attributable to an exact version, and makes rollback a configuration change. The obligation it creates: you must actively re-evaluate and repoint pins, track deprecation dates so a retired pin does not become an outage, and run a release process (harness, per-category comparison, canary) for each repoint.

    Engineering questions¶

    E1. Requirements: tools, up to about 150k prompt tokens plus output, EU zone. From the illustrative catalog: primary nw-reasoning (200k, tools). nw-general (128k, tools) is a valid fallback only for requests that fit in 128k, so it belongs in the fallback list and the capability filter will skip it for larger requests. nw-longctx must never be a fallback, because it lacks tool calling; the router would skip it anyway, but listing it signals a misunderstanding. For a 250k-token request, no model in the catalog has both the window and tools, so the router raises NoCompatibleModelError. The application should then reduce the context: retrieve and summarize logs by time window, or decompose the research into sub-queries over chunks (a recursive or map-reduce pattern), rather than truncating silently. When the primary is down and the request is 150k, the only compatible model is unavailable, so the request fails fast with a clear error or is queued; that is correct behavior.

    E2. Make the utility model slice-aware: a silent-error cost per priority, set from the 20-minute human cost for P1 and near zero for P4. Collect outcomes once, then sweep thresholds per priority and pick the utility-maximizing threshold for each. In the router, let the cascade's min_confidence depend on request metadata (priority), or define separate routes per priority with rules. New data needed: priority known at routing time (from the requester or an upstream classifier, which itself can be wrong and must be evaluated), enough labeled P1 cases to estimate the small model's P1 accuracy with a usable interval, and a validated estimate of the human cost per misroute by priority. Because P1 tickets are rare, consider sending them straight to the strong model by rule; the escalation savings on a rare slice are small and the error cost is high.

    E3. For: handles nuanced requests rules cannot separate; adapts to new traffic by prompt change. Against: adds a full model call (latency and cost) to every request; its decisions drift with model updates; it is manipulable through user text (users can talk their way to the expensive route); its errors are harder to explain. Required test: on a labeled routing set, compare end-to-end utility (including the router's own cost and latency) against the existing rule-plus-classifier router, with paired comparison and per-route error rates. Accept only if utility improves beyond the interval. Production safeguards: output validated against the closed set of route names with a default on anything else; policy rules (data zone, risk) evaluated before it and not overridable; per-user and per-route spend caps; caching of routing decisions for repeated prompts; route-distribution monitoring with alerts; a kill switch back to rules.

    E4. (a) Skip the cheap stage for predicted-hard requests: a rule or classifier sends them directly to the strong model, removing small-plus-large latency from the tail; price: classifier errors and its own cost. (b) Tighten the cheap stage with a short timeout and stream the strong model's answer, so time to first token stays low; price: occasional unnecessary escalations when the cheap model is merely slow, and streaming only helps if the SLO is on first token. (c) Lower the escalation rate below 5%, either by lowering the threshold (price: more false accepts, lower quality) or by improving the cheap model or its confidence signal (price: engineering or fine-tuning effort). A fourth option is speculative parallelism for uncertain requests: call both models concurrently and cancel the strong call if the cheap answer passes; this bounds latency at the strong model's but pays for both calls on those requests.

    E5. Numbers needed: monthly input and output tokens on the moved traffic (about 1.8 billion input and 120 million output tokens here) and the hosted per-token prices; for self-hosting, the cost per node-hour, sustained throughput per node for this prompt shape (input-heavy, so prefill matters as much as decode), the number of nodes needed to meet the p95 latency at the peak hour, and the people cost of running them (on-call, upgrades, evaluation of each server or quantization change). Traffic shape decides the answer: capacity is sized for the business-hours peak, so average utilization across nights and weekends may be 20 to 30 percent, and the cost per token must be computed at that average, not at peak throughput. A managed open-weight endpoint billed per token removes the utilization problem and is the natural intermediate comparison. Before any cost comparison matters, run the selection harness on the exact self-hosted deployment (same weights, quantization, server version, prompt) and confirm it meets the quality floor on its lower bound, per slice; a cheaper candidate that fails the floor is not a candidate. Also check the model's license terms and whether the move changes the data zone in a way that helps or hurts.

    Practical exercises¶

    P1. Expected implementation: a confidence function or router hook that calls the small client twice (second call with a different temperature or a second small model) and returns 1.0 on agreement and 0.0 on disagreement, or the router gains an agreement signal option. Attempts must record both small calls with cost and latency. In cascade_eval, CaseOutcome gains small_agree: bool and a second small cost and latency; simulate gains a signal selector, charging both small calls on every case. Acceptance: tests show (a) a case where both small answers agree on a wrong label is accepted, demonstrating agreement's blind spot; (b) the cost per request for agreement policies includes two small calls; (c) a comparison table at two error prices with both signals' utility. With the chapter's deterministic keyword fake, the two samples always agree, so the solution must use a second, differently behaving small fake; noting this is part of the expected answer.

    P2. Expected implementation: UtilityModel replaced or extended by a mapping from slice key (priority) to silent-error cost; CaseOutcome gains a slice field populated from EvalCase.tags; a sweep_by_slice returns the best threshold per slice. In the router, Route gains min_confidence_by: dict[str, float] keyed by a metadata field, with fallback to min_confidence. Acceptance: a test where per-slice thresholds produce strictly higher total utility than the best single threshold on the ticket set with costs such as P1 0.05, P2 0.01, P3 0.002, P4 0.0002 (illustrative); a router test showing a P1 ticket escalates at a confidence where a P4 ticket does not; online and offline results still match.

    P3. Expected implementation: deprecation_date: date | None on ModelProfile; a check_deprecations(catalog, routes, today, warn_days) function returning warnings for routed aliases expiring within the window and raising for expired ones; Router calls it in _check_config with an injectable clock. Acceptance: tests with a fixed date for both a warning and a failure, a test that unrouted aliases are ignored, and the JSON catalog round-trips the date.

    P4. Expected implementation: run_effort_sweep(name, client, efforts, cases, scorer, pricing) that, for each effort level, copies each request with metadata["reasoning_effort"]=level and records a candidate named name@level; results merge into one SelectionReport before the Pareto computation. Acceptance: with a fake whose latency and accuracy grow with effort (a handler reading the metadata), the report shows one row per effort, the Pareto front marks dominated levels, and choose can select a lower effort when it meets the floor.

    Debugging exercises¶

    D1. Root cause: the prompt update shifted the small model's self-reported confidence downward, so answers that used to be reported at 0.80 or above now land at 0.70 to 0.79, just under the cascade threshold of 0.80. Accuracy is unchanged, so the extra escalations are false escalations: paying the large model for answers the small model already had right. Telemetry that reveals it: escalation rate on small_first jumped from 15% to 61%; the attempt records show low_confidence with confidences clustered just under the threshold; the calibration table re-run on the new prompt shows the same accuracy per case with lower confidences. Fix: re-run the calibration and the cascade sweep for the new prompt and re-tune the threshold (or use a better-calibrated signal such as log-probabilities or a validator); add an alert on escalation rate and make any change to the cheap model's prompt trigger the cascade evaluation in CI.

    D2. Root cause: during the outage, tool-using research requests were served by a model without tool calling, so the model answered from its prompt alone and claimed to have found nothing. The router believed nw-reasoning served the request (its router.model attribute and empty substitutions list show it saw no gap), yet the completion came from the long-context model. The code path that allowed it is a fallback configured below the router: the client registered for nw-reasoning is a ModelGateway whose fallbacks list included the long-context client. The gateway falls back on retryable errors without knowing the request's requirements, and the router only sees a successful completion from the client it called. Telemetry: the completion's model field differs from the pinned model_id of the alias the router chose, tool calls dropped to zero, and finish_reason is stop on a route whose requests always carry tools. The router's model_mismatch check exists for exactly this case: it compares the completion's model with the planned pin and sets router.model_mismatch on the span, so these traces carry true, and an alert on any mismatch would have fired in the first minute of the outage. Fix: keep same-capability retries in the gateway and move every capability-changing fallback into the router's route definitions, where capability_gaps filters them; add a test that a tool-carrying request never reaches a model without tools, and an alert on tool-call rate per route.

    D3. Root cause: input distribution drift. The traffic changed (new topics, phrasing, or a new user population) so that requests now fall between the classifier's centroids or nearer the general one. The classifier's confidence dropped, more requests fell below the classifier's floor to the default (general) route, and analytical questions that need the reasoning route no longer reach it. No deploy was needed for this to happen. Confirming telemetry: share of decisions at stage default up from 5% to 19%; classifier confidence histogram shifted down; the reasoning route's share down; lower ratings concentrated on requests that the old traffic mix would have routed to reasoning; a labeled sample of recent default-route requests shows many that belong to reasoning. Earlier detection: monitor stage shares and the classifier confidence distribution with alerts, re-label a monthly sample of traffic and re-run the route classifier's evaluation, and refresh centroids from recent labeled examples. The offline 92% route accuracy was measured on the old distribution and cannot detect this.

    D4. Root cause: the pinned version behind nw-general (general-2026-02) reached its retirement date. The provider rejects it with a "model not found" error, which aie_core would map to a non-retryable InvalidRequestError, but the internal proxy translates every upstream failure into a 503. The adapter therefore raises a retryable ProviderUnavailableError, and the router, behaving as designed, moves to the next compatible candidate on the route, nw-reasoning. Every request now pays a fast failed call plus a reasoning-model call: about five times the cost (illustrative prices 0.000928 versus 0.000186 per request) and the reasoning model's latency, with unchanged quality because the fallback is stronger. Telemetry that reveals it: error attempts on nw-general at 100% starting at one instant, with millisecond latencies (a rejection, not a timeout); served_by shifting entirely to nw-reasoning; cost per request on the route jumping in a step; no matching provider incident; the alias's pin unchanged for eight months. Two changes that make it loud and early: (1) track deprecation dates in the catalog and warn at startup weeks before a routed pin expires, failing after (exercise P3), with a migration run according to the procedure in the chapter; (2) fix the error mapping so "model not found" stays non-retryable through the proxy, and alert when any alias's error-attempt rate exceeds a small threshold, so a fallback that hides an outage still pages someone. A cost alert per route (more than 20% above the 7-day median) is the backstop.
