    Chapter 9 — Solutions¶

    Identifiers match the Exercises section of book/chapters/09-vector-search-and-vector-databases.md.

    Knowledge questions¶

    K1. Each embedding model learns its own coordinate system. Dimension k in model A and dimension k in model B encode unrelated directions, so the dot product between an A-vector and a B-vector measures nothing; the scores look like numbers in the usual range and rank essentially at random. Equal dimensionality only means the arithmetic does not throw an error. Project 2 puts the embedding model name into the namespace (make_namespace(index_name, embedding_model, index_version)), and the query path computes the namespace from the same embedder it uses to embed the query, so a query embedded with model B is always sent to a namespace that only contains model-B vectors. Every record also stores embedding_model for audit and migration.

    K2. M is the maximum number of graph neighbors per node (the bottom layer typically allows 2 * M). Raising it improves recall and robustness on hard, clustered data, and costs memory (more edges per vector) and build time. ef_construction is the candidate list size used while inserting each vector to find its neighbors; raising it produces a better graph and therefore higher recall at a given ef_search, and costs only build time. ef_search is the candidate list size at query time; raising it increases recall and costs latency roughly linearly. Only ef_search can change without a rebuild; it is a per-query setting (in pgvector, hnsw.ef_search, set per transaction in Project 2). It must be at least k.

    K3. ANN recall is measured against exact search over the same vectors with the same filters: the fraction of the exact top-k that the index returned (overlap@k). It improves by raising ef_search or nprobe, raising M or ef_construction and rebuilding, or using less aggressive quantization or rescoring. Retrieval recall is measured against human (or gold-set) relevance judgments: the fraction of relevant documents found in the top k. It improves through changes upstream of the index: a better embedding model, better chunking, query rewriting, hybrid retrieval with lexical search, or a reranker over a larger candidate set (Chapters 11 and 12). Index tuning can only recover the gap between exact-search retrieval recall and indexed retrieval recall.

    K4. Expected survivors are about 60 x 0.03 = 1.8 results, so on average fewer than two of the ten requested. Ways to get all ten: pre-filter, that is restrict the candidate set to allowed rows and search those exactly (cheap here, because the allowed set is small); use a filter-aware or iterative index scan that keeps traversing until ten allowed rows are found (pgvector 0.8+ hnsw.iterative_scan); route queries with selective filters to an exact scan using an index on the filter columns; partition or namespace by the dominant filter so it is no longer a filter; or, as a weaker stopgap, raise the candidate count, which needs about 10 / 0.03, roughly 330 candidates, to expect ten survivors and still gives no guarantee.

    K5. PQ replaces each sub-vector with the id of its nearest codebook centroid, so distances computed from codes are approximations, and the ordering among close candidates is noisy. Rescoring fixes the ordering: the compressed index (kept in RAM because it is small) returns a larger candidate set, for example 100, and those candidates are re-ranked with exact distances computed from full-precision vectors kept on disk or in a cheaper storage tier; the top 10 of the re-ranked list is returned. The cost is fetching and scoring the candidate set's full vectors, which is extra I/O and compute per query proportional to the candidate count, plus storing the full vectors somewhere.

    K6. Examples: a small corpus (a few hundred documents) that fits in the context window or in a brute-force scan, where long context or exact search is simpler; exact lookups by identifier, code, or name (tickets, invoice numbers, error codes), better served by SQL, key-value lookup, or full-text search; structured data such as metrics, orders, or HR records, better served by SQL, possibly model-generated over a semantic layer; and well-structured documents with a navigable hierarchy (manuals, legal codes, API references), better served by metadata filters, section navigation, or a model choosing from an outline.

    Engineering questions¶

    E1. Expected design: keep retail, logistics, and shared in the existing shared store with tenant and ACL columns, and give wholesale its own physically separate store (its own database or schema with its own credentials and backups, or its own vector-store cluster or collection with separate keys). Query routing: a single tenancy function derives the tenant from verified identity and selects the store: wholesale users query the wholesale store plus the shared corpus (either a read-only copy of shared documents replicated into the wholesale store, or a second query against the shared store merged by score or rank); retail and logistics users never get a handle to the wholesale store. Shared documents stay authoritative in one place; if copied, the copy is derived and re-synced by the same ingestion pipeline. Deletion: wholesale deletion requests go through the ingestion pipeline (delete_document on the wholesale store), then purge caches and evaluation snapshots that contain wholesale text, record an audit event, and verify with a search that returns nothing; for a full tenant offboarding, drop the database. Monitor time-to-unretrievable against the 24-hour bound. Testing: CI tenant-leak tests with principals from each tenant asserting that no wholesale doc id ever appears for others and vice versa; gold rows tagged forbidden-doc for cross-tenant questions; a test that the wholesale store's connection credentials are not configured in the retail and logistics service instances.

    E2. Plan: (1) create namespace knowledge:<new-model>:v2 (new table or new vector column if dimensions differ; in pgvector a new table or column with the new dimension and its own HNSW index). State: Building. (2) Turn on dual-write in ingestion before the backfill starts: every changed document is written to both namespaces, so the backfill cannot fall behind. (3) Backfill from the source documents in batches with an embedding cache keyed by model and text hash, rate-limited so the backfill does not starve production embedding calls; build the HNSW index after the bulk load. (4) Verifying: run the retrieval gold set and the leak gate against v2, compare recall@k and MRR with v1 (gate: no leaks, recall@5 not lower than v1 minus a small agreed margin), run ann-check on v2, and compare chunk counts and document versions between namespaces to confirm parity. Optionally shadow a sample of live queries to v2 and compare result overlap. (5) Switch: change the active namespace (alias or config) atomically; queries must embed with the new model at the same moment, so the model setting and namespace switch together. (6) Draining: keep dual-writing and keep v1 for the rollback window; rollback is switching the alias and the query model back. (7) Retire v1. Monitor throughout: backfill progress and error rate, embedding spend, dual-write failures, ingestion lag on both namespaces, and after the switch p95 latency, underfill rate, top-score distribution, and user feedback.

    E3. Sizing: 300,000 tickets, maybe one to three chunks each, so up to about a million vectors; at 1,024 dimensions in float32 that is about 4 GB (illustrative), which fits in memory. 20 QPS. The dominant filter is the account, with very uneven sizes; most accounts are tiny, so per-account result sets are small and an exact scan of one account's rows is cheap, while a global ANN index with post-filtering would starve small accounts. Recommendation: PostgreSQL + pgvector (assuming PostgreSQL is already run), with a B-tree index on (account_id, created_at), an HNSW index for the few largest accounts' unfiltered or weakly filtered queries, and iterative scans enabled; the planner will use the B-tree for small accounts and the vector index otherwise. Alternatively exact search in memory partitioned by account. A dedicated vector database is not justified at this scale. Measurements that would change the decision: p95 latency for the largest accounts above budget at the needed ef_search; ANN recall below target for filtered queries on large accounts; vector memory competing with the transactional workload on the database; or growth projections into hundreds of millions of vectors.

    E4. A pooled connection is reused across requests. SET hnsw.ef_search = 200 at session level persists on that connection for every later request that borrows it, and any code path that changes it (a debugging session, an admin endpoint, a per-request override for "high recall mode") leaks its value to unrelated requests. Scenarios: a request that sets ef_search = 1000 for an offline evaluation leaves the connection slow, and random production requests that get that connection see latency spikes that are impossible to reproduce; or a request that lowers it to 10 for a fast autocomplete leaves the connection with ef_search below k for the next search, which then silently returns fewer results and lower recall. Similarly, enable_indexscan = off set for an exact-search measurement would turn every later query on that connection into a full scan. set_config(name, value, true) (equivalent to SET LOCAL) scopes the setting to the current transaction, so it is reset automatically at commit or rollback.

    Practical exercises¶

    P1. Expected implementation: add updated_after: date | None = None to SearchFilter and include it in is_empty. In matches, parse record.metadata["updated_at"] (the loader keeps front matter fields in metadata as strings) and compare dates, treating a missing date as not matching (fail closed for a narrowing filter). In SQL, either use the JSONB field ((metadata->>'updated_at')::date > %(updated_after)s), which needs an expression index to be efficient, or, preferably, promote updated_at to a typed DATE column populated at ingestion with a B-tree index on (namespace, updated_at), because the filter is common and typed columns give the planner statistics. Justify the choice. Acceptance: contract tests for inclusion and exclusion, a highly selective date filter whose only match is far from the query still returns it (no underfill), a build_where test showing the clause is parameterized, the offline suite passes, and the integration suite passes with DATABASE_URL.

    P2. Expected implementation: GraphIndex(m, ef_build) with fit(vectors) that links each vector to its m nearest neighbors (exact kNN graph for the teaching version, made undirected or with reverse edges), and search(query, k, ef) that starts from one or several fixed or random entry points and runs best-first search with a candidate heap of size ef and a visited set, returning the top k and the number of vectors scored. Extend bench.py with graph_sweep over ef in, for example, (10, 20, 40, 80, 160). Acceptance: recall increases monotonically with ef on the clustered data; a test shows that with ef equal to n it matches exact search; the report compares recall at matched "vectors scored" with the IVF sweep. The usual observation is that the graph reaches high recall with fewer vectors scored than IVF, while costing more memory and build time.

    P3. Expected implementation: an optional ann_index attribute on the NumPy store plus a min_ann_rows threshold. In search, compute the allowed row mask first; if the allowed count is below the threshold (or the filter is selective relative to the namespace size), run the exact pre-filtered path; otherwise query the ANN index for a candidate set larger than k, drop disallowed candidates, and if fewer than k survive, fall back to the exact path. The index must be rebuilt or marked stale when the namespace is dirty. Acceptance: tests where the filter allows exactly one row far from the query and the result has that row; tests where the filter allows fewer than k rows and the result size equals the allowed count; a property-style test over random filters asserting len(result) == min(k, allowed); and a test that results equal exact results when the ANN index is configured with full probing.

    P4. Expected implementation: the command loads the corpus, creates a store for namespace INDEX_NAME:model:v2, ingests into it, runs evaluate against both the active namespace and v2, and runs ann-check on v2. It refuses (non-zero exit, clear message) if v2 has any leak, any ingestion gap, recall@5 below active minus the configured margin, or ANN overlap below the threshold. On success it writes the active version atomically (temp file plus rename) to a state file, for example .index/active.json, and namespace_for reads it with the environment variable as fallback. Acceptance: tests with a deliberately broken v2 (a document whose ACL is changed to ["all"] in a temp corpus) prove the command refuses; a passing case switches the active version and the API serves from it; re-running is idempotent.

    Debugging exercises¶

    D1. Root cause: filtered ANN starvation by post-filtering. With pgvector's default hnsw.ef_search of 40 and no iterative scan, the HNSW scan returns about 40 nearest candidates across all tenants and the WHERE tenant = ANY(...) clause is applied to them. Retail chunks are about 2% of the table, so roughly 40 x 0.02, under one retail chunk, survives on average; shared documents also pass the filter, which is why results are 0 to 3 instead of always 0. Logistics is a large share of the table, so its queries are unaffected. The NumPy store pre-filtered and never had the problem, which is why it appeared at the migration. Telemetry: the underfilled rate and returned values by tenant, and EXPLAIN ANALYZE showing an index scan on the HNSW index with rows removed by the filter. Fixes: upgrade to pgvector 0.8+ and enable iterative index scans (hnsw.iterative_scan = relaxed_order, as PgVectorStore does when available) with an appropriate hnsw.max_scan_tuples; route selective tenants to an exact scan via the (namespace, tenant) B-tree index; partition the table by tenant, or use partial HNSW indexes per tenant, so the tenant filter is no longer part of the ANN problem; raising ef_search alone helps only partially.

    D2. What happened: the embedding service now uses a different model for queries, while the index still holds vectors from the old model. Query vectors and document vectors are in unrelated spaces, so cosine similarities collapse toward zero and the ranking is effectively random. Ingestion shows nothing because nothing was re-ingested. The span field embedding_model on search spans shows the new model name, which no longer matches the model encoded in the active namespace and the embedding_model column of the records. Structural prevention: derive the namespace from the query embedder's model (as Project 2 does), so a model change routes queries to a namespace that does not exist yet, which fails loudly (empty namespace, /healthz 503) instead of returning garbage; pin the embedding model version explicitly instead of "latest"; check at startup that the configured model equals the model recorded for the active index; and treat model changes as index migrations (E2).

    D3. Root cause: a stale ACL in the production index. The ACL fix changed only the front matter, and the declared version stayed the same, so the production ingestion job, which skips documents whose declared version is unchanged, never re-indexed the runbook. The chunks in production still carry acl_groups = ["all"], so the authorization filter correctly lets an all user see them; the filter is right, the data is stale. The evaluator did not catch it because it runs against an index built from scratch from the repository, where the runbook already has the corrected ACL, so it measures the code and the source, not the production index's state. Telemetry that reveals it: the store's doc_version (and stored acl_groups) for the runbook differs from the source's current state; an inventory diff between source ACLs and indexed ACLs. Fixes: version documents by content hash including front matter (Project 2's index_version does this, so any ACL edit triggers re-indexing); run the leak gate periodically against the production index or a snapshot of it, not only against a fresh CI build; and run a scheduled reconciliation that compares source metadata (ACL, tenant, version) with indexed metadata and alerts on drift.
