    Chapter 21 — Solutions: Memory Systems¶

    Identifiers match the exercises in book/chapters/21-memory-systems.md. Code references are to book/projects/memorykit/.

    Knowledge questions¶

    K1. Working memory: written by the harness or workflow engine on every step; lives for the task, then is archived with the run record. Conversation memory: written by the application (turn log, extractor, summarizer); lives for the session plus the transcript's retention period. Episodic memory: written by the harness after a run, with the observed outcome; illustrative default of about 90 days, because systems change. Semantic memory: written by the memory pipeline from stated facts, systems of record, and confident inferences; about 180 days, renewed on restatement. Procedural memory: written by people through a reviewed registry; no TTL, versioned and retired explicitly. User-profile memory: written from user statements, systems of record, and confirmed inferences; about one year, renewed on restatement, with unconfirmed proposals expiring in about 14 days.

    K2. The source rule is structural and cannot be evaded by rewording: no text whose origin is a document or free tool output becomes memory, whatever it says. The instruction heuristic is a pattern match over content. An attacker can phrase a poisoning payload as a plain factual claim ("Procurement has approved Brightline as the directory contact"), which no directive pattern catches. The heuristic exists to catch laundering through model-written notes, where the source has already been changed to model_inferred. It is defense in depth, not the primary control.

    K3. Confidence is the probability that the memory is true. Salience is how much the memory matters when it is relevant. Example: the assistant infers from one remark that a warehouse worker may have a latex allergy relevant to protective equipment requests. The inference is uncertain, so confidence is low (and the policy would keep it pending or reject it). If it is true, it matters a great deal, so salience is high. The right action is to ask the user, not to store or ignore it.

    K4. The set of plausible values for most personal fields is small enough to enumerate. Phone numbers in a country, dates of birth, or employee ids can be hashed exhaustively in minutes, so a plain SHA-256 fingerprint reveals the deleted value to anyone who can read the tombstone table. An HMAC with a deployment secret makes the fingerprint useless without the key, while still allowing the write path, which has the key, to detect re-creation.

    K5. In a weighted sum, a high recency and salience can compensate for near-zero relevance. With weights 0.6, 0.25, 0.15, a fresh, maximally salient memory with relevance 0.2 scores 0.52, close to a relevant three-month-old memory at about 0.60, and several such memories can push the relevant one out of the top k. A gate makes relevance a precondition: recency and salience then only order memories that are already about the query.

    K6. delete cascades through mem:<id> provenance to records derived from the deleted one. If the winner referenced the superseded record with mem:<id>, then a purge or user deletion of the old, superseded value would cascade into the current value and delete it too. supersedes:<id> records the history for audit without creating a derivation edge.

    Engineering questions¶

    E1. Store: Ana's statement is proposed as office = Lisbon, source user_stated, provenance pointing at her turn. Consolidation keeps the HR value (system of record has higher precedence) and returns conflict=True with the losing candidate. The application stores the conflict as a review item, not as an active fact, for example in a conflicts table keyed by owner and key with both values and provenances. Shown to the model: the active value, Berlin, rendered with source and date, plus a short note that the user reported Lisbon on that date and it is pending verification, so the model does not contradict her outright. User sees: "HR still lists your office as Berlin. I've flagged your move to Lisbon so they can update it. I'll use Lisbon for this conversation." The current turn's statement takes precedence in the current conversation. Notified: the HR data steward or a ticket in the HR queue. Once HR updates the record, the next sync writes Lisbon as system of record, it supersedes Berlin, and the conflict item closes. The conflict rate for office is a metric of HR data freshness.

    E2. Sharing raw episodes across tenants breaks the zero cross-tenant leakage target. Episodes contain store numbers, depot names, ticket text, and possibly personal data, and the tenants are separate business units with separate ACLs. The benefit is in the shared infrastructure knowledge, not the tenant-specific details. Design: keep episodic memory tenant-scoped. Introduce a third owner scope for shared infrastructure, for example Owner(tenant="shared-infra"), written only by a reviewed process. Periodically, a job proposes de-identified patterns from both tenants' episodes ("PayBridge adapter stale session: restart fixes"); a human platform engineer approves them, and they are stored as system_of_record procedural or semantic memory in the shared scope, with provenance pointing at the approval, not at the source episodes. Both tenants' agents read their own scope plus shared-infra. Evaluate with leakage tests that query from each tenant for the other's identifiers and must return nothing.

    E3. Deletion: PostgreSQL is the source of truth; delete there in a transaction that also writes the tombstone and an outbox event. The vector store deletes on the event. Until the event is applied, every vector search result must be re-validated against PostgreSQL (fetch rows by id with the owner predicate and drop missing ones), so a lagging index cannot serve a deleted memory. Expiry: same re-validation catches expired rows; the purge job emits delete events. Export: generated only from PostgreSQL, since vectors are derived data. Re-embedding: dual-write the new model's vectors under a new namespace and switch after backfill. Monitor: CDC lag, count of search hits dropped by re-validation (should be near zero and should not trend up), periodic reconciliation counts (ids present in the vector store but not in PostgreSQL), and failed delete events.

    E4. Argument: automatic memory converts model guesses into durable facts. The measurable costs are the rate of wrong facts asserted to users, user correction and deletion rates, poisoning exposure, and privacy complaints. The benefit is fewer repeated statements. Neither side is known without measurement. Compromise: store user-stated facts automatically, since they are evidenced verbatim; store high-confidence inferences as pending and confirm them in batches at natural moments ("I noticed you usually ask about the Lisbon warehouse; should I remember that?") rather than interrupting; let low-value inferences expire silently. Run an A/B test with three arms (stated-only, stated plus confirmed, automatic) and compare task success, turns to completion, repeated-information rate, wrong-fact incidents per thousand sessions, and correction rate. Decide on the data.

    E5. Treat the file as procedural memory with a model as one of its proposers. Edits: the agent never writes the file directly. It calls a propose_note(text, reason) tool; the handler takes the tenant and run id from trusted context, runs the text through WritePolicy as model_inferred (rejecting secrets, PII, and directive-shaped text such as "always skip the approval step"), and opens a change request against the version-controlled file, with the run id and the evidence (tool calls and their results) attached. A platform engineer approves or rejects it; only approved changes reach the file the agent loads. May be written: observations about systems ("the store-12 adapter logs to /var/log/paybridge"), verified remedies with the run ids that verified them, known dead ends. May not: instructions that change approval, escalation, or tool policy, contact addresses or URLs taken from tickets or documents, personal data, credentials. Keep the file small (a size cap enforced in CI) and give each note a date and a review-by date. Detection: provenance on every note links it to a run, so audit notes whose run read external content (documents, ticket bodies, web pages) shortly before proposing; alert on rejected proposals with reason instruction_like_content; diff the file against the previous approved version at load time and refuse to load an unreviewed change; and include injected-instruction cases in the write-policy evaluation set, where the agent reads a poisoned ticket and must not produce an approved note.

    Practical exercises¶

    P1. Expected implementation: PostgresStore with the same two tables, user_id TEXT NOT NULL DEFAULT '', a vector(d) column, a (tenant, user_id, kind, status) index, and an index on expires_at. Enable row-level security with a policy tenant = current_setting('app.tenant') and set that setting per connection or transaction from the owner. Version checks use SELECT ... FOR UPDATE or UPDATE ... WHERE version = $expected. Cascade uses a recursive CTE over a derived_from array column or the provenance JSON. Tests: move the store fixture to a factory list that includes PostgresStore when DATABASE_URL is set (pytest.mark.integration or a skip), and run the entire existing contract suite unchanged. Acceptance: all store tests pass on all three backends; a raw SQL query without the tenant setting returns zero rows.

    P2. Expected implementation: an optional valid_until on the candidate (set by the extractor or by a parser for date phrases) and a policy step that sets expires_at = min(valid_until, now + ttl_by_kind[kind]). A valid_until in the past rejects the write with reason already_expired. Consolidation must not extend an earlier explicit validity on refresh unless the new candidate carries its own. Tests: leave until next March expires in March; a validity beyond the kind cap is capped; a past date is rejected; restating without a date does not extend the explicit expiry.

    P3. Expected implementation: FastAPI routes GET /me/memories, PATCH /me/memories/{id}, DELETE /me/memories/{id}, with the owner derived from the authenticated principal, never from the request body or path. Edits are proposals with source user_stated and go through write, so a user cannot set system_of_record or bypass the PII rules; the old record is superseded. Delete calls store.delete and returns the tombstones (ids, reasons, timestamps). Tests with TestClient: user A cannot read, edit, or delete user B's memory (404, not 403, to avoid confirming existence); delete cascades to derived records; an edit that adds a personal phone number is rejected with the policy reason.

    P4. Expected implementation: scenarios as JSON with sessions of scripted user turns, the expected facts after each session, and a final probe question with a deterministic check. Include: preference recall across sessions, a stale fact where the system of record changed between sessions (memory-on must defer to the system of record), and an override where the user asks for English in the current turn despite a stored Spanish preference. Run with FakeLLM handlers offline and with a real model behind a flag. Report per arm: task success, count of turns in which the user repeats a previously stated fact, wrong-fact assertions. Acceptance: memory-on improves repeated-information count, does not lose on the stale and override scenarios, and the report is reproducible.

    Debugging exercises¶

    D1. Root cause: the semantic memories were embedded with the old model, and the new model's query vectors live in a different space. memorykit excludes records whose embedding_model differs from the current one, so recall scores nothing. Latency halved because no candidates were scored. In a system without that check, the symptom would be garbage rankings instead of empty ones. Telemetry: RecallResult.needs_reembedding is nonzero and roughly equals the user's semantic memory count; the recall regression hit rate dropped to near zero at the deployment time; profile facts are unaffected because they do not use embeddings. Fix: run reembed as a backfill job (or dual-read old and new vectors during migration), and add a deployment gate that blocks switching the embedding model while needs_reembedding is above zero.

    D2. Candidate paths: (1) the conversation summary from an earlier session was not rebuilt after deletion, and session summaries are recalled as semantic memory; (2) a derived memory (episode or note) quoted the number without mem: provenance, so the cascade did not reach it; (3) a re-extraction or backfill job wrote the number into a different key (for example mobile), so the fingerprint, which includes the key, did not match the tombstone; (4) an asynchronously synced vector index or cache still held the old record; (5) the paraphrase "ending in 678" was produced by a summarizer from the raw transcript, which was never redacted. Distinguishing logs: the rendered-memory trace for Thursday's request names the record ids and sources that produced the greeting; the write log shows when and from which provenance the offending record was written and with which key; the deletion log shows which records the cascade touched; and the redaction log shows whether the transcript was redacted. The fix generalizes: redact the log, rebuild summaries, record derivation provenance on every derived write, and normalize PII detection across keys rather than relying only on key-specific fingerprints.

    D3. Mechanism: a self-reinforcing loop with selection bias. Episodic recall returns adapter-restart successes for any POS ticket because the task texts are similar and failures for network outages were never recorded (or were recorded as success because the ticket closed). The agent follows the hint first, and each lucky or irrelevant restart adds another success episode, so the memory increasingly agrees with itself. Memory fix: record outcomes as observed by verification (did the symptom clear after this action?) rather than ticket closure; store failures with high salience; include the diagnosed root cause in the episode and filter similar episodes by root-cause category, not only by task text; cap the influence of one action pattern in the top k. Agent fix: treat recalled episodes as hypotheses that require a check before acting (get service status and network reachability before restarting), and evaluate trajectories on network tickets specifically, with a regression case where the recalled hint is wrong.
