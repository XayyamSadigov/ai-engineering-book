    Chapter 25 — Solutions¶

    Knowledge questions¶

    K1. Task completion measured by end state says nothing about how the state was reached. An agent can reach the correct state through an action it was not allowed to take (a reply sent without approval, data read through a forbidden tool), and that action is the failure the business cares about most, because it is a policy or security violation that happened in production even though the user got the right result. Defining traj_success as completed AND safe AND loop-free makes the headline metric fail in exactly those runs. If the runtime silently skipped approvals, a task-completion dashboard would show a flat, high completion rate (possibly even higher, since no run waits for or is blocked by an approval), while the approval-violation rate, if anyone computed it, would equal the share of runs that sent replies. The dashboard would look like a good week.

    K2. Replay fidelity is the share of tool results in a replayed run that agentkit served from the recording, as opposed to replay misses (exported as unrecorded) because the original run never made that call with the same action key, that is, the same tool and canonical arguments. Replay evaluates well any change that keeps the planner on or near the recorded path while changing its decisions: prompt wording, a model swap that makes the same calls in a different order, removing redundant calls, stopping earlier, or skipping a step. Changing a write tool's arguments is a miss in agentkit's replay (nothing executes), so replay evaluates it only as "the planner deviated"; the projected end state then lacks the record and completion fails. It evaluates badly any change that makes the planner ask new questions: new tools, different read arguments (a reworded search query), new branches that depend on observations the old run never saw. Those need a live run against mocked or sandboxed tools that can answer arbitrary calls.

    K3. A wrong value is both a wrong claim (the system asserted something false, which is what precision penalizes) and a missed fact (the correct value is not in the output, which is what recall penalizes). Counting it only once would make a wrong total look as harmless as a missing one, though the wrong one is worse because it flows downstream unreviewed. Evidence is scored only for correct fields because a wrong field is already a failure on the field metrics; scoring its evidence too would count one error twice, and its evidence has no "correct" location to compare against anyway, since the gold value it should support is not the value that was extracted.

    K4. - Macro-F1 asks: how good is the classifier across all categories, with each category counting equally regardless of size? It decides whether a cheaper model is acceptable overall without letting large categories hide small ones. - Per-class recall asks: of the tickets that really belong to a given class, how many did we catch? For security_report, it decides whether security incidents reach the security queue; it gets its own floor because a miss is expensive. - Calibration asks: when the classifier says 0.9, is it right about 90% of the time? It decides whether confidence can drive the escalation threshold (route low-confidence tickets to a human or a stronger model), and whether a cascade built on that threshold behaves as designed.

    K5. Each look is a separate test with a 5% chance of crossing the threshold by noise when nothing changed. The looks are correlated (they share data) but not identical, so the chance that at least one of many looks crosses grows well beyond 5%; the chapter's simulation shows 16% for ten looks. The planned-looks rule fixes the number of looks in advance and spends the 5% across them (alpha divided by the number of looks per look), so the probability of any false rollback over the whole canary stays at or below 5%. It also changes promotion: it promotes only at the final look and only on positive evidence of non-inferiority, not on a mere absence of significant harm.

    K6. Any two of: - Lexical echo: generated questions reuse the source's wording. In a report, the synthetic slice scores much higher on retrieval recall than the golden or production slices, and bias_report shows a large overlap gap; difficulty tags skew to easy-lexical. - Explicit-fact clustering: generators favor facts stated plainly in tables, headings, or bold text, and underproduce questions needing inference, multiple documents, or negative answers. In a report, the synthetic slice's coverage matrix is dense on a few documents and sections and empty on multi-document or abstention cells; scores on it are higher than on expert-written hard cases. - Shared blind spots: when the same model family generates and answers, its misunderstandings appear in both questions and expected answers, so they are scored as correct. In a report, the synthetic slice agrees with the system more than human review of a sample does; human-reviewed synthetic cases show a higher error rate in expected answers than the automatic filters caught.

    Engineering questions¶

    E1. Example specification: - allowed_tools: get_service_status, lookup_oncall (a read tool returning the on-call engineer for a service), page_engineer (side effect, approval-gated or at least rate-limited). - reference_steps: 3 for the degraded branch (status, lookup, page), 1 for the healthy branch (status only; looking up the on-call engineer is unnecessary but tolerable). - max_steps: 4 for degraded, 3 for healthy. - Degraded case: final_state_contains a page record {"service": "scanner-fleet", "engineer": "<expected id>"}; expected_args for page_engineer: service = scanner-fleet, engineer id equal to the lookup result. - Healthy case: final_state_forbids any page record ({"collection": "pages", "where": {}}). - Both: approval before page_engineer if the policy requires it; no loops.

    For replay, record two agentkit runs of the baseline agent: one where get_service_status returned degraded and one where it returned healthy (canned FunctionTools in a recording session, as build_agent_runs.py does). Create two cases, each pointing at its event log. The healthy case is the important one: the new planner sees the recorded healthy status and must not page. If it pages, that call is a replay miss because the healthy recording contains no page, so nothing executes; the attempt still appears in the export as a page_engineer tool call, so add an assertion (or a forbidden tool in allowed_tools for that case) that fails on any attempt to page. If the new planner calls lookup_oncall on the healthy branch where the baseline did not, that call is a replay miss and fidelity drops; either accept that (the decision not to page is still evaluated) or add the lookup to the recording.

    E2. - Weights: set by the legal or finance owner. Example: party names, effective date, termination date, governing law, total contract value, payment terms, and liability cap at 3; renewal terms, notice periods, and signatories at 2; addresses, reference numbers, and descriptive fields at 1. - Critical fields: party names, total value, effective and termination dates, liability cap. They must be exact on every contract; the gate uses must_pass_all. - Evidence: a quote plus page number for every non-null field; verify that the quote exists on that page and supports the value; for long clauses, accept a quote that contains the key value or phrase instead of the whole clause. - Slices: template or counterparty, language, scan quality (native text or OCR), page count bucket, table presence. - Keeping the fast suite under five minutes: run the deterministic evaluator on a stratified sample (for example, 30 contracts covering every slice and every contract with a past critical failure) using cached or replayed extractor outputs where only the evaluator changed; run the full set nightly. Extraction is deterministic to score, so the cost is the model calls; cache them by document hash and prompt version so unchanged documents are not re-extracted.

    E3. - Split pipelines by source. Merge requests from forks run the unit tests and the fast suite with stand-ins or a self-hosted small model, with no protected variables. GitLab does not expose protected variables to fork pipelines by default; keep it that way. - Mark the provider keys as protected and masked variables available only on protected branches and scheduled pipelines. The nightly suite runs from a schedule on the default branch. - For internal merge requests that need a real-provider check, use a manually triggered job on a protected environment with required approval, not automatic exposure. - Baselines live in an artifact store or a protected branch. Only the release job, which runs on tags from the protected default branch, writes them. The gate reads baselines from that location, not from the merge request's tree, so a merge request cannot lower its own bar. Changes to gates.toml and pins require code-owner approval. - Never print secrets in logs; the gate summary contains only metrics and case ids.

    E4. Adding early promotion to a rule designed only to control false rollbacks introduces a second error: promoting a harmful or merely equal release because it looked better at an early look by chance. Each early-promotion look is another opportunity for that error, so unplanned early promotion inflates the probability of promoting a bad release. A sound design defines both boundaries in advance. Plan K looks; at each look, roll back if the harm test crosses its boundary, and promote early only if the improvement (or non-inferiority) test crosses its boundary, with each boundary's alpha spent across the looks (Bonferroni, or an alpha-spending function such as O'Brien-Fleming, which is strict early and lenient late). Require a minimum sample and minimum duration (a full weekly cycle, for example) before any promotion, because early traffic is rarely representative. Keep the critical-event rollback unconditional. If the business wants continuous monitoring rather than planned looks, use an always-valid sequential test instead of adapting a fixed-sample test.

    Practical exercises¶

    P1. Expected implementation: a scripted_tools(case) factory returning agentkit FunctionTools whose functions follow a per-case script: canned reads, a degraded status for a named service, a tool that raises TransientToolError on its first call and succeeds on the second (agentkit retries transient errors on idempotent tools per LoopConfig.transient_retries), and sandboxed writes. Approval-gated tools keep requires_approval=True, and the approver follows the case specification (approve or deny), never defaulting to approve. The agent target first replays with agentkit_replay_target; if that case's replay fidelity is below the gate threshold (read from config or passed in), it runs AgentRuntime(candidate_llm, scripted_tools(case), policy=DefaultPolicy(allowed=...), approver=...), exports the events with trajectory_from_events, and records {"mode": "live-sandbox", "replay_fidelity": x} in TargetResult.metadata, otherwise {"mode": "replay"}. Acceptance: a test where the candidate planner asks an unrecorded question produces mode live-sandbox with a complete trajectory and a correct end state. A test where the tool fails transiently once shows attempts == 2 on the ToolResult event and passes the loop check, because a retry is not a loop. The mode appears in the Run JSON and in the per-suite report.

    P2. Expected implementation: add an optional labels: Mapping[str, tuple[list[str], list[str]]] argument mapping a field to required and forbidden label words (for example, total requires one of "total", "total due", "amount due" and forbids "subtotal"). evidence_status returns a new status wrong_label when the quote contains the value but fails the label rule. Update ExtractionEvaluator to pass the defaults for total, subtotal, and tax. Acceptance: tests using INV-003, INV-012, INV-014, and INV-017 (untaxed statements where subtotal equals total) show that a quote of the subtotal line is now wrong_label for the total; quotes of the correct total line still pass on all 20 invoices; the baseline extractor's evidence score falls from 0.994 to reflect all five statement invoices.

    P3. Expected implementation: a build_summary_dataset() that loads the inc- documents with shared_data.load_docs(), with hand-written key facts (root cause, impact, duration, action items), must-keep qualifiers where the report has exceptions, and a compression band (for example 0.05 to 0.35). A stand-in summarizer (FakeLLM handler) whose baseline returns a fixed good summary per document and whose regressed version drops a qualifier and changes one number. Register the suite in SUITES and add a [[suites]] section with must_pass_all on summary_faithfulness and summary_qualifiers, min_mean on summary_coverage, and must_pass_all on summary_compression_ok, plus a pinned hash. Acceptance: baseline passes, regressed fails with the dropped qualifier and the changed number named in the summary detail; baselines regenerated with run_suite.py --system baseline.

    P4. Expected implementation: a stand-in classifier that takes a seed per trial (from the case id and the repeat index, so runs are reproducible), adds noise to confidence, and flips a label with small probability on ambiguous tickets. A nightly test marked eval_full runs run_target with repeats=3, writes the run, and the gate gains an aggregator, for example trials, exposing pass_all_k:label_correct and flaky_rate:label_correct (the share of cases in run.flaky_cases). The gate section adds aggregate rules such as flaky_rate:label_correct <= 0.05 and pass_all_k:label_correct >= 0.85. Acceptance: with noise off, flaky rate is 0 and the gate passes; with a flip probability that makes several cases flaky, the gate fails on the flaky-rate rule and the summary lists the rule; the run records repeats = 3.

    P5. Expected implementation: a perturb_invoice(case, kind) function in taskevals/synthetic.py (or a new module) with one rule per perturbation kind. move_total rewrites the document so the total appears on a different line, gold unchanged. distractor_amount inserts a second amount with a different label (for example "Previous balance"), gold unchanged, which is exactly the case the whole-token evidence check cannot tell apart from the real total. relabel replaces field labels with synonyms ("Amount due" for "Total", "Ref" for "PO"), gold unchanged. Each variant gets a derived id (INV-007~move_total), the tags of its source plus origin:synthetic and perturbation:<kind>, the source invoice as group key so a source and its variants never straddle a split, and metadata recording the rule and source hash. Validation checks that every gold value still appears in the perturbed text, so a broken rule cannot produce an unanswerable case. The gate gains a slice rule on origin:synthetic for field_f1_weighted and critical_fields_exact, and the dataset hash is re-pinned in a reviewed change. Acceptance: the report shows the synthetic slice separately; the baseline extractor's letter-format PO misses reappear under relabel; the stand-in's subtotal-quote habit becomes visible under distractor_amount once P2's label check is in place; and no synthetic case enters the holdout.

    Debugging exercises¶

    D1. Root cause: the new prompt made the planner word its tool queries differently, so most calls were replay misses (exported as unrecorded): agentkit found no recorded result for their action keys. The planner interpreted those results as "service unreachable", concluded no ticket was needed, and stopped early. With no ticket expected in its reasoning, it made fewer calls (efficiency rose) and, on tasks whose specs had weak or missing state predicates, success rose. The improvement is an artifact of divergence: the replay no longer measured the planner on the recorded situation. The gate should have failed on mean replay fidelity below 0.9, and those cases should have been rerun in a live agentkit runtime over sandboxed tools. Telemetry that reveals it: replay_fidelity at 0.55; a jump in tool results with status unrecorded; final answers mentioning unreachable services; shorter trajectories. The broader lesson is that commenting out a gate rule is a gate change and must go through review like one; the specs for tasks that should create tickets also need final_state_contains predicates so that "did nothing" cannot pass.

    D2. The new model is more accurate but badly overconfident: it reports confidence above 0.9 on almost everything while being right only 68% of the time in that bin. Accuracy and macro-F1 do not depend on confidence, so they improved, while any decision that uses confidence is now broken: an escalation threshold at 0.7 escalates almost nothing, and cases that should go to a human or a stronger model are auto-handled. Whether to block depends on whether confidence drives behavior. At Northwind it drives escalation, so the gate is right to block. The fix is to recalibrate on the dev set (temperature scaling or isotonic regression for scores you control, or a lookup from stated confidence to observed accuracy for verbalized confidence), re-run the suite to confirm ECE is back under the ceiling, and re-tune the escalation threshold on dev data. If confidence were unused, the ECE rule should not be in the gate at all.

    D3. Root cause: the new version broke trace-id propagation to the feedback channel (for example, the UI component for the new prompt version does not attach the trace id, or the new service path generates a different trace id than the one logged). Feedback for the new version therefore fails to join and is counted as orphans; the corrections that do join are a small, biased remainder, so the correction rate looks halved. Delayed labels arrive through a different path (the ticketing system, keyed by request id) that still joins, which is why labeled accuracy is unchanged and is the more trustworthy signal here. Telemetry to confirm: orphan rate by version and by client or UI release; trace-id presence on feedback events over time, with a step change at the rollout; feedback event volume per version normalized by traffic (the new version receives far fewer joined events per request); a sample of orphan events whose payloads reference the new version's UI. Fix the propagation, then recompute online metrics for the affected window and do not trust the canary decision made on it.
