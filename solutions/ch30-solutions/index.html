    Chapter 30 — Solutions¶

    Knowledge questions¶

    K1. Stage latencies are not perfectly correlated: a request that hits the retrieval tail rarely also hits the reranker tail and the model tail at once, so the p95 of the sum is below the sum of the p95s. Parallel stages also overlap, so their durations do not add at all. The sum is still useful as a conservative feasibility check: if the stage p95s fit inside the target, the end-to-end p95 will too. If they do not fit, the budget is at risk and a stage must get faster, move off the critical path, or the target must change. LatencyBudget.from_measurements uses the sum for exactly this reason.

    K2. Prompt caching is not memory. The provider or serving engine reuses the prefill computation for a token prefix that is byte-identical to one it processed recently, and bills those tokens at a cached rate. A hit depends on an identical prefix (same model, tokenizer, adapter and text from the first token), on any minimum prefix length the provider applies, and on the entry not having expired. It does not carry conversation state: the application still sends the whole history every time. Savings come from keeping stable content first and volatile content last, and are measured with Usage.cached_input_tokens.

    K3. Normalized query text: without it, different questions collide (or, unnormalized, trivial variants all miss). Tenant: without it, one business unit receives another's evidence. ACL scope (a hash of the caller's groups): without it, a user without HR access receives evidence retrieved for an HR user. Index version: without it, results computed before a reindex, document deletion or re-permissioning keep being served. Retriever configuration (k, fusion weights, reranker version): without it, a config change does not take effect for cached queries, and comparisons in experiments are contaminated. A TTL is also needed as a backstop for changes the version does not capture.

    K4. The two designs differ in calls per attempt, retries, success rate and review rate, and cost per call captures none of them. The agent pays its per-call price times its number of steps times one plus its retry rate, and each failure has to be paid for by the successes. A model at one tenth of the price that needs 20 calls and fails a quarter of the time costs more per success than one strong call that succeeds 90 percent of the time. Cost per successful task divides total spend by successes, so it charges each design for all of this.

    K5. Micro-batching in application code coalesces concurrent single-item requests, such as query embeddings, into one call within a few milliseconds; use it on interactive paths with a tiny wait window. Provider batch APIs take a file of requests and return results within hours at a discount; use them for offline work nobody waits on, such as classification backfills, re-embedding and evaluation runs. Server-side continuous batching is the serving engine's scheduling of concurrent sequences on the accelerator; it matters when you self-host and is why throughput depends on concurrency (Chapter 34).

    K6. A check of remaining budget is a check-then-act race. Many concurrent requests all read the same remaining amount before any of them commits its cost, so all pass and jointly overshoot the limit. Reserving the worst-case cost at admission makes each request's exposure visible to the next one immediately. Committing the actual cost afterwards releases the difference.

    Engineering questions¶

    E1. There are three placements. (a) After the full answer, before it is shown: the answer cannot be streamed, TTFT becomes completion time plus 600 ms, and the 2-second TTFT target is lost. This is acceptable only for high-risk features where streaming is disabled anyway. (b) Streamed answer with the guardrail running on the complete text afterwards: TTFT is unaffected, the 600 ms comes out of the post-model budget (validate plus reserve; the 100 ms validate budget must grow, so shrink generation's budget or the reserve), and a failing answer is retracted or annotated in the UI after the user has seen it. This suits low-risk content. (c) Incremental: run the check per sentence or paragraph on a held-back buffer, so each chunk is checked before release. TTFT grows by one chunk's check, and the check must be cheap and local, perhaps a small classifier, with the 600 ms model check reserved for the final pass. Whichever you choose, the guardrail gets its own budget line and timeout, and you must define its failure behavior: fail closed for policy-critical checks, fail open with logging for advisory ones.

    E2. Collect labeled pairs from retail's traffic: near misses from the semantic cache log, sampled and judged for whether the two questions have the same correct answer. Compute hit rate and false-hit rate per threshold on retail's data separately from logistics'. Also measure the share of retail questions that are personalized or depend on fast-changing data (inventory, promotions), which are ineligible however the threshold is set, and the business cost of a wrong answer in retail's domain. Say no if the false-hit rate at the lower threshold exceeds the agreed target. Also say no if the gain is small because retail's traffic is simply less repetitive, or if retail's answers depend on context that is not in the eligibility check, so a lower threshold would mostly add wrong hits. Per-tenant thresholds are reasonable mechanically; the decision must rest on measured false hits.

    E3. Allocate the vector database by each tenant's share of stored vectors plus query volume, since those drive its size and load. Allocate on-call and platform cost by share of direct spend or of requests. Allocate the idle failover GPU by each tenant's share of peak concurrency, since failover capacity exists to cover peaks. Storage-based allocation encourages tenants to delete stale documents; peak-based allocation encourages shifting batch work off-peak; spend-based allocation encourages the token discipline the chapter recommends. Avoid an equal split per tenant: it charges a small tenant as much as a large one, removes every incentive to be efficient, and invites the small tenant to leave the platform. Write the rule down and keep it stable across quarters.

    E4. Each replica holds its own ledger, so each admits up to the full limit and the tenant can spend up to three times its limit; alerts also fire three times. Replace the ledger with a shared store. In Redis, keep one key per tenant and day for committed spend and a hash of open reservations with expiry. Make reserve an atomic script: read committed plus open reservations, compare with the limit, and add the reservation. Make commit an atomic script that removes the reservation and adds the actual cost. Reservations need a TTL so a crashed replica's holds expire. Alert deduplication uses a set-if-absent flag per threshold and day. When the store is unavailable, choose per mode. In enforce mode, fail closed or fall back to a conservative local allowance: the limit divided by the replica count, with a small per-replica cap. In observe mode, fail open and log. Either way, alert on store unavailability, and reconcile against provider usage when it returns.

    E5. Use p = 1 − e^(−λT) and expected prefix cost per request (1 − p) × 1.25 + p × 0.1, in units of the prefix's normal input price. With one shared prompt, the prefix sees both tenants' traffic, 43 requests an hour, so λT ≈ 43 / 60 × 5 ≈ 3.6, p ≈ 0.97, and the cost is about 0.13: an 87 percent saving on the prefix for everyone. Split per tenant, retail keeps λT ≈ 3.3, p ≈ 0.96, cost about 0.14, nearly unchanged. The small tenant drops to λT = 3 / 60 × 5 = 0.25, p ≈ 0.22, cost about 1.0: at break-even, so it gets almost nothing from caching and pays the write premium on most requests. The arithmetic says: keep the shared, byte-identical system prompt first and put tenant-specific content after it, so every tenant reads the shared part from cache and only the short tenant section varies. If tenant prompts must differ, a low-traffic tenant should not use explicit caching for its own section. Check the minimum cacheable length and per-account cache scoping on the provider before relying on the shared prefix, and confirm the estimate from cached_input_tokens after rollout.

    Practical exercises¶

    P1. Expected implementation: in LatencyReport or a new tracker method, for each request with an end_to_end violation, collect the stages that also violated their own budgets, and report for each stage the fraction of end-to-end violations in which it appears. A request with no stage over budget contributes to an "accumulated" bucket: every stage slightly slow, which is a budget problem rather than a stage problem. Acceptance: a test with, for example, ten synthetic requests, where seven blow the total because retrieval exceeds its budget, two because generation does, and one through small overruns everywhere. The report gives retrieval 0.7, generate 0.2 and accumulated 0.1. Existing tests still pass.

    P2. Expected implementation: a ToolResultCache holding a read-only registry that maps tool name to TTL and tool version, built on TTLCache. The key is make_key(f"tool:{tenant}", {"tool", "arguments" (canonical JSON, sorted keys), "tenant", "tool_version"}), and key_components = {"tool", "arguments", "tenant", "tool_version"}. Provide get_or_call(tool, args, tenant, fn), which raises for unregistered tools and caches only successful results, never errors. Acceptance: lint_cache_key("tool", ToolResultCache.key_components) is empty. A send_reply call is refused. Argument order does not change the key. A version bump misses. Entries expire after the per-tool TTL under a fake clock. Two tenants do not share entries.

    P3. Expected implementation: a dataset of pairs (q1, q2, same_answer: bool) built from the shared vocabulary, including hard negatives with high word overlap and opposite answers ("carry over vacation days" versus "cash out vacation days"). For each threshold, compute the similarities with FakeEmbeddings(vocabulary=...) and cosine_similarity. Hit rate is the share of same-answer pairs at or above the threshold. False-hit rate is the share of different-answer pairs at or above it, or alternatively the share of hits that are false; state which you use. Choose the lowest threshold whose false-hit rate is at or below the target, for example 1 percent, and print the curve. Acceptance: deterministic output, a test asserting that the chosen threshold excludes every hard negative in the fixture, and documentation that a real deployment must use the production embedding model, because hashing embeddings only demonstrate the procedure.

    P4. Expected implementation: read spans with load_jsonl, bucket spend (non-cache-hit llm.complete cost plus other cost_usd) by tenant and by hour in UTC from the span start, and key each bucket by hour of week. For each tenant and hour, compute the median spend of the same hour of week over the previous seven days, then flag hours above three times that median, with a minimum absolute floor so near-zero baselines do not page. Return flagged records (tenant, hour, spend, baseline). Acceptance: a synthetic trace with eight days of steady traffic and one hour at five times normal flags exactly that hour. A new tenant with no history is not flagged below the floor. Cache-hit spans do not count as spend.

    Debugging exercises¶

    D1. Root cause: the release made the prompt prefix volatile. The date and time at the top of the system prompt change every request, or at least every minute, so no two requests share a prefix. Emitting tool definitions from a set makes their order vary between processes, because of string hash randomization, so even the part after the timestamp would not match. Provider prefix caching needs an identical token prefix from the first token, so cached input tokens fell to zero and every request paid full price for the 800-token prefix. Fix: remove the timestamp from the system prompt, or move it to the volatile tail next to the user message, rounded to the day if the model needs it. Emit tool definitions in a deterministic order (a sorted list), and add Chapter 5's prefix-stability check on rendered prompts to CI. Confirming telemetry: the cached_input_tokens / input_tokens ratio on llm.complete spans returns to its previous level, cost per request in chargeback drops back, and TTFT falls slightly, because cached prefill is faster.

    D2. Root cause: the retrieval cache key has no ACL scope. An HR user in the same tenant asked a salary question first. The miss ran the SQL query with HR's groups, and the cache stored the resulting evidence ids under a key built only from query, tenant and index version. The supervisor's identical question hit that entry and received HR evidence. The ACL filter in SQL never ran, because a hit skips the query. (If tenant were the only boundary, the same leak would happen between any two users of one tenant with different groups.) The spans show it: the supervisor's request has a retrieval span with cache_hit=true, and the evidence ids cite documents whose ACL is hr, while the request's bound groups do not include hr. The earlier HR request with the same normalized query has the miss that populated the entry. Fix: add the ACL scope (a hash of the sorted groups) to the key, and also re-check ACLs when hydrating cached ids as defense in depth. Purge the tenant's retrieval cache immediately, and treat the event as a security incident. Prevent recurrence with lint_cache_key("retrieval", ...) in CI, plus a test that issues the same query under two group sets and asserts two misses and disjoint evidence.

    D3. Contributing causes: (1) Four replicas each kept an in-memory ledger, so each admitted up to 50 USD, about 200 USD in total, which matches the observed 210. Each replica's blocked alert fired only when that replica alone crossed the limit, late in the burst. (2) The batch job's burst of concurrent requests, if reservations were not used or were too small, let many requests pass the check before any committed. (3) The worst-case estimate may have been too low: for example, if max_tokens was unset or very large for summarization, or long documents made actual input larger than estimated, commits exceeded reservations. (4) An interactive tenant budget was shared with a batch job that belongs on a batch API with its own budget and a lower priority. Fixes: a shared atomic ledger across replicas (see E4); reservations sized from real worst cases, with max_tokens always set; a separate budget and tenant or feature attribution for batch jobs, routed through the provider batch API; admission control and concurrency limits for batch traffic (Chapter 29); and an hourly anomaly alert (P4), which would have fired minutes into the spike.
