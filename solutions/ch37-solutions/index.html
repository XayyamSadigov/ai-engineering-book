    Chapter 37 — Solutions¶

    Identifiers match the Exercises section of book/chapters/37-advanced-retrieval-patterns.md. Code references are to book/projects/examples/ch37/.

    Knowledge questions¶

    K1. Every controller turn resends the system prompt, the question, the search history, and the whole evidence ledger accumulated so far. If each search adds roughly the same amount of evidence, turn n carries about n units of evidence, so total input over n turns grows roughly with n squared over two, not with n. With the chapter's illustrative numbers (300-token prompt, 600 tokens of new evidence per search), four turns send 300 + 900 + 1,500 + 2,100 = 4,800 input tokens against 940 for a single-shot request. The code bounds it in two ways: Budget.max_searches and Budget.max_steps cap the number of turns, and Budget.max_evidence_tokens caps the ledger, because EvidenceLedger.add refuses evidence once the token total would exceed it. De-duplication (a chunk already in the ledger is skipped, and exclude=ledger.seen keeps the retriever from returning it) also stops repeated evidence from inflating the ledger. Stall detection ends runs that add nothing.

    K2. A local query starts from entities named in the question, links them to graph nodes, expands their neighborhood k hops, and returns the facts (edges) found there with their source chunks. It suits questions about specific entities and their relationships: "What does the PayBridge Adapter depend on?" or "Which team owns the action item that registers store certificates?". A global query does not start from entities; it maps the question over community summaries (each summary describes a cluster of related entities), keeps the relevant partial answers, and reduces them into one answer. It suits questions about the corpus as a whole: "What recurring causes appear across Northwind's incident reports?" or "Which teams appear most often as owners of incident action items?". No single chunk or neighborhood contains those answers.

    K3. A missed merge splits one real entity into two nodes, so each node's neighborhood is incomplete: the system misses some facts and answers with lower recall, often visibly ("I found no owner"). A false merge combines two different entities, so every fact about either attaches to both: answers become confidently wrong, mixing properties of unrelated things, and the error is invisible because the answer still cites real sources. False merges also propagate into community detection (two clusters fuse) and every summary built from them. Wrong answers with citations are worse than incomplete answers, which is why resolution rules should favor precision and send uncertain merges to review.

    K4. MaxSim takes, for each query token vector, its highest similarity with any token vector of the document, and sums those maxima over query tokens. It is cheaper than a cross-encoder at query time because document token vectors are computed once at indexing time; at query time only the short query is encoded and the score is a matrix product plus a row-wise maximum. A cross-encoder must run the full model over every query-document pair at query time. It is more expensive to store than single vectors because it keeps one vector per document token instead of one per passage: storage scales with passage length (for example 200 vectors per passage instead of 1), partly offset by smaller dimensions and compression.

    K5. (1) Low traffic per scope: a cached prefix expires after its time-to-live, so if requests for a scope arrive less often than the TTL, every request is a cache miss and pays the cache-write price, which is usually higher than the plain input price. (2) Permission scopes: each distinct set of visible documents needs its own prefix, so the cache fragments; twelve scopes means twelve prefixes to keep warm. (3) Prefix instability: anything that changes the prefix (a corpus update, a per-user line before the documents, a timestamp, a different document order) invalidates the cache, so a prefix that changes often is written repeatedly and rarely read. The chapter's calculator shows (1) and (2) together: twelve scopes at 20,000 questions a month cost more with caching than without.

    K6. A per-reader budget multiplies down the recursion: if each reader may make 20 calls and each call may recurse, a depth-2 tree can make 20 + 20 × 20 + 20 × 20 × 20 calls. The configured limit then says nothing about the cost of a question. A shared counter makes the budget a property of the top-level question: every reader, at every depth, draws from the same pool, so total calls are bounded by the configured number regardless of how the model recurses. RecursiveReader.answer resets self.calls once per top-level question, and _answer checks and increments the same counter at every depth.

    Engineering questions¶

    E1. Keep the baseline (hybrid retrieval, reranking, metadata filters, ACL) for the 340 single-hop questions and measure its failure rate on that slice first; that is where most of the volume and most fixable errors are. For the 28 multi-hop questions whose second hop follows a "Related documents" link, do not build an agentic loop: parse the links at ingestion into a link table and add a deterministic workflow step that, when a retrieved document links to others, retrieves within the linked documents with the same query (or a fixed decomposition). It is predictable, cheap, and testable. For the 20 aggregates over tickets, add a SQL route over the tickets table through a semantic layer with the Chapter 36 guard, and a router rule that sends count, sum, and filter questions there. For the 12 corpus-wide incident questions, do not build GraphRAG for 3 percent of traffic over a few dozen incident reports: run a query-focused map-reduce over incident documents the user can see, possibly cached per day. Not built, and why: GraphRAG (build and maintenance cost far exceeds the value for 12 questions; links already exist explicitly), agentic RAG (hop structure is known), late interaction (no evidence of fine-grained mismatch). Revisit triggers: multi-hop questions whose next hop is not a link (measured as baseline-plus-links failures on the multi-hop slice) above an agreed share, corpus-wide questions growing beyond a few percent or needing sub-minute latency, the SQL route's execution accuracy below target, and per-class answer quality dropping after corpus growth.

    E2. Trigger: the indexer's chunk diff for the edited document gives removed, added, and unchanged chunk ids. Invalidate, in order: (1) edges and node mentions whose provenance is a removed chunk, deleted in one transaction with the new graph version; nodes left with no mentions and no edges are removed. (2) Extract the added chunks, verify spans, resolve entities against the current resolver state (with overrides), and insert edges with the new chunk ids and current ACL. (3) Mark communities containing any touched node as dirty. (4) Recompute communities, incrementally if the algorithm supports it, otherwise on the next scheduled rebuild, and regenerate summaries for dirty or changed communities. Meanwhile, answer metadata shows the graph version and the summary build date, and a global answer that used a dirty community is labeled as possibly stale; local queries are already correct after step 2. ACL changes without text changes still change every edge's ACL fields: update edge ACLs in place (no re-extraction), then recompute the source-ACL list of every summary that cites those chunks; if the change restricts access, hide affected summaries immediately (fail closed) until they are rebuilt. A permission test for the old audience runs after the update.

    E3. Workload: one 400-page contract (on the order of a few hundred thousand tokens, illustrative), about 60 questions over two weeks, one small audience per contract. Long context with caching: each question sends the whole contract; 60 questions over two weeks means long gaps between questions, so the prefix cache rarely stays warm and most requests pay full price; it may not fit the window with headroom; time-to-first-token is high. Retrieve-then-read-whole: "documents" here are sections; retrieve the relevant clauses and send them whole, cheap and fast, but cross-references between clauses ("as defined in Section 1.4") need link following. TOC navigation: contracts have authored, descriptive headings and numbered sections, a single document, and questions that need whole clauses; navigation reads complete sections with exact provenance, needs no index beyond the parsed outline, costs a few calls per question, and handles cross-references naturally if the reader can open the referenced section. Recommendation: TOC navigation with section summaries added at ingestion, plus lexical search over the contract for defined terms and section numbers, and a rule that follows explicit cross-references. Access control is simple because the whole contract shares one ACL. Validate on a set of the legal team's real questions with gold clause references.

    E4. Ingestion: store the original scan; run OCR per page with confidence scores; detect tables and extract them into rows with column headers, keeping page number and bounding box per cell or row; generate a short page description for layout context; index the OCR text and the table rows (serialized with headers) for retrieval, and load line items into an invoice_line_items table (invoice id, supplier, line number, description, amount, currency, page, bbox, extraction confidence). Low-confidence pages or totals that do not reconcile (sum of lines vs printed total) go to a review queue (Project 1's ReviewQueue). Query: "total of line items over 500 USD" routes to SQL over invoice_line_items with tenant and ACL filters; the answer shows the query and links each contributing row to its page and bounding box for visual verification. Open-ended questions ("what did supplier X charge for freight?") use retrieval over OCR text and rows, and the answer step may send the cropped region image to a vision-capable model when OCR confidence is low. Evaluation: a labeled sample of scans with ground-truth fields and cells; measure OCR character error rate, table cell accuracy, line-item reconciliation rate (perception), then SQL execution accuracy and answer correctness given correct extraction (reasoning), and end to end. Security: OCR text is untrusted; strip instructions from the context and never let extracted text alter routing.

    Practical exercises¶

    P1. Change Decision.query: str to queries: list[str] = Field(default_factory=list, max_length=3) (keep query for backward compatibility by folding it into the list). In run, for a search action: drop empty and already-run normalized queries (counting them toward the stall logic), truncate the remainder to max_searches - searches, run the retrievals concurrently (a ThreadPoolExecutor for the sync retriever, or asyncio.gather with an async one), then add results to the ledger in the order the queries were given so labels stay deterministic. searches increases by the number of executed queries. StepRecord records a list of queries and, per new label, the query that produced it (already in LedgerEntry.query). Acceptance: a test where the controller requests three queries with max_searches=2 executes exactly two and records the third as skipped for budget; a test asserts each ledger entry's query equals the query that retrieved it; a test with a duplicate query in the batch executes it once; existing tests still pass.

    P2. Define class SufficiencyJudge(Protocol): def judge(self, question: str, cited: list[LedgerEntry]) -> Verdict with Verdict(sufficient: bool, score: float, missing: list[str]). Move coverage into TermCoverageJudge(min_coverage). Implement LLMSufficiencyJudge(llm) that sends the question and the cited evidence (as <untrusted_data> blocks) and asks, with complete_structured, for a schema like {"requirements": [{"need": str, "supported": bool, "evidence_label": str | null}]}; code computes sufficient = all(supported) and checks that every evidence_label is among the cited labels (unknown labels count as unsupported). AgenticRAG.__init__ takes judge: SufficiencyJudge | None = None, defaulting to TermCoverageJudge. Acceptance: existing tests pass unchanged; a FakeLLM test where the judge reports one unsupported requirement causes a gate rejection with that requirement in the feedback; a test where the judge cites a label that was not cited is treated as unsupported; the judge's model calls count toward a separate, bounded judge budget.

    P3. Parse each document's "Related documents" section (bulleted lines containing a backticked id) at ingestion into links: dict[str, list[str]], keeping only ids that exist. Implement follow_links(hits, principal, query, k): for the top hit's document, retrieve within linked documents only (filter doc_ids), skipping documents the principal cannot read. As a deterministic workflow: retrieve, follow links once, pack. On the outage question for an on-call user, the incident report links to the POS overview, so a link-restricted search with the original question finds the Payments section without a second model-generated query. Measure model calls: the agentic version uses three controller calls plus the answer; the workflow uses zero controller calls and one generation call. Acceptance: a test that the workflow's evidence contains the Payments section, a test that links to documents outside the principal's ACL are not followed, and a short comparison table of calls and evidence recall on the multi-hop gold questions.

    P4. In build_toc, accept an optional summarizer: Callable[[str], str] and a cache keyed by sha256(section_text); store summary on TocNode. The summarizer prompt asks for one line naming what the section answers ("how PayBridge certificates are tracked and renewed"). _line appends :: <summary> when present. Update keyword_picker to score section lines on title plus summary text. Acceptance: a test with a scripted summarizer that returns "card payments, PayBridge client certificate renewal 30 days before expiry" for the Payments section shows the navigator now reads prod-retail-pos-overview Payments for the renewal-process question; a test that a second build_toc call with the same text does not call the summarizer again (cache hit); summaries inherit the document ACL because they are stored per document.

    Debugging exercises¶

    D1. Root cause: the global path does not enforce summary visibility. A community summary was built from facts sourced from both the retail incident report (tenant retail, groups it-oncall, managers) and other documents, and the global query mapped over all summaries, or checked only group membership (the manager is in managers) without the tenant rule. Local queries filter each edge with the full rule (tenant must match or be shared, and groups must intersect), so they never showed retail facts to a logistics user. Telemetry that reveals it: the trace of the global query lists the community ids used and their source chunk ids; any source chunk whose tenant differs from the principal's is the leak. A permission test that would have caught it: for a logistics manager, assert that no summary used by global_query has a source with tenant retail (the chapter's CommunitySummary.visible_to requires every source to pass Principal.can_read, including the tenant check). Fix: apply the all-sources rule in the global path, or build summaries per tenant scope; add the cross-tenant permission test to CI.

    D2. Likely cause: the deterministic sufficiency gate computes coverage only over cited evidence. The new model cites sparingly (one or two labels, the most relevant), so question terms covered by other ledger entries no longer count; coverage drops below min_coverage, the gate rejects good answers, the controller searches again, and later searches find nothing new, ending with no_new_evidence. Quality is unchanged because when an answer is finally accepted it is the same answer. Confirm: count "rejected: coverage" step notes per run before and after the upgrade; recompute coverage offline on rejected answers using the full ledger instead of cited entries; compare the number of cited labels per answer. Fix: base the gate on claims rather than citation count (P2's judge), or compute coverage over cited entries plus the ledger entries from the same documents, and recalibrate min_coverage on the multi-hop slice for the new model. Add a regression test with a sparsely citing scripted controller, and alert on gate rejection rate per model version.

    D3. The reduce levels shrink by only about 20 percent each (31, 24, 19, 15, 12, 10), so the job hits the level limit before reaching one summary. That means reduce outputs are almost as long as their inputs: the new model writes long merged summaries, and with the code-side truncation removed nothing enforces the output budget. Groups that fit the reduce input budget therefore contain only one or two partial summaries, and the summary tokens per level barely fall. The forced-pairs guard did not trigger because most groups still held two partials. Fix: restore the code-enforced output cap (truncate at a sentence boundary instead of mid-sentence if that was the complaint), set max_tokens on every request, and keep the instruction to be concise. Metric that would have warned them: total partial-summary tokens per level and average output tokens per call relative to summary_tokens, alerting when a level reduces total tokens by less than half.
